# 人与 AI 的文档阅读路径及项目工作流

> 文档性质：协作方式留存  
> 不属于产品、架构或版本开发文档  
> 不进入开发 Agent 的默认上下文  
> 首次记录：2026-08-15
> 最近更新：2026-09-05

本文记录项目当前约定的人机协作方式，便于后续回忆。具体版本的开发范围和验收要求仍以该版本 `PLAN.md` 为准。

## 1. 基本分工

本项目是人机共同开发：

- 人：提出需求、验收实际产品，并在必要时选择技术方案；
- 文档 Agent：只接触项目文档，负责架构连续性、版本规划、文档验收、项目记忆，以及用户确认后的公开仓库最终发布；
- 开发 Agent：读取开发文档和源码，负责实现、测试，并在候选冻结前提交版本 RESULT 的实施、自测与偏差；
- 验收 Agent：在 PLAN 标记高风险任务或阶段收口审查时介入，检查相关源码、测试、失败路径和结构一致性。

协作参与者和执行过程只按职责记录“开发 Agent”“验收 Agent”“文档 Agent”，不使用具体客户端、模型、执行器或自动化工具名称指代协作者。产品依赖、配置和架构事实仍按实际技术名称记录；历史档案中的协作者名称只允许做不改变原意的中性化修正。

“独立源码验收”要求执行者独立：参与同一候选实现、自测、源码修复或开发结论编写的开发 Agent，不得兼任该候选的验收 Agent。更换工作目录、会话、模型或职责名称不构成独立性。开发 Agent 可以做补充自查，但只能记录为开发验证；没有符合条件的验收 Agent 时，独立验收任务保持未完成，版本保持“待验收”。

文档 Agent 不读取源码，因此不能独立声明“代码已经正确”。版本通过需要同时具备开发验证证据、必要的高风险源码验收、人工验收和文档一致性验收。

文档 Agent 负责统领全局影响，但“统领”不等于亲自修改源码。若文档改名、目录收束或架构规则变化会影响源码中的路径、构建脚本、测试输出或发布配置，文档 Agent 必须把依赖项写入当前版本 PLAN / RESULT，明确新状态、旧状态退出和复验要求；开发 Agent 完成源码修改后，再按风险安排源码验收。未完成这条同步链路前，版本不能完成最终冻结。

开发 Agent 只交付候选分支、候选 commit 和 RESULT，不操作公开 `main` 或正式 tag。文档 Agent 的发布职责不代表可以绕过用户确认、开发验证或源码验收；它只负责在全部结论收口后执行最终远端核对和发布。

## 2. 文档职责

~~~text
根 README           GitHub 普通用户的项目介绍与使用入口
docs/README         开发目标、版本边界和架构不变量
CURRENT_STATE       当前已经验收的实现事实
DECISIONS           影响后续版本的重要决策
PLAN                当前版本准备做什么
RESULT              当前版本实际做了什么及验收结论
~~~

规则：根 README 不属于开发事实真源；PLAN 规定要做什么，RESULT 记录实际做了什么，CURRENT_STATE 只记录已经验收的事实。

## 3. 工作路径与版本身份

本机长期区分三个固定、独立的 Git 仓库；公开文档只记录语义别名，不记录真实用户名、盘符和绝对路径：

| 路径别名 | 版本含义 | 使用规则 |
|---|---|---|
| `<canonical-repo>` | 文档 Agent 的本地集成线、候选接收点和唯一发布入口 | 本地 `main` 可以在发布准备期领先远端；只有此仓库配置具有 GitHub push 能力的发布 remote |
| `<current-workspace>` | 固定开发仓库，检出活动版本分支 | 开发 Agent 实现、测试并冻结候选；只从本地 canonical 同步基线，不操作公开 `main`/tag |
| `<review-workspace>` | 固定验收仓库，detached 指向本轮冻结候选 | 验收 Agent 只读源码并返回报告；会产生写入的测试在一次性临时副本和隔离 runtime 中执行 |

三个仓库各自拥有独立 `.git`，不得用 linked worktree 共享 object database、refs、remote、hooks 或 worktree 注册表。它们长期固定复用，不因版本号或返工轮次增加 `review-2`、`review-3` 等默认路径；每轮变化的是 current 的活动分支和 review 指向的候选 commit。固定仓库损坏时从 canonical 重新创建；临时测试副本只存在于受控临时目录，结束后必须清理，不升级为默认入口。

`publish/main` 表示 GitHub 当前公开主线，本地 `<canonical-repo>/main` 表示待发布集成线，annotated tag 的目标 commit 表示正式版本唯一发布身份；三者不得混称。current 的活动分支可以移动，验收只绑定不可变候选 commit，不使用“分支最新版”代替实现标识。

正常 Agent 任务只把自身固定仓库设为可写 workspace root，不以三个仓库的共同父目录作为日常可写根。current 和 review 不配置具有 GitHub push 能力的 remote；候选通过本地 Git 从 current 进入 canonical 的本地候选引用，再由 review 获取精确 commit。该结构用于防止误操作，不构成同一 Windows 账户下的对抗性安全边界；若要求 Agent 技术上无法取得其他角色权限，必须使用独立系统账户、凭据和 ACL。

更新 review 前必须确认没有验收 Agent 正在运行、仓库 clean，随后将其 detached 到新的冻结候选 commit；验收开始和结束都核对同一个 HEAD。路径和仓库隔离不建立验收独立性；独立性仍由“验收者未参与该候选实现、自测或修复”决定。

每次 Agent 交接必须同时给出：版本、语义路径、实际执行路径、基线 commit、候选 commit、分支、批准 PLAN commit/blob 和工作区状态。接收方开始任务前检查仓库根、独立 `.git`、`HEAD`、分支和 `git status`；SHA、PLAN blob 不一致或工作区不干净时停止并报告。固定路径解决“在哪里工作”，commit/blob 解决“处理的是哪一版”。

### 3.1 文件与 Git 权限

| 对象或操作 | 人 | 文档 Agent | 开发 Agent | 验收 Agent |
|---|---|---|---|---|
| 当前 PLAN | 审核、批准或撤回 | 唯一写入者 | 只读；有疑问时停止并报告 | 只读 |
| 当前 RESULT | 确认人工结果 | 负责验收、收口和发布状态 | 只在候选冻结前写实施、自测和偏差 | 只读，只返回报告 |
| 全局文档、CURRENT_STATE、根 README | 决策与确认 | 按已验证事实写入 | 只读 | 只读 |
| 源码、测试、依赖和构建配置 | 提需求并人工验收 | 不修改 | 在 PLAN 范围内修改 | 不修改 |
| current 活动分支 | 无日常操作要求 | 接收文档同步时管理 | 实现并提交候选 | 不操作 |
| review 仓库 | 无日常操作要求 | 准备冻结候选 | 不操作 | detached 只读验收 |
| 本地 `main`、正式 tag、GitHub remote | 批准发布或事故处置 | 唯一操作者 | 禁止 | 禁止 |

同一 Windows 账户无法用 NTFS ACL 区分三个 Agent，文件只读属性也可以被同账户解除并可能阻断 Git 更新。因此上述权限由独立仓库、单目录 workspace、remote 收缩和提交/验收门禁共同执行；Git hook 只能防误操作，不能替代最终 diff 与身份核对。

### 3.2 PLAN 冻结、候选和发布身份

用户批准 PLAN 时，文档 Agent 记录版本、PLAN 路径、批准 commit 和 PLAN blob。开发 Agent 与验收 Agent 必须保持该路径、普通文件类型和 blob 不变；需要返工时，由文档 Agent 在原 PLAN 末尾追加返工契约并形成新的批准 commit/blob，原始批准内容不被覆盖。版本目录仍只保留 PLAN 和 RESULT。

开发 Agent 完成实现和开发侧 RESULT 后提交候选 `H` 并确认 clean，候选即冻结。文档 Agent 从本地 current 获取 `H` 并以不发布的本地候选引用保护它，再把 review detached 到 `H`；验收结论只对 `H` 有效。开发分支之后产生的新 commit 不继承 `H` 的结论。默认在验收结束前不继续修改同一版本；确需并行时必须明确新提交尚未验收，不能移动 review 的 HEAD。

源码验收和人工验收通过后，文档 Agent 将已验收候选纳入 canonical 本地 `main`，再完成 RESULT、CURRENT_STATE、索引和必要的根 README。若最终发布候选 `R` 晚于被验收源码 `H`，`H..R` 必须只有授权文档变化；出现源码、测试、依赖、配置、构建或可执行元数据变化时必须重新验收。用户明确批准发布后，文档 Agent 才将 `R` 推送为远端 `main` 并创建 annotated tag。

## 4. 人的阅读路径

### 提需求或审核方案

1. 当前版本 `PLAN.md`；
2. 需要了解现状时读取 `CURRENT_STATE.md`；
3. 需要选择技术路线时按需读取 `DECISIONS.md`。

### 验收版本

1. 查看 PLAN 的范围和验收标准；
2. 查看开发 Agent 提交的 RESULT；
3. 实际使用产品并给出通过、需修正或补充意见。

### 回顾或学习开发过程

按版本依次阅读 `PLAN.md → RESULT.md`。PLAN 用于理解当时面对的问题和准备采用的方案，RESULT 用于理解实际结果、偏差、证据和遗留经验。

## 5. 文档 Agent 的阅读路径

### 编写新版本 PLAN

~~~text
docs/README
→ CURRENT_STATE
→ 上一版本 RESULT
→ 用户新需求和补充
→ 必要时读取 DECISIONS 或更早版本 RESULT
~~~

默认不读取全部历史文档。

### 验收版本文档

~~~text
当前 PLAN
→ 当前 RESULT
→ 人工验收反馈
→ PLAN 要求的高风险源码验收结论
~~~

文档 Agent 检查：范围是否完成、偏差是否解释、证据是否充分、结论是否与历史架构冲突。不能从 RESULT 没有提供的信息推断代码事实。

## 6. 开发 Agent 的阅读路径

~~~text
docs/README
→ CURRENT_STATE
→ 当前版本 PLAN
→ 源码和相关测试
~~~

只有 PLAN 明确要求理解某项历史决策时，才读取对应的 `DECISIONS.md` 或历史 RESULT。

用户批准后的 PLAN 对开发 Agent 只读。开始实现前必须核对批准 commit/blob；若 PLAN 缺失、不可执行或需要扩展范围，停止并交由文档 Agent 修订，不能自行修改 PLAN、以 RESULT 反向改变任务范围或用源码事实覆盖批准契约。

开发完成后，开发 Agent：

1. 在候选冻结前创建或更新本版本 `RESULT.md` 的实施、自测与偏差；
2. 将状态标记为“待验收”；
3. 记录实际完成内容、PLAN Task 对照、偏差、测试、遗留问题和建议更新的全局事实；
4. 分别记录功能验收与结构变更验收；涉及替换型变更时提供新状态生效、旧状态退出和回归证据；
5. 如果实际改动超出 PLAN，或新增触及数据、事实来源、持久化、安全、公共 API、模块职责的变化，主动标记“待独立验收”；
6. 不更新根 README、docs/README、CURRENT_STATE 或 DECISIONS。
7. 不操作 canonical 本地 `main`、GitHub remote 或正式 tag，也不通过其他目录绕过固定 workspace 权限。

开发 Agent 提交候选 commit、批准 PLAN commit/blob 和 clean 状态后，本轮候选冻结；此后不再修改该候选的 RESULT。验收结论、人工反馈、文档收口和发布状态由文档 Agent 写入。

如果当前 PLAN 包含由文档整理触发的源码同步任务，开发 Agent 还必须全仓库检查旧路径、旧文件名和固定清单数量是否仍被配置、脚本或测试引用；不能只修改文档链接或依赖 `.gitignore` 掩盖残留。

## 7. 验收 Agent 的阅读路径

PLAN 出现“高风险，需源码验收”标记时，执行定向源码验收：

~~~text
PLAN 中被标记的 Task
→ RESULT 中对应实施说明
→ 相关源码、测试和失败路径
→ 将只读验收报告交给文档 Agent
~~~

不在仓库创建独立验收报告，不直接修改 PLAN/RESULT，也不读取无关历史。数据迁移、事实正确性、持久化和安全等高风险变化应在 PLAN 中显式标记。文档 Agent 根据验收报告把结论、绑定 commit 和证据摘要写入同一份 RESULT，版本目录仍只有 PLAN 与 RESULT。

V1、V2、V3 阶段收口或重要公开发布前，PLAN 必须安排一次全局架构一致性审查。此时验收 Agent 对照 `docs/README.md`、`CURRENT_STATE.md` 和相关决策，检查实际模块职责、主调用链、并行旧路径、事实真源、配置与版本元数据；不默认重读全部历史 PLAN / RESULT。

验收 Agent 开始前必须确认自己没有参与该候选的实现、自测或源码修复；不满足时停止并报告“待独立验收”。满足独立性后，验收 Agent 必须先从 PLAN 和产品规则独立推导正向、反向和失败场景，再核对开发 Agent 的测试与 RESULT。报告必须写明被验收的 Git commit；该 commit 之后发生相关源码修改，原结论自动失效。验收过程中不得修改源码、测试、配置、构建文件或文档；任何落盘修复都会使修改者成为该补丁的开发者，并要求另一名独立验收者复验。

会产生依赖、构建物、缓存、数据库、日志或输出的验证，默认从 `<review-workspace>` 的冻结 commit 创建一次性临时副本，并强制使用临时 runtime；不得读取或修改真实 runtime、`.env`、凭据或用户输出。临时副本 cleanup 失败、review 前后 HEAD 改变、tracked/index 不 clean，或出现会影响执行的未批准 ignored 文件时，本轮验收失败。仅做静态读取的检查可以直接在 review 中完成。

返工复验继续使用同一个固定 `<review-workspace>`：前一验收 Agent 结束后，由文档 Agent 将它更新到新的冻结候选；不得在旧 HEAD 上复用旧结论，也不得为每轮返工新增默认 review 仓库。

## 8. 全局验收规则

### 8.1 功能与结构分开验收

每个版本的 RESULT 分别记录：

- **功能验收**：用户可观察行为和核心流程是否符合 PLAN；
- **结构变更验收**：本版本涉及的架构、事实来源、模块职责、废弃路径和全局元数据是否完成收口；没有结构变化时写“不适用”。

两项只使用“通过”“失败”“不适用”或“待源码复核”。动态测试只能证明已执行路径的行为，不能单独证明死代码、旧配置或旧实现已经从仓库消失。不得把局部测试“全部通过”表述为整个项目不存在其他问题。

### 8.2 替换型变更必须闭环

PLAN 出现“改为、只允许、不再、统一、替换、废弃、删除、迁移”等语义时，必须明确：

1. 新状态或唯一真源；
2. 被取代且必须退出的旧代码、测试、配置、接口或文档语义；
3. 新状态生效的正向验证；
4. 旧状态退出的反向验证；
5. 其他链路未受损的回归验证。

开发 Agent 在 RESULT 中给出上述证据；需要源码验收时，验收 Agent 独立复查。缺少“旧状态退出”证据时，只能声明新行为已经生效，不能声明迁移已经完成。

### 8.3 验收绑定实现

- 开发验证、源码验收和最终发布都必须指向明确的 Git commit；尚未提交时必须明确记录工作区状态，不能作为最终发布验收对象；交接还必须携带批准 PLAN commit/blob；
- 被验收 commit 之后如有源码、测试、依赖、配置、构建或可执行元数据变化，受影响的验收自动失效并需重跑；只有授权文档变化时，须以精确路径 diff 和文档验收证明源码树未变；
- 发布前确认最终分支和 tag 可追溯到被验收 commit，不得用旧报告证明后续代码；
- RESULT 必须记录被验收源码 commit；最终发布 commit 不要求在该 commit 自身的文档中写入自身 SHA，发布后以 annotated tag 的目标 commit 为唯一发布标识，防止“回填 SHA → 内容变化 → commit 再变化”的自引用循环；
- 源码候选通过后再把 RESULT、CURRENT_STATE、版本索引和根 README 收口为最终语义；最终发布候选相对被验收源码只能包含授权文档变化，不得为了回填该 commit 自身 SHA 继续修改入包文件；
- 文档 Agent 只能在证据与最终实现标识一致时，把结论写入 `CURRENT_STATE.md`。
- 开发侧自查不得标为独立源码验收；用户产品验收也不豁免 PLAN 规定的独立源码验收。缺少独立验收者时，RESULT 保持“待验收”，不得进入 CURRENT_STATE 或发布。
- 验收 Agent 如果在验收目录直接产生源码、测试、配置或构建修复，该修改只能视为新的开发候选补丁：必须原样同步回开发真源并进入新的冻结 commit；修改者不得独立验收自己产生的补丁，必须由未参与该补丁实现的另一验收 Agent 复验；不得继续把修复前的 HEAD 写成最终发布标识。
- V1.4.0 的单 commit 干净首发只用于切断含敏感数据的旧历史；公开仓库建立后以其 `main` 为长期基线，后续版本正常增量提交，不再逐版本重建 orphan/single-commit 仓库。
- 最终发布由文档 Agent 在用户确认后执行：先 fetch 并验证远端 `main` 仍是预期基线，再确认候选是其可快进后代，然后更新 `main` 并创建新的 annotated tag。遇到非 fast-forward、未知远端提交或已存在 tag 时停止，不把 force push 当作常规发布手段。
- 已正确发布的 tag 不移动。只有安全事故或明确发布事故无法通过新增提交修正、且用户单独授权时，才允许使用带精确旧 SHA 保护的事故处置；过程必须追加记录到对应 RESULT。

### 8.4 基础设施与资源生命周期验收

测试脚本、迁移工具、发布工具、临时目录、数据库连接、外部 client、缓存和后台任务不会因为“不增加产品功能”自动成为低风险改动。PLAN 必须先写清跨退出路径不变量，开发 Agent 自验和源码验收至少覆盖：

| 场景 | 最低证明 |
|---|---|
| 正常成功 | 业务结果正确，资源释放，临时状态清除 |
| 初始化或依赖导入失败 | 非零退出，不留下已创建的目录、文件或连接 |
| 断言失败、异常或提前退出 | 仍执行必要清理，错误保持可见 |
| cleanup 重复调用 | 幂等，不重复破坏状态 |
| 文件句柄或 client 占用 | 显式关闭后才能声明目录已删除 |
| cleanup 自身失败 | 有限重试后仍失败必须非零退出，不得静默成功 |
| 隔离边界 | 不读取、修改或删除真实 runtime 和相邻哨兵对象 |

日志只能提供诊断，不能代替判定；程序检测到验收后置条件失败却仍以 0 退出时，该项必须判为失败。开发 Agent 在交接前完成适用场景的正反向自验，验收 Agent 再从 PLAN 独立推导场景，不能只复跑开发侧命令。

验收 Agent 的动态测试默认在冻结 commit 的一次性副本中执行，并显式隔离 runtime、数据库、输出、日志、缓存、Python 环境和前端依赖缓存。`git status` clean 不能证明 ignored 文件无影响；验收开始前还必须排除 `.env`、数据库、真实输出、旧构建物和其他会改变执行结果的本地残留。

首次验收打回后，文档 Agent 必须把症状概括为完整问题类别，例如从“成功后目录未删除”上升为“所有退出路径的资源生命周期与隔离边界”，再一次性补齐返工和复验矩阵。只要求修复已观察到的单一路径，会把验收标准推迟到后续轮次，增加重复返工。

### 8.5 公开文档脱敏

- 内部执行阶段可以临时使用本机路径，但进入公开源码包前必须由文档 Agent 扫描本机绝对路径、用户名、真实凭据和把 Token 写入 URL 的示例；
- 对外档案使用 `<canonical-repo>`、`<current-workspace>`、`<review-workspace>` 或环境变量表达内部路径；公开仓库 URL、项目名和 release/tag 是正常用户入口，不按个人隐私清除；
- 脱敏不删除开发证据：版本、branch、commit、文件数、决策、验证结果和计划偏差必须保留。

### 8.6 历史档案修正边界

- 不反向改写历史 PLAN / RESULT 当时的目标、结论、决策和偏差；
- 允许隐私/安全脱敏、路径/链接迁移、编码/换行统一和明显笔误修正，但不得借机械修正改变原意；
- 发布后才能确认的远端事实或事故处理，以注明日期和“发布后补录”的附录追加；附录所在的新 commit 不属于旧 tag，也不得因此移动旧 tag。

### 8.7 定向检查与阶段审查

- 普通版本只对本次变化做定向功能、结构和回归检查；
- 数据迁移、事实正确性、持久化、安全及重要架构替换按 PLAN 安排验收 Agent 源码验收；
- V1、V2、V3 阶段收口或重要公开发布前，PLAN 必须安排一次全局架构一致性审查，用于发现 PLAN 范围外的并行旧路径、重复真源和文档—源码偏差；
- 全局审查是阶段性兜底，不替代开发 Agent 对每次变更的闭环责任。

## 9. 项目工作流

~~~text
1. 人提出需求或补充背景
2. 文档 Agent 根据已验收状态编写 PLAN
3. 人审核 PLAN；文档 Agent 记录批准 commit/blob
4. 开发 Agent 在 current 核对基线与 PLAN 身份，按 PLAN 实现和测试
5. 开发 Agent 在 RESULT 记录实施、自测和偏差，提交 clean 候选 H 后冻结
6. 文档 Agent 从本地 current 接收 H，以本地候选引用保护，并把 review detached 到 H
7. 如 PLAN 有高风险或阶段审查标记，安排未参与实现、自测或修复的验收 Agent 只读验收；动态测试在一次性临时副本和隔离 runtime 中执行
8. 验收 Agent 返回绑定 H 的报告；文档 Agent 将结论写入 RESULT
9. 人实际使用并验收产品
10. 未通过：文档 Agent 在 RESULT 标记“需修正”，必要时追加 PLAN 返工契约并形成新的批准 commit/blob，开发 Agent 产生新候选
11. 通过：文档 Agent 将已验收候选纳入 canonical 本地 main，并把 RESULT 标记“已验收”
12. 文档 Agent 更新 CURRENT_STATE、索引及必要的根 README，确认相对 H 只有授权文档变化，形成最终发布候选 R
13. 人确认是否发布
14. 文档 Agent 核对远端 `publish/main`、可快进关系和 tag 不存在，更新公开 main 并创建指向 R 的 annotated tag；异常时停止并报告
15. 人提出下一阶段需求，文档 Agent 编写下一版本 PLAN
~~~

返工继续使用同一份 PLAN/RESULT，不增加交接、评审或状态文档；开发与验收继续复用各自固定独立仓库，不为轮次增加工作树、clone 或默认路径。文档 Agent 可以在 canonical 并行讨论下一版本 DRAFT；当前候选冻结前，开发 Agent 必须同步已批准的文档变化，未批准 DRAFT 不构成当前版本任务。

## 10. RESULT 的最低信息

RESULT 保持简洁，至少包括：

1. 批准 PLAN commit/blob、对应分支和候选 Git commit；未提交时记录工作区状态，最终验收必须绑定 commit；
2. 实际完成内容和 PLAN Task 对照；
3. 计划偏差、原因和遗留问题；
4. API、数据表/模型、模块职责、配置/依赖的实际变化；无变化的类别写“无”；
5. 功能验收与结构变更验收，两项分别标记“通过”“失败”“不适用”或“待源码复核”；
6. 验证表，每项标记“通过”“失败”“未执行”或“待独立验收”，并附简短证据或原因；替换型变更必须包含正向、反向和回归证据；
7. 高风险或阶段性源码验收结论及对应 commit，如 PLAN 要求；
8. 人工验收反馈；
9. 文档验收结论；
10. 建议写入全局文档的已验证事实。
11. 发布后如发生远端修正或安全处置，在后续 main 上追加“发布后补录”，不移动已经正确发布的旧 tag。

RESULT 顶部只使用三个状态：`待验收`、`需修正`、`已验收`。

开发 Agent 的自查记录不得写成“独立源码验收已完成”。PLAN 要求独立验收时，RESULT 必须记录执行角色、被验收 commit 和独立性结论；执行者不独立、候选尚未冻结或验收后发生相关修改时，对应任务只能标记“未执行”或“待独立验收”。

## 11. 上下文控制

- 默认只读取完成当前角色所需的最少文档；
- PLAN 只写相对 CURRENT_STATE 的变化，不重复全部历史；
- CURRENT_STATE 只保存当前事实，不累积版本流水账；
- 测试只记录命令、结论和关键数据，不粘贴长日志；
- 历史细节留在各版本 RESULT，需要时再读取；
- 根 README 只服务普通 GitHub 用户，不进入开发 Agent 的默认上下文；
