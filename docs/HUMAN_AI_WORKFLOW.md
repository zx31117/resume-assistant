# 人与 AI 的文档阅读路径及项目工作流

> 文档性质：协作方式留存  
> 不属于产品、架构或版本开发文档  
> 不进入开发 Agent 的默认上下文  
> 记录日期：2026-08-15

本文记录项目当前约定的人机协作方式，便于后续回忆。具体版本的开发范围和验收要求仍以该版本 `PLAN.md` 为准。

## 1. 基本分工

本项目是人机共同开发：

- 人：提出需求、验收实际产品，并在必要时选择技术方案；
- 文档 Agent：只接触项目文档，负责架构连续性、版本规划、文档验收和项目记忆；
- 开发 Agent：读取开发文档和源码，负责实现、测试并提交版本 RESULT；
- 高性能源码验收 Agent：只在 PLAN 标记高风险任务时介入，检查相关源码、测试和失败路径。

文档 Agent 不读取源码，因此不能独立声明“代码已经正确”。版本通过需要同时具备开发验证证据、必要的高风险源码验收、人工验收和文档一致性验收。

## 2. 文档职责

~~~text
README          稳定目标、版本边界和架构不变量
CURRENT_STATE   当前已经验收的实现事实
DECISIONS       影响后续版本的重要决策
PLAN            当前版本准备做什么
RESULT          当前版本实际做了什么及验收结论
~~~

规则：PLAN 规定要做什么，RESULT 记录实际做了什么，CURRENT_STATE 只记录已经验收的事实。

## 3. 人的阅读路径

### 提需求或审核方案

1. 当前版本 `PLAN.md`；
2. 需要了解现状时读取 `CURRENT_STATE.md`；
3. 需要选择技术路线时按需读取 `DECISIONS.md`。

### 验收版本

1. 查看 PLAN 的范围和验收标准；
2. 查看开发 Agent 提交的 RESULT；
3. 实际使用产品并给出通过、需修正或补充意见。

### 回顾或学习开发过程

按版本依次阅读 `PLAN.md → RESULT.md`。PLAN 用于理解当时面对的问题和准备采用的方案，RESULT 用于理解实际结果、偏差、证据和遗留经验。

## 4. 文档 Agent 的阅读路径

### 编写新版本 PLAN

~~~text
README
→ CURRENT_STATE
→ 上一版本 RESULT
→ 用户新需求和补充
→ 必要时读取 DECISIONS 或更早版本 RESULT
~~~

默认不读取全部历史文档。

### 验收版本文档

~~~text
当前 PLAN
→ 当前 RESULT
→ 人工验收反馈
→ PLAN 要求的高风险源码验收结论
~~~

文档 Agent 检查：范围是否完成、偏差是否解释、证据是否充分、结论是否与历史架构冲突。不能从 RESULT 没有提供的信息推断代码事实。

## 5. 开发 Agent 的阅读路径

~~~text
README
→ CURRENT_STATE
→ 当前版本 PLAN
→ 源码和相关测试
~~~

只有 PLAN 明确要求理解某项历史决策时，才读取对应的 `DECISIONS.md` 或历史 RESULT。

开发完成后，开发 Agent：

1. 创建或更新本版本 `RESULT.md`；
2. 将状态标记为“待验收”；
3. 记录实际完成内容、PLAN Task 对照、偏差、测试、遗留问题和建议更新的全局事实；
4. 不更新 README、CURRENT_STATE 或 DECISIONS。

## 6. 高性能源码验收 Agent 的阅读路径

只有 PLAN 出现“高风险，需源码验收”标记时介入：

~~~text
PLAN 中被标记的 Task
→ RESULT 中对应实施说明
→ 相关源码、测试和失败路径
→ 将简短结论写入同一份 RESULT
~~~

不创建独立验收报告，不读取无关历史。数据迁移、事实正确性、持久化和安全等高风险变化应在 PLAN 中显式标记。

## 7. 项目工作流

~~~text
1. 人提出需求或补充背景
2. 文档 Agent 根据已验收状态编写 PLAN
3. 人审核 PLAN，并完成必要的技术选择
4. 开发 Agent 按 PLAN 实现和测试
5. 开发 Agent 提交状态为“待验收”的 RESULT
6. 如 PLAN 有高风险标记，安排高性能源码验收并把结论写入 RESULT
7. 人实际使用并验收产品
8. 文档 Agent 对照 PLAN、RESULT、人工反馈和源码验收结论
9. 未通过：RESULT 标记“需修正”，开发 Agent 继续修改同一版本
10. 通过：RESULT 标记“已验收”
11. 文档 Agent 更新 CURRENT_STATE；必要时更新 README 或 DECISIONS
12. 人提出下一阶段需求，文档 Agent 编写下一版本 PLAN
~~~

返工继续使用同一份 RESULT，不增加交接、评审或状态文档。

## 8. RESULT 的最低信息

RESULT 保持简洁，至少包括：

1. 对应分支、Git commit；未提交时记录工作区状态；
2. 实际完成内容和 PLAN Task 对照；
3. 计划偏差、原因和遗留问题；
4. API、数据表/模型、模块职责、配置/依赖的实际变化；无变化的类别写“无”；
5. 验证表，每项标记“通过”“失败”“未执行”或“待独立验收”，并附简短证据或原因；
6. 高风险源码验收结论，如 PLAN 要求；
7. 人工验收反馈；
8. 文档验收结论；
9. 建议写入全局文档的已验证事实。

RESULT 顶部只使用三个状态：`待验收`、`需修正`、`已验收`。

## 9. 上下文控制

- 默认只读取完成当前角色所需的最少文档；
- PLAN 只写相对 CURRENT_STATE 的变化，不重复全部历史；
- CURRENT_STATE 只保存当前事实，不累积版本流水账；
- 测试只记录命令、结论和关键数据，不粘贴长日志；
- 历史细节留在各版本 RESULT，需要时再读取；
