# V1.4.2 PLAN：发布基线与开发档案收口

> 文档角色：V1.4.2 唯一开发指令
> 当前状态：已完成；T1–T10 闭合，第三轮源码验收和用户最终验收通过
> 版本性质：补丁版本，不增加产品能力
> 强制基线：公开仓库 `v1.4.1` / `main` 共同指向的 commit `cbccdc8f40c9d4c2952c08504c14aa248fbfa29a`
> 建议分支：`version/v1.4.2`

## 1. 为什么需要 V1.4.2

V1.4.1 的业务修正和源码验收已经完成，最终公开代码也已统一到正确 commit。但重新从 GitHub README、全局文档、历史档案和发布流程走一遍后，仍发现一组不会立刻破坏核心功能、却会持续影响后续开发的问题。

这些问题有一个共同点：它们主要位于“源码之外的项目控制面”——Git 基线、发布权限、文档真源、测试环境和未来计划之间的关系。普通功能 E2E 很难发现它们，但它们会让后续 Agent 从错误基线开发、误判当前事实，甚至再次覆盖公开仓库。

因此建议单列 V1.4.2，只做工程和文档治理收口，不把它混入 V1.5.0 的产品架构调整。

## 2. 当前发现的问题

| 编号 | 问题 | 现在的表现 | 不处理的风险 |
|---|---|---|---|
| P1 | 后续开发基线不唯一 | 当前开发 worktree 不是公开的 V1.4.1 最终 commit，且混有历史未提交改动；最终候选包又位于临时目录 | Agent 可能在错误代码上继续开发，导致已发布修正丢失或旧改动被重新带回 |
| P2 | V1.4 的一次性首发方式仍可能被当成常规发布方式 | `_v14_t8_delivery.py` 会重新生成单 commit 的干净仓库；V1.4.1 实际又走了一次类似冻结流程 | 每次小版本都可能重建历史、需要强推，并让本地、tag、远端 main 再次分叉 |
| P3 | 发布责任没有写清 | 实际约定是开发 Agent 交付候选，文档 Agent 最终核对并上传 GitHub；现有工作流没有完整表达 | 开发 Agent 可能提前 push/tag，文档 Agent 只能事后修复远端 |
| P4 | 根 README 的 clone 命令不可直接使用 | 公开 README 使用 `<github-owner>` 占位符 | 普通用户复制后无法 clone，也显得项目仍是内部模板 |
| P5 | “隐私脱敏”边界过宽 | 公开仓库地址也被当作敏感信息清除 | 真正的个人信息应隐藏，但公开项目名和公开 URL 本来就是用户入口，全部占位会损害可用性 |
| P6 | 当前状态文档混入过多发布过程 | `CURRENT_STATE.md` 同时记录多个候选 commit、失败冻结过程和历史验收细节 | 默认阅读上下文过长，Agent 容易把失败候选或历史 commit 当成当前基线 |
| P7 | V1.4.1 的最终发布事实没有完整归档 | 开发汇总称已正确发布，但复核时远端 main/tag 实际不一致，后来才统一到 `cbccdc8...` | 开发经验缺失，未来无法解释为什么发布权限和远端复核成为强制规则 |
| P8 | 历史文档“永不修改”规则过于绝对 | 它与隐私修正、路径迁移、格式统一、发布后事实补录互相冲突 | 要么为了守规则保留错误，要么修改后没有规则解释，档案可信度反而下降 |
| P9 | Markdown 换行格式不一致 | 少量历史文件存在 CRCRLF 或 LF/CRLF 混用 | Git diff 噪声增大，Agent 可能误判整篇文档被改写 |
| P10 | Stub E2E 没有完全隔离用户 runtime | `_v13_stub_e2e.py` 的清理路径仍指向旧仓库内数据目录；真实 runtime 已迁到仓库外 | 本机残留数据可能造成偶发 19/20，而干净环境是 20/20；测试结果受用户数据影响 |
| P11 | 后续草稿之间存在信息不同步 | V3.0.0 草稿已记录 V1.5.0 要收束 SQLite、事实和向量架构，但 V1.5.0 草稿仍主要描述内容决策 | 执行 Agent 只读 V1.5.0 时可能看不到已经确认的架构方向 |
| P12 | 若干文档元信息已过期 | 开发文档仍把 `317c5266` 写成当前源码验收 commit，V1.4.1 PLAN 仍称“当前活动补丁”，另有日期、阶段名和版本文案小错误 | 不影响程序，但会持续降低文档作为项目真源的可信度 |
| P13 | 缺少固定工作路径和 commit 交接规则 | 主仓库、开发候选、临时冻结包和验收副本名称不稳定；交接时有时只给路径或口头版本 | 用户、文档 Agent、开发 Agent 和验收 Agent 可能读取不同代码，却都以为自己看到的是最新版本 |

## 3. 建议怎么解决，以及为什么

### 3.1 建立唯一、长期使用的开发基线

建议从公开仓库 `main@cbccdc8...` 新建一个稳定的本地开发目录或 worktree，作为 V1.4.2 及后续版本的唯一主基线。当前这个带历史改动的 worktree 只允许查阅，不把其 Git 历史或整个工作区合并回主基线；确有价值的内容按文件差异逐项确认后重新提交。

这样做的原因是：当前发布到 GitHub 的代码才是用户能够获得的真实产品。后续开发如果不从它继续，就无法证明“本地下一版本”确实包含“公开上一版本”的全部内容。

### 3.2 恢复正常的 Git 迭代方式

V1.4.0 为了第一次公开源码，需要把源码、数据和历史切开，重建一次干净首发仓库，这是合理的一次性动作。公开仓库建立后，应执行普通流程：

~~~text
公开 main → 新版本分支 → 开发与验收 → 合并/快进 main → 创建新 tag
~~~

建议 V1.4.2 删除 `_v14_t8_delivery.py` 这一“一键重建单 commit 仓库”的现行工具。V1.4 首发方法继续保留在历史 RESULT 中，但不再把它当作后续版本的发布工具。清洁检查改为只读验证：检查 Git 跟踪文件、隐私、runtime 隔离和工作区状态，不创建另一个仓库，也不改写历史。

这样做的原因是：正常增量提交能自然保留开发路径，也不需要每次重新计算一个孤立的首发包，更不应把 `force push` 变成惯例。

### 3.3 明确开发、验收与最终发布责任

建议把工作流明确为：

1. 开发 Agent 根据 PLAN 修改源码、测试和版本 RESULT，交付候选 commit，但不操作公开 `main` 和正式 tag；
2. 高风险改动由可读源码的验收 Agent 独立复核；普通低风险改动按 PLAN 指定的验证范围验收；
3. 文档 Agent 汇总实际结果，更新全局文档，并核对“代码、RESULT、当前状态、公开 README”是否一致；
4. 用户确认发布后，文档 Agent 执行远端 preflight，确认远端没有未知变化，再快进上传 `main` 并创建 annotated tag；
5. 若不是 fast-forward、目标 commit 不一致或 tag 已存在，立即停止并报告，不自动 force。

这样解决的原因是：文档 Agent 掌握当前版本应当公开什么，开发 Agent 掌握实现细节，两者各自完成职责后再交叉核对。最终发布口只有一个，可以避免“候选验收正确，但远端对象传错”。

### 3.4 修正 GitHub README 与隐私规则

根 README 的 clone 地址改为真实、可复制的公开仓库地址。隐私扫描继续禁止真实密钥、令牌、本机用户名、本机绝对路径、真实用户简历和 runtime 数据，但允许出现以下公开信息：

- 公开仓库 URL；
- 公开项目名；
- 公开 release/tag；
- 为安装和反馈所必需的 GitHub 链接。

内部历史示例如果不需要绑定公开仓库，仍可使用 `<github-owner>` 等占位符。

这样做是在“不能泄露私人信息”和“公开说明必须可用”之间划清边界，而不是把所有 GitHub 信息一律视为敏感内容。

### 3.5 收紧当前事实与历史过程的分工

建议把文档重新压回各自的唯一职责：

- `CURRENT_STATE.md` 只保留当前已验收能力、当前版本、当前公开基线和仍存在的缺口；
- 失败候选、返工原因、发布事故和验证过程放入对应版本 `RESULT.md`；
- `docs/README.md` 只保留长期产品边界、架构不变量和文档规则；
- 未来需求只进入候选版本 `DRAFT.md`，审核后才进入 `PLAN.md`。

V1.4.1 的 RESULT 建议增加一段“发布后补录”：如实说明首次上传汇总与远端实际状态不一致、最终如何复核并统一到 `cbccdc8...`。这段内容是在 V1.4.2 的 main 上追加的历史说明，不回写 `v1.4.1` tag，也不假装它原本就在发布包中。

这样既保留真实开发经验，又不让所有执行 Agent 默认加载整段历史过程。

### 3.6 给历史档案设置有限、可审计的修正规则

建议把“历史 PLAN/RESULT 不修改”改成：不重写当时的目标、结论和决策；允许以下修正，但必须保持原意并说明原因：

- 隐私与安全脱敏；
- 路径、链接和版本目录迁移；
- 编码、换行和明显笔误修正；
- 发布后才能确认的事实，以标明日期和来源的附录追加。

这样做不会把历史文档变成随时可改的百科，而是允许修复会妨碍公开、阅读或事实完整性的客观问题。

### 3.7 统一 Markdown 格式并减少无意义 diff

建议将仓库内 Markdown 统一为 LF，并在根 `.gitattributes` 增加 Markdown 换行规则。现有 CRCRLF 和混合换行文件做一次机械规范化；该操作不改写语义，验收时单独标记为格式变化。

固定换行规则后，Windows 和其他环境不会反复改动整篇文档，后续 diff 更容易审查真正的内容变化。

### 3.8 修复 Stub E2E 的 runtime 隔离

建议让 `_v13_stub_e2e.py` 每次使用临时 `RESUME_DATA_DIR`，测试结束后清理临时目录，并验证测试不会读取或修改用户真实 runtime。连续运行两次都应得到 20/20。

这不是产品功能调整，而是让测试真正具备可重复性。测试只应验证当前候选代码，不能受用户以前运行过什么影响。

### 3.9 同步未来版本草稿，但不提前开发

V1.5.0 草稿补齐已经确认的架构方向：SQLite 作为事实与向量的单一持久化载体；移除 Chroma 与 numpy + JSON 双后端；建立内部 LLM/Embedding Provider 边界；任意供应商由用户配置仍留到 V3.0.0。

V1.4.2 只修正文档之间的矛盾，不实现上述 V1.5.0 能力。这样下一版本 Agent 能看到完整目标，又不会把架构重构混进补丁版本。

### 3.10 修正版本与文档元信息

V1.4.2 实施时统一更新应用版本真源、FastAPI/OpenAPI 元数据、Stub Demo 展示和根 README，使对外版本均为 `1.4.2`。同时修正当前文档中的旧 commit、过期角色、日期、阶段名称和明显版本笔误。

版本号同步是此前已经建立的规则；本次需要把规则本身纳入发布检查，避免再次只改 README 或只改代码。

### 3.11 固定本机工作角色，并用 commit 完成交接

本机长期保留三个工作角色，实际绝对路径由本机配置，公开文档只使用以下别名：

| 路径别名 | 用途 | 写入规则 |
|---|---|---|
| `<canonical-repo>` | `main`，只代表 GitHub 已发布的最新正式版本 | 文档 Agent 在用户确认发布后更新 |
| `<current-worktree>` | 当前活动版本分支，V1.4.2 为 `version/v1.4.2` | 开发 Agent 与文档 Agent 按交接阶段顺序写入，不并发修改 |
| `<review-worktree>` | 指向候选 commit 的干净验收副本 | 验收 Agent 只验证；需要修正时退回开发工作树，不在此直接修复 |

本机建议固定为 `Projects` 下的 canonical、current、review 三个目录，但真实用户名和绝对路径不得写入公开仓库。随机 临时 worktree、`%TEMP%` 构建目录和旧验收副本不得再被称为 canonical 或 current。

每次交接必须同时给出：版本、基线 commit、候选 commit、分支、工作区状态。Agent 开始任务前必须执行等价检查，确认 `HEAD`、分支和 `git status` 与任务一致；发现 SHA 不一致或工作区不干净时必须停止并报告，不能自行选择“看起来较新”的目录。

这里区分两个“最新”：`<canonical-repo>/main` 是最新正式版本；`<current-worktree>` 是最新开发候选。四方需要共享同一 commit 身份，不需要并发写同一个物理目录。

## 4. V1.4.2 建议范围

### 包含

- 建立并记录唯一 canonical 开发基线；
- 修正 Git 增量开发和发布流程；
- 明确文档 Agent 是公开 main/tag 的最终发布执行者；
- 删除一次性首发重建工具，改为只读清洁验证；
- 修正公开 README 的 clone 地址和隐私边界；
- 精简全局文档并补录 V1.4.1 的真实发布过程；

- 同步 V1.5.0 草稿与已确认的远期架构；

- 固定 canonical/current/review 三类工作路径，并建立基线 commit、候选 commit 和 clean 状态交接规则。

3. **T2，开发 Agent + 文档 Agent**：修正根 README 的真实 clone 地址和隐私边界；更新 `HUMAN_AI_WORKFLOW.md`，写清固定工作角色、commit 交接、发布职责和 fast-forward 规则。
4. **T3，文档 Agent**：精简 `CURRENT_STATE.md`，修正全局入口和元信息；向 V1.4.1 RESULT 追加带日期的发布后事实，不移动历史 tag。
5. **T4，开发 Agent**：新增 `.gitattributes` 并一次性将 Markdown 规范为 LF；机械格式变化与语义变化必须分开检查。
6. **T5，开发 Agent**：修复 `_v13_stub_e2e.py` 的临时 runtime 隔离，连续运行两次，并证明真实 runtime 和源码树未变化。
7. **T6，文档 Agent**：补齐 V1.5.0 已确认的 SQLite、向量后端收束和 Provider 边界；只同步规划，不实施 V1.5.0 功能。

11. **T10，文档 Agent**：验收通过后汇总 RESULT 和全局文档；用户确认发布后执行远端 preflight、fast-forward main 和 annotated tag `v1.4.2`。遇到非 fast-forward、未知远端提交或已存在 tag 时停止。

## 7. 已确认的执行规则

用户已确认以下规则进入 V1.4.2：
