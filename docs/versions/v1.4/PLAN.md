> 重要依据：[D-014 PII 不依赖 gitignore 保护](../../DECISIONS.md#d-014-pii-不依赖-gitignore-保护)、[D-020 运行数据与源码仓库物理解耦](../../DECISIONS.md#d-020-运行数据与源码仓库物理解耦)

本文只描述 V1.4 相对已验收 V1.3 的发布架构整理。因涉及长期运行数据边界、统一路径配置、本地数据迁移和新发布基线，本计划使用次版本号 V1.4，而不是补丁版本号。核心目标不是每次发布制作一份人工快照，而是把运行数据与源码仓库物理解耦，使新 GitHub 仓库在后续版本中可以直接正常提交和推送。V1.4 不增加产品功能。

## 1. 目标与边界

目标：把 V1.3 已验收实现改造成“源码仓库本身即可公开、运行数据天然位于仓库之外”的长期结构，再完成一次性干净首发，并建立代码版本与文档版本的明确对应关系。

本版本要完成：

- 固化 V1.3 第三轮最终代码，消除“验收结果只存在于未提交 worktree”的状态；
- 建立统一的仓库外 runtime data root，把输入、输出、数据库、向量索引、日志、缓存和密钥配置与源码物理解耦；
- 对现有本地数据执行可回滚迁移或重建，保证解耦不丢失事实数据；
- 清理源码树中的中间产物和一次性诊断文件，并检查 PII、凭据和不应公开的大文件；
- 补齐面向 GitHub 访问者的入口说明、环境配置样例和可复现验证命令；
- 建立最终 commit、branch、tag、仓库地址与 V1.4 RESULT 的对应关系；
- 在外部发布前安排安全类高性能源码验收。

本版本不做：

- V2 的匹配、措辞、交互、性能、模板或排版优化；
- V3 的登录、多用户、服务器、数据库迁移和生产部署；
- 依赖升级、API 变更或业务架构重构；
- 为了“看起来更完整”加入未经验证的功能；
- 未经用户确认执行历史重写、force push、创建公开仓库或改变仓库可见性。

## 2. 当前基线与主要风险

已验收功能基线以 `CURRENT_STATE.md` 和 V1.3 RESULT 为准。

当前发布前事实：

1. V1.3 验收时 HEAD 为 `14b49ac`，第三轮最终修正仍在未提交 worktree；该 commit 不能单独代表最终代码。
2. worktree 含第三轮源码修改、验证脚本、文档修改和未跟踪诊断文件，需要逐项决定“发布 / 保留本地 / 删除”。
3. V1.2.1 已确认早期代码和文档曾包含真实 PII；当时只清理当前文件，没有执行 Git 历史清理。
4. `.gitignore` 只能阻止未来误提交，不能保护已经存在于历史 commit 中的敏感内容。
5. 真实 PDF、JD、DOCX、SQLite、Chroma、日志、`.env` 和 API Key 都不得进入 GitHub 发布内容。

因此，V1.4 默认不直接推送现有仓库的完整历史。

## 3. 实施路线：先识别数据边界，再完成长期解耦

### 3.1 审计目标

第一步不复制、不删除、不移动文件，只读回答以下问题：

1. 哪些目录是源码、不可变模板或公开文档，可以长期进入 Git；
2. 哪些文件可以公开，但需要脱敏、改成相对路径或换成虚构数据；
3. 哪些目录是用户输入、生成输出、数据库、向量索引、日志或缓存，必须与源码隔离；
4. 哪些脚本、二进制或第三方资源用途不清，需要进入隔离区人工判断；
5. 代码在哪里创建、读取和写入运行数据，是否存在硬编码路径或“源码目录兼作数据目录”；
6. 从全新 clone 启动时，哪些目录和文件应由程序自动生成。

### 3.2 四类文件结论

| 类别 | 典型内容 | 处理方式 |
|---|---|---|
| A：可公开源码 | API、services、models、prompts、依赖、公开配置样例 | 审计通过后直接进入发布仓库 |
| B：整理后公开 | README、历史文档、测试 fixture、模板、示例配置 | 脱敏、改相对路径、确认许可证或替换成虚构数据后进入仓库 |
| C：运行时私有数据 | `.env`、用户 PDF/JD、DOCX 输出、DB、向量索引、日志、缓存 | 移出源码资产边界；默认生成到统一 runtime root；永不进入发布仓库 |
| D：隔离审查 | 未跟踪诊断脚本、来源不明二进制、临时报告、用途不明大文件 | 先隔离并查调用关系；确认长期价值和安全性后才能进入 A/B，否则不发布 |

“需要隔离”不等于把真实数据复制到源码仓库的另一个目录。C 类数据完全不进入源码仓库；公开 Demo 必须重新生成完全虚构的数据。

### 3.3 数据—源码解耦目标结构

V1.4 必须完成以下长期边界，不以 `.gitignore` 作为主要隔离手段：

- 建立统一、可配置且**默认位于 Git checkout 之外**的 runtime data root；数据库、向量索引、输入、输出、日志和缓存都从该根目录派生；
- 用单一配置项（实现时统一命名，例如 `RESUME_DATA_DIR`）覆盖 runtime root；未配置时使用操作系统用户数据目录，不默认写入源码仓库；
- 程序首次启动时创建必要空目录和空数据库，不从 Git 仓库读取用户数据；
- 测试使用临时目录和虚构 fixture，不复用开发者的 runtime 目录；
- 系统模板等不可变产品资产与用户生成文件分目录保存；是否公开模板须单独检查内容和许可证；
- `.env.example` 只保留字段名和无效占位符；真实密钥优先使用系统环境变量或仓库外配置，不依赖仓库根目录 `.env`；
- 源码、README 和测试不出现作者本机绝对路径。

目标关系：

~~~text
Git 仓库（可公开、不可变资产）
  source / prompts / templates / docs / tests / examples / config examples

仓库外 runtime root（本地私有、可变数据）
  input / output / database / vectorstore / logs / cache / local config
~~~

运行核心流程后，Git 工作区不应因为生成数据而出现新增或修改文件。

如果解耦需要改变 API、事实模型或 V1.3 业务行为，停止实施并交回用户决定，不得借发布整理扩大重构范围。

### 3.4 现有本地数据迁移原则

数据路径改变属于高风险任务，必须采用“复制/重建 → 验证 → 切换”，不能直接移动或删除：

1. 先记录旧 input/output/database/vectorstore/log 路径、文件清单、大小、事实记录数量和关键 ID；
2. SQL 是事实源：数据库复制到新 runtime root 后校验表、记录数和关键 ID；
3. 向量索引优先从迁移后的 SQL 全量重建，不把旧 Chroma 文件视为唯一资产；
4. 用户输入和历史输出默认保留在旧位置作为本地档案，不自动进入新 runtime，也不进入 Git；是否迁移由用户按需决定；
5. 新路径完成 E2E 和人工核对前，旧数据不得删除或覆盖；
6. 保留回滚方式：恢复旧路径配置即可重新使用旧数据；
7. RESULT 记录迁移前后位置、数量、重建结果和未迁移项，但不记录真实内容。

### 3.5 首次发布与后续开发

由于历史文档已经确认旧 commit 曾包含 PII，现有 `.git` 不进入 GitHub。首次发布从审计和解耦后的 A/B 类文件建立新 Git 历史；原仓库只作为本地历史档案。

V1.4 发布通过后，新 GitHub 仓库成为后续开发的发布基线。只要后续版本继续遵守数据边界，就可以正常 commit/push，不需要每个版本重新制作或人工整理发布快照。自动 Secret、PII 和运行产物检查作为持续安全门保留。

## 4. 发布内容边界

### 必须进入仓库

- 运行核心源码、模板定义和必要静态资源；
- 精确锁定的依赖文件；
- 不含真实值的 `.env.example`；
- 数据库初始化或首次运行所需脚本；
- 可重复的 Stub E2E 和必要测试；
- 完全虚构的 Demo Profile、经历和 JD，以及一条可重复运行的演示命令；
- 根目录 GitHub README；
- `docs/` 下的全局文档和版本开发经验；
- `.gitignore` 及必要的项目配置。

### 默认不得进入仓库

- `.env`、API Key、token、cookie 和本机配置；
- 用户 PDF、JD 原文、真实简历 DOCX 和人工验收输入；
- SQLite、Chroma、numpy 向量文件和其他运行数据；
- `backend/output/` 生成物、日志、缓存、临时目录和虚拟环境；
- 仅用于一次排错且无长期复用价值的诊断脚本；
- 含真实身份、联系方式、公司、学校、项目或本机绝对路径的报告；
- 未确认许可证来源的第三方素材。

不确定的文件不得凭文件名猜测。开发 Agent 必须根据调用关系、读写路径、README 用法和测试依赖判断，并在 RESULT 记录 A/B/C/D 分类及去留依据。

## 6. 安全审计要求

T1 与 T6 至少覆盖：

1. **完整文件盘点**：同时枚举 tracked、untracked、ignored、隐藏文件和符号链接；每项进入“发布 / 排除 / 待人工判断”之一，不能只扫描 Git tracked 文件；
2. **凭据模式扫描**：API Key、Bearer token、私钥、`.env`、连接串、常见云服务密钥、高熵字符串和编码后的可疑值；
3. **人工语义审查**：检查测试常量、注释、Prompt、配置、URL、账号 ID、本机路径和内部服务地址，弥补正则无法识别的未知敏感信息；
4. **PII 扫描**：姓名、手机号、邮箱、学校、公司、项目名、用户 ID，以及此前已知的真实值清单；
5. **容器与二进制扫描**：DOCX/ZIP 解包扫描正文与属性；PDF 提取文本并检查元数据；图片检查 EXIF；SQLite、Chroma、缓存和运行数据默认直接排除；
6. **Git 清单检查**：安全扫描直接针对最终 allowlist 和待发布源码树，不以“已被 `.gitignore` 命中”代替内容安全；
7. **忽略规则验证**：对 `.env`、数据库、向量文件、output、日志、缓存、虚拟环境和真实输入构造代表路径，确认全部被忽略；
8. **大文件和许可证检查**：识别异常大文件及第三方模板、字体、图片、示例代码的分发许可；MIT 只能授权项目有权授权的内容；
9. **历史隔离检查**：干净首发仓库只能包含新发布 commit，不能意外携带原仓库 `.git`、旧对象或其他 worktree 元数据；
10. **平台防护复核**：Private 预发布阶段检查 GitHub 安全设置；转 Public 后查看 secret scanning 结果。GitHub push protection 只识别其支持的 secret 类型，不能替代本地扫描和人工审查。

任何真实凭据命中都必须先停止发布并视为已泄露处理：撤销或轮换凭据，再清理文件。只删除文本不等于风险解除。
