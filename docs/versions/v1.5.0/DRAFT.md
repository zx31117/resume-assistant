# AI Career Resume Assistant V1.5.0 草稿：履历事实级内容决策与持久化收束

> 文档角色：下一版本产品与架构草稿，供用户审核
> 状态：DRAFT，非开发指令；待 V1.4.2 收口后继续审核，不得直接执行
> 假定基线：V1.4.2 完成验收后的实现状态
> 版本边界：V1.5.0 只调整架构；检索召回效果、权重和质量调优属于 V2

## 1. 核心判断

“检索相关性”和“简历内容决策”本质上是同一个问题：面对当前 JD，完整职业履历中哪些经历仍在候选范围内，以及这些经历中的哪些事实值得占用简历篇幅。

检索结果不应只返回 Experience，再由后续模块重新选一次内容；它应直接形成可追溯的“入选事实集合”。内容生成 LLM 只改写已经选中的事实，Builder 只负责装配。

V1.5.0 先建立正确的处理顺序、数据契约和模块职责，不验收“选得准不准”。当前数据量不足以支持有意义的召回质量评估；时间权重、相关性权重、阈值、Top-K 和不同 JD 的实际选材效果统一留到 V2。

本版本同时收束本地持久化：SQLite 保存完整 Experience、Fact、索引任务和向量；Chroma 与 numpy + JSON 两套向量后端退出，避免双后端长期产生不同的写入、删除、重建和故障语义。LLM/Embedding 在内部建立 Provider 接口，但“用户填写任意供应商即可使用”仍由 V3 负责。

## 2. 目标产品链路

~~~text
完整职业履历与 Fact（SQLite 事实源）
↓
① 硬规则预筛
   时间、经历类型、用户明确排除项等
↓
② 根据 JD 检索相关事实
   检索粒度从“整段经历”下沉到“经历内部事实”
↓
③ 形成简历内容决策
   选择哪段经历 + 该经历中的哪些事实 + 表达侧重
   ② 与 ③ 是同一个决策过程，不产生两套互相冲突的结果
↓
④ LLM 改写
   只能把已选事实改写为适合当前 JD 的 bullets
↓
⑤ Builder 确定性装配
   章节、顺序、数量预算、来源映射和告警
↓
ResumeDocument
~~~

## 3. 各阶段职责

### 3.1 完整职业履历永远保留

- SQLite 中的 Experience / Fact 保存用户完整职业履历，是唯一事实源；
- 早期经历被当前简历预筛排除，不等于从职业库删除；
- 同一份完整履历可以针对不同 JD 产生不同候选经历和事实组合；
- 向量和内容决策结果都是派生数据，可以从 SQLite Fact 重建；向量与事实位于同一数据库文件不改变其派生属性。

### 3.2 第一阶段：硬规则预筛

预筛先于语义检索执行，用低成本、可解释的规则缩小候选范围。

架构需要支持的规则维度包括：

- 时间；
- 全职、实习、项目、教育等经历类型；
- 用户明确要求保留或排除的经历；
- 记录是否具有可验证事实及必要归属信息。

预筛输出至少包含 `included_ids`、`excluded_ids` 和逐项原因。被排除的 Experience/Fact 不进入后续检索和 LLM 上下文。

V1.5.0 只建立预筛阶段、规则接口和可解释输出，可以使用最小确定性规则验证链路。具体时间窗口、权重、经历类型优先级、例外策略和实际筛选效果留到 V2。

### 3.3 第二、三阶段：相关性检索就是内容决策

检索粒度从 Experience 下沉到 Experience 内部的事实单元，例如：

- 所属产品或行业；
- 用户、业务、软件或硬件相关理解；
- 需求分析、方案设计、协作、验收和交付；
- 使用的方法、工具和流程；
- 可验证的结果、指标或产物；
- 能证明某项能力的具体行为。

每个事实单元必须保留 `experience_id` 和稳定的 `fact_id`，并能回到 SQL 原始事实。相关性阶段直接产出统一的 `SelectedEvidenceSet`：

| 字段 | 含义 |
|---|---|
| `experience_id` | 所属完整经历 |
| `fact_ids` | 本次允许表达的事实 |
| `selection_reason` | 事实与当前 JD 的关联依据 |
| `expression_focus` | 表达侧重，不是新增事实 |
| `scores` | 可解释的语义、技能、岗位/领域、时间等分项 |
| `source_text` | 供核验的原始事实，不直接作为最终文案 |

该结果在架构上同时承载“选哪段经历”和“这段经历写什么”。V1.5.0 只验收结果契约、来源追踪和调用边界，不验收候选排序或事实召回的实际质量。

### 3.4 第四阶段：LLM 只改写已选事实

- LLM 输入只包含当前 `SelectedEvidenceSet`；
- 每条输出 bullet 必须回传所使用的 `fact_ids`；
- LLM 可以压缩、重组和改变表达方式，但不能增加事实；
- 未选事实不得因为“写起来更完整”而重新进入结果；
- 未知 `experience_id`/`fact_id`、无来源 bullet 或越界推断必须丢弃并告警；
- 如果选中事实不足以形成有效 bullet，应显式返回材料不足，不能用通用话术填充。

### 3.5 第五阶段：Builder 只负责装配

Builder 接收已经完成语义决策和事实约束的内容，负责：

- 映射到工作、项目、教育等章节；
- 按上游优先级、既定顺序和数量预算装配；
- 合并同一 Experience 的已选 bullets；
- 保留 Experience/Fact 来源映射；
- 对容量、重复、缺失章节和超页风险告警；
- 生成 `ResumeDocument`。

Builder 不再判断哪个事实更符合 JD，也不能用自己的规则替换 `SelectedEvidenceSet`。

## 4. 预期架构变化

| 当前边界 | V1.5.0 拟议变化 |
|---|---|
| RAG 主要返回 Experience ID | 返回 Experience 下的 Fact ID，并保留父级 Experience ID |
| 检索后由多个模块继续做语义选材 | 检索与内容决策合并为一个可追溯结果 |
| Builder 是内容选择入口 | Builder 收缩为确定性装配入口 |
| LLM 面对较完整的经历上下文再决定写什么 | LLM 只看到预先选中的事实 |
| 相关性以语义、技能、岗位为主 | 增加时间/经历类型预筛阶段，再处理保留集合；具体效果留 V2 |
| Chroma 主后端 + numpy/JSON 故障回退 | SQLite 保存 Fact 和向量，形成单一持久化实现；两套旧向量后端及其配置、分支和测试退出 |
| 业务代码直接依赖当前模型服务实现 | 建立内部 `LLMProvider` / `EmbeddingProvider` 契约；V1.5.0 只接入当前供应商适配器 |
| Experience 变化触发独立向量库同步 | SQLite 事务记录 Fact/索引状态，支持安全重建、失败可见和模型 fingerprint 隔离 |

这会形成对 D-007“RAG 多因素评分”和 D-016“Builder 是唯一内容选择入口”的拟议演进。正式 PLAN 必须明确哪些旧决策被扩展或部分替代；草稿阶段不修改 `DECISIONS.md`。

## 5. V1.5.0 边界

本版本拟做：

- 硬规则预筛阶段及其输入、输出和原因记录；
- 经历事实单元及其稳定来源 ID；
- JD 驱动的事实级相关性与内容决策统一契约；
- 受 `fact_ids` 严格约束的 bullet 改写；
- Builder 职责收缩和 ResumeDocument 来源追踪；
- SQLite 中的 Fact、向量和索引状态模型，以及从 Experience 可验证重建的路径；
- 删除 Chroma 与 numpy + JSON 双后端及其活动配置、依赖、分支和测试契约；
- 内部 `LLMProvider` / `EmbeddingProvider` 接口，并用当前供应商 Adapter 验证业务模块不再直接耦合供应商实现；
- 旧索引安全退出：迁移前后数量、来源 hash、维度/fingerprint、失败和可重试状态可核对；
- 使用少量完全虚构数据验证模块顺序、接口连通和事实边界。

本版本不做：

- 相关性权重、时间阈值、召回数量和排序策略调优；
- 用真实履历评估 Precision、Recall、Top-K 命中或人工招聘质量；
- 承诺同一经历在不同 JD 下已经能产生理想的差异化表达；
- 为效果测试专门扩充真实职业履历数据集；
- 一页纸或视觉排版优化；
- 为了匹配 JD 补造履历事实；
- 删除完整职业履历中的早期经历；
- 用户系统、服务器化和多用户数据隔离。
- 用户填写任意 LLM / Embedding API 即用、BYOK、安全存储和供应商能力探测；这些属于 V3；
- 远程向量数据库和针对大规模数据的 ANN 索引；当前预期仅几百到几千条事实，先使用 SQLite + 内存精确检索；
- 在 V1.5.0 保留 Chroma 或 numpy + JSON 作为“保险后端”。迁移失败必须显式失败或回滚，不能静默切到第二实现。

## 6. 验收草案

- [ ] Pipeline 中存在独立硬规则预筛阶段，并且发生在语义检索前；
- [ ] 预筛接口能记录 included/excluded ID 和原因，不要求当前规则达到最佳筛选效果；
- [ ] 被预筛排除的事实不会进入检索结果或 LLM 上下文；
- [ ] 检索结果包含稳定 `experience_id` + `fact_id`，可回查 SQL；
- [ ] 架构允许同一 Experience 的不同 Fact 被独立选择，而不是只能整段保留/删除；
- [ ] 每条生成 bullet 都能追溯到一个或多个已选 `fact_id`；
- [ ] LLM 不能输出未选事实，材料不足时显式失败或降级；
- [ ] Builder 不执行第二套语义相关性判断，只做确定性装配；
- [ ] 更换 JD 不修改 SQL 完整职业履历；
- [ ] 少量虚构 fixture 可以完整走通预筛、事实决策、改写、Builder 和 ResumeDocument；
- [ ] SQLite 是 Fact、向量和索引任务的唯一持久化载体，向量仍可从 Fact 重建；
- [ ] Chroma、numpy + JSON 及相关运行配置、依赖、活动分支和旧测试契约均退出，且没有隐藏 fallback；
- [ ] Fact 增删改后向量状态一致；Embedding 失败、维度或 fingerprint 改变时显式失败/重建，不使用旧向量；
- [ ] 迁移支持备份、数量/hash 核对、失败回滚和重复执行；数据与持久化变化必须由高性能源码验收 Agent独立复核；
- [ ] 业务模块只依赖内部 Provider 契约，当前供应商通过 Adapter 接入；V1.5.0 不开放任意供应商用户配置；
- [ ] 既有 V1.3.0–V1.4.2 事实边界、错误可见性、测试隔离和 DOCX 主链路无回归。

V1.5.0 不以 Precision、Recall、Top-K 命中质量、不同 JD 的表达差异或人工招聘质量评分作为 PASS 条件。

## 7. 正式 PLAN 前待确认

1. Fact 单元由程序拆分、AI 结构化提取，还是两者结合；
2. Fact 与原始 Experience 字段如何分工、版本化和保留来源文本；
3. 预筛、事实决策、改写和 Builder 之间采用哪些最小数据契约；
4. 现有 Experience 级 Chroma/numpy 索引是直接废弃后从 SQL 重建，还是提供一次性可核对迁移工具；
5. SQLite 向量字段、fingerprint、维度和索引任务采用哪些最小 Schema；
6. 同一事实支持多个 bullet 时如何保留来源映射并避免重复；
7. 当前几百到几千 Fact 的精确检索性能阈值和退化告警如何定义，但不在本版本调优相关性；
8. V2 需要采集什么规模和类型的数据，才能开始评估时间规则与事实级召回质量。
