# AI Career Resume Assistant V2.4.0 草稿：Job Model、召回与润色调优

> 文档角色：版本范围草稿，供 Product Owner 审核
> 状态：DRAFT，非开发指令，不改变当前版本状态
> 草稿日期：2026-09-19
> 假定前置：V2.3.0 的账号、多用户隔离、PostgreSQL/pgvector、ApplicationCase、埋点和服务器
> Alpha 已完成并通过独立验收
> 发布列车：V2.3.0（底座）→ V2.4.0（本版调优）→ V3.0.0（免费多用户首发）
> 核心目标：用固定评测和受控多用户 Beta 证明 Job Model、分层证据与增量生成确实改善召回、
> 润色和等待体验，同时验证浏览器助手对真实岗位页面的最小可行路径

## 1. 版本判断

V2.4.0 是质量专项版本，不再继续堆叠服务器基础设施。它把现有“JD 文本 → 两层选材 → 受约束
改写”扩展为第一版 `Person Model × Job Model`：用户侧仍以确认的 Career Memory 为事实真源；
岗位侧由 JD 明示要求、Role Prior 和有来源的 Company Context 组成。新增岗位知识只能改变召回、
排序和表达重点，不能改变用户事实命题。

本版同时建立 Stable Evidence / Adaptive Evidence 与 Fast Lane / Precision Lane，使新增智能能力不再
按步骤串行累积用户等待时间。浏览器助手进入受控网站验证：可以识别岗位、创建专项投递、展示拟填
字段并在用户确认后填充允许字段；自动上传简历只做可行性探针，最终提交始终由用户完成。

## 2. 用户结果

受控 Beta 用户应能够：

1. 从产品内粘贴 JD，或在获准招聘页面主动调用浏览器助手创建目标岗位；
2. 看见系统区分“JD 明示要求”和“岗位通常重视的能力”，不把先验冒充招聘方要求；
3. 更早看到高置信、完整且有事实来源的结果，后续精排完成后得到冻结最终版；
4. 对系统发现的信息缺口选择回答、跳过、仅用于本次或确认写回 Career Memory；
5. 在受控页面查看待填字段和来源，确认后完成个人信息填充；
6. 下载针对岗位生成的 Word/PDF，并手工上传；若自动上传探针成立，仍需用户单独确认；
7. 对结果提供低摩擦反馈，使调优指标与真实行为相互校验。

## 3. Job Model v1

### 3.1 三层结构

~~~text
JobModelSnapshot
├── explicit_requirements     JD 明示
├── role_prior_requirements   岗位先验
└── company_context           公司/业务公开信息
~~~

| 来源 | 召回 | 排序 | 表达重点 | 可声称为招聘方硬要求 |
|---|---:|---:|---:|---:|
| JD 明示 | 是 | 是 | 是 | 是 |
| Role Prior | 是 | 是 | 是 | 否 |
| Company Context | 是 | 是 | 是 | 否 |
| 无来源模型推测 | 否 | 否 | 否 | 否 |

每条 Job Model 项必须保存来源类型、来源文本或 URL、采集时间、置信度、版本、适用范围和是否允许
进入召回。联网材料可能错误或过期，不能作为用户事实，也不能静默改变 JD 原文。

### 3.2 Role Profile Library

首批 Role Profile 只覆盖 Product Owner 批准的高频岗位，每个 Profile 至少包含：

- 岗位名称及同义词；
- 基础能力维度；
- 常见工作成果与证据类型；
- 可用于召回的技能/场景词；
- 不得推定为硬要求的边界；
- 版本、编辑来源、审核状态与更新时间。

Role Prior 先进入影子评测，再进入真实选材。无法识别岗位或 Profile 置信度不足时，只使用 JD，
不得强行套用相近岗位。

### 3.3 Company Context v1

本版先支持受控来源和缓存，不建立无边界网络 Agent：

- 同一公司/业务上下文按标准实体、来源和版本缓存，避免每个用户重复研究；
- 所有公开信息保留 URL、抓取时间、摘要和过期时间；
- 公司同名、部门不明、产品线不明时显示不确定，不自动合并；
- Company Context 可以把低文本相似度但业务相关的 Fact 重新带回候选池；
- 它只能改变 emphasis，不能改变 proposition；
- 来源不可访问、过期或冲突时，系统退回 JD + Role Prior，并显示降级原因。

## 4. Person Model 与证据分层

### 4.1 Fact enrichment

在低频写入阶段，为确认 Fact 生成可重建派生数据：

- Embedding 与 fingerprint；
- 能力、技能、行业和业务场景标签；
- 关键词与通用摘要；
- 通用职业表达候选；
- enrichment 模型、Prompt、版本、来源和状态。

Fact 原文及其来源仍是唯一事实真源。任何 enrichment 变化只令派生内容失效或重建，不修改 Fact。

### 4.2 Stable Evidence / Adaptive Evidence

- `Stable Evidence`：多个相似岗位都成立、表达成熟、事实版本未变化的基础内容；
- `Adaptive Evidence`：受特定 JD、Role Prior、Company Context 或用户新补充影响，需要重新选材或
  表达的内容。

缓存键至少包含 Fact revision/hash、Role Profile family、表达策略和生成模型/Prompt 版本。目标岗位
变化后只复用仍满足边界的稳定表达；任何事实、规则或版本不匹配都必须失效，不能为了速度使用旧文。

## 5. 召回调优

### 5.1 候选生成

候选集合由以下信号共同产生：

- JD 语义相似度；
- Role Prior 能力匹配；
- Company Context 隐藏业务相关性；
- 技能、行业、场景和岗位结构化命中；
- 经历类型、时间、来源质量和事实状态；
- 用户明确保留、排除和待确认状态。

候选生成和最终排序分开记录。Company Context 的主要价值是 Recall Booster：允许文本相似度较低但
业务相关的 Fact 进入候选；最终是否入选仍由可解释排序和事实边界决定。

### 5.2 排序与评测

至少冻结：

- short / typical / long Career Memory；
- 完整、宽泛、缺失关键信息和噪声 JD；
- 多岗位、多行业、旧经历、弱相关和反例；
- Company Context 能发现隐藏相关性的样例；
- 不应被先验或公司信息误召回的负样例。

指标至少包括：

- Recall@K、Precision@K、nDCG 或等价排序指标；
- 关键岗位要求覆盖率；
- 无来源、过期和跨账号 Fact 进入率；
- 低相关性回退触发率；
- 人工选择一致性和用户最终保留率；
- 召回耗时、Embedding 调用和总成本。

跨账号召回泄漏的容忍度始终为 0，质量提升不能覆盖隔离失败。

## 6. 润色调优

润色只基于冻结 EvidenceSelection，并保留逐条 `fact_refs`。评测至少覆盖：

- 事实越界和虚构指标；
- JD 与 Job Model 关键点覆盖；
- 重复、套话、空泛和过度包装；
- Stable Evidence 与 Adaptive Evidence 的表达一致性；
- 重点变化是否只改变 emphasis，没有改变 proposition；
- 篇幅、可读性、结构与一页纸适配；
- 用户偏好胜率、保留率、局部重生成率；
- Token、延迟和单位 ApplicationCase 成本。

任何“更好”必须绑定冻结样例、盲评或真实用户行为。模型评分只能作为辅助指标，不能独立宣布质量
通过。

## 7. Fast Lane / Precision Lane

~~~text
Fast Lane
岗位识别 → Role Prior → 高置信候选 → 可复用 Stable Evidence → 首批完整结果

Precision Lane
完整 JD → Company Context → 扩展候选 → rerank → 信息缺口 → Adaptive Evidence
~~~

要求：

- 高置信完整 Fact 可以先显示，但最终文件只从冻结最终快照生成；
- Precision Lane 不得在用户不知情时把已确认内容替换成语义不同的版本；
- 中间结果标识状态和来源，`pending` 不冒充最终结果；
- 缓存命中、并行、局部重算和无需 LLM 的规则路径分别计时；
- 新增 Role/Company 智能能力不得线性叠加总等待时间；
- 性能门禁使用服务器真实环境 P50/P95、cold/warm 和缓存命中/未命中矩阵。

## 8. 信息缺口与 Fact 回流

本版建立 `PROPOSED → CONFIRMED / CURRENT_ONLY / REJECTED` 交互：

1. 系统只在当前岗位结果会因此显著改善时提出问题；
2. 问题说明为什么需要该信息，并允许跳过；
3. 用户回答先服务当前 ApplicationCase；
4. 用户明确选择后才能写回 Career Memory；
5. 冲突、低置信和模型补全进入待确认区，不覆盖旧 Fact；
6. Company Context、Role Prior 和模型猜测永远不能写入 Person Model。

## 9. 浏览器助手受控 Beta

### 9.1 能力级别

| 级别 | 能力 | V2.4.0 口径 |
|---|---|---|
| L0 | 复制/引导用户手工填写 | 必须可用的失败回退 |
| L1 | 读取当前岗位并创建 ApplicationCase | 必须通过 |
| L2 | 展示映射并由用户确认后填充字段 | 首批受控站点验证 |
| L3 | 选择并上传生成的简历文件 | 可行性探针，不承诺发布 |
| L4 | 点击最终提交 | 明确禁止 |

### 9.2 填充规则

- 用户必须先在目标网站自行登录并打开具体岗位；
- 助手只在用户点击后运行，不后台遍历页面；
- 所有字段先展示“目标字段、拟填内容、Career Memory 来源和是否敏感”；
- 联系方式等直接身份只能填入用户确认的字段；
- 开放题不能把模型生成内容无提示直接提交；
- 站点 DOM 或适配器版本变化时 fail closed，退回 L0；
- 文件上传探针必须验证浏览器安全模型、站点控件、文件生成时点和用户确认；
- 不处理验证码、MFA、密码、Cookie、反自动化绕过或最终提交。

首批站点必须在正式 PLAN 前明确，不以“任意官网通用”作为完成标准。

## 10. 埋点与实验

本版利用 V2.3.0 事件契约建立：

- 岗位捕获 → ApplicationCase → 首结果 → 最终简历 → 下载/填充的转化漏斗；
- JD-only、JD+Role Prior、JD+Role Prior+Company Context 的影子或受控实验；
- Stable Evidence 命中率和节省的模型调用；
- 信息缺口问题的回答、跳过、确认写回和后续复用；
- 浏览器助手 L0/L1/L2/L3 的成功、回退和站点适配器版本；
- 补贴/测试行为与自然行为区分。

实验事件不保存网页整页、表单正文、简历正文、JD 原文、密码、Cookie 或第三方账号标识。

## 11. 明确不做

- 不向公众全面开放；
- 不启用人民币支付；
- 不自动提交求职申请；
- 不绕过招聘网站安全或反自动化控制；
- 不承诺任意网站通用填充或自动上传；
- 不把 Role Prior 或 Company Context 写入用户职业事实；
- 不建设完整模拟面试、开放题 Agent、投递跟踪或移动端；
- 不用少量演示样例替代冻结评测和真实服务器证据。

## 12. 三天实施顺序候选

| 阶段 | 重点 | 退出条件 |
|---|---|---|
| Day 1 | Role Profile、评测集、混合召回和基线 | JD-only 与新路线可重复对比 |
| Day 2 | Stable/Adaptive、润色调优、Fast/Precision | 质量、延迟、成本矩阵成立 |
| Day 3 | 浏览器助手受控 L1/L2、Company Context 探针、Beta 回归 | 受控纵切和反向安全门禁通过 |

## 13. 验收候选

- [ ] Role Prior 不被展示或记录为 JD 明示要求；
- [ ] Company Context 有来源、版本、时间和失败降级，不改变用户事实；
- [ ] 固定评测集证明召回指标相对 V2.3.0 基线提升；
- [ ] 事实越界率不增加，未知或跨账号 Fact 始终被拒绝；
- [ ] 润色盲评或真实偏好指标提升，且延迟/成本不越过批准上限；
- [ ] Stable Evidence 的缓存键、失效和来源可复核；
- [ ] Fast/Precision 中间结果与最终冻结文件不形成双真源；
- [ ] 信息缺口回答未经确认不进入长期 Career Memory；
- [ ] 浏览器助手 L1/L2 只在用户主动操作和字段预览后执行；
- [ ] L3 自动上传有独立可行性结论，未通过时保持手工上传，不伪装完成；
- [ ] L4 最终提交、验证码/MFA/密码/Cookie 访问均不存在；
- [ ] V2.3.0 多用户隔离、备份恢复、埋点脱敏和服务器 Gate 无回归。

## 14. 正式 PLAN 前待冻结

1. 首批 Role Profile 和冻结评测集；
2. 召回、润色、延迟和成本的具体通过阈值；
3. Company Context 的批准来源、缓存 TTL 和冲突处置；
4. 首批招聘官网/平台适配器及测试账号边界；
5. L2 字段填充的允许字段和敏感字段确认方式；
6. L3 文件上传探针是否有任何站点足以进入 V3.0.0；若无，如何把 L0 手工上传冻结为正式回退；
7. Fast/Precision 中间状态的用户界面和最终结果替换规则；
8. Beta 用户数量、数据类型和退出条件。

在范围、阈值、站点和必要 Design Snapshot 获批前，本文不授权开发。
