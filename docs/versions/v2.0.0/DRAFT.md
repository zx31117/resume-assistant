# AI Career Resume Assistant V2.0.0 草稿：用户主页、个人履历库与模型管理后台

> 文档角色：V2 产品与架构草稿，供用户审核
> 状态：DRAFT，非开发指令，不改变当前版本状态
> 草稿日期：2026-08-22
> 假定前置：V1.5.0 已完成事实级内容决策、来源追踪与本地持久化收束
> 核心方向：用户端包括主页和个人履历库，管理端提供独立后台；完成 DOCX 预览、逐条锁定、局部重新生成、DOCX/PDF 导出，以及模型/API 图形化配置和 Token 用量查看

## 1. 核心判断

V2.0.0 的重点不是新建另一条简历生成链路，而是把已经验证的后端能力整理成普通用户可以独立完成、管理者可以配置和诊断的本地产品。

V1.5.0 不提供多模型/API Provider 扩展，也不进行 LangChain 重构。统一 Provider、多模型配置、模型能力验证及是否调整 AI 框架的评估均由 V2 首次建立，不作为 V1.5.0 前置。

V2 设置三个顶层入口：

| 页面 | 建议路由 | 核心任务 |
|---|---|---|
| 用户主页 / 生成工作台 | `/` | 输入 JD、审核选材、生成预览、锁定满意内容并迭代，最终导出 |
| 个人履历库 | `/profile` | 分层查看和维护当前职业事实库，决定保留、归档、修改或删除哪些内容 |
| 管理后台 | `/admin` | 配置模型与 API，查看 Token 用量、系统状态、索引、任务、模板和质量评测 |

“三个入口”指稳定的顶层页面。每个页面内部可以使用步骤区、标签页、抽屉和对话框，不再为每个小操作拆出独立页面。

V2 仍是本地单用户应用。“管理者”是本机应用维护者，不是 SaaS 超级管理员。V2 不管理账号、租户、订阅、订单或跨用户数据；这些仍属于 V3。

## 2. V2 要解决的问题

相对当前已验收状态和 V1.5.0 拟议前置，V2 需要解决：

1. 当前核心流程主要通过 API、脚本或 Swagger 使用，普通用户缺少完整界面；
2. 用户无法直观看清履历库中有哪些 Experience 和 Fact，也缺少安全的保留、归档、编辑和删除流程；
3. PDF 导入、经历确认、JD 分析、事实选材、生成、排版和下载之间缺少连续体验；
4. 用户无法固定已经满意的简历内容，只让 AI 重写不满意的部分；
5. DOCX 生成结果缺少与实际文件一致的页面预览，也不能从同一版本导出 PDF；
6. 长耗时 AI 操作缺少阶段进度、失败位置、重试入口和恢复提示；
7. 模型、API 地址和密钥只能通过配置文件或环境变量维护，缺少图形化切换和连通性验证；
8. 模型调用缺少统一 Token 用量记录，管理者无法判断不同任务、模型和阶段的消耗；
9. 模板容量、超页、相关性、表达质量和性能仍缺少稳定评测与回归。

## 3. 总体用户流程

### 3.1 首次使用

~~~text
打开主页
→ 了解本地数据与 AI 调用边界
→ 进入个人履历库
→ 上传已有简历 PDF，或手工新增经历
→ 查看 AI 提取结果并逐项确认、修改、归档或排除
→ 将确认后的 Experience / Fact 保存到本地事实库
→ 返回主页开始第一次简历生成
~~~

提取结果未经用户确认不得直接成为最终职业事实。批量保存必须明确展示成功、失败和未保存项，不能把部分失败显示为全部成功。

### 3.2 日常生成与迭代

~~~text
打开主页
→ 输入本次身份信息和目标 JD
→ 分析 JD 并展示岗位、技能和职责理解
→ 展示事实级选材结果，允许本次保留或排除候选
→ 选择模板、页数目标和排版密度
→ 生成第一版 ResumeDocument 与 DOCX
→ 将这份实际 DOCX 转为页面预览
→ 用户勾选需要“锁定不动”的内容条目
→ AI 只重新生成未锁定条目
→ 生成新的 DOCX 修订版并再次预览
→ 满意后从同一修订版导出 DOCX 或 PDF
~~~

用户可以重复“预览 → 锁定 → 局部重新生成”，直到满意。系统必须始终知道当前预览、锁定状态和导出文件对应的是哪个修订版。

### 3.3 管理与故障处理

~~~text
打开管理后台
→ 查看当前 LLM / Embedding Provider 与连接状态
→ 图形化新增、测试并激活模型/API 配置
→ 查看按时间、模型、任务和阶段统计的 Token 用量
→ 检查数据库、Fact、向量、索引、模板和失败任务
→ 执行允许的重试、重建或诊断
→ 返回主页复验
~~~

## 4. 页面一：用户主页 / 生成工作台

### 4.1 页面目标

主页承担日常生成主流程。用户无需理解 API、数据库、向量索引或 Prompt，即可完成“输入岗位 → 审核选材 → 生成预览 → 锁定与重写 → 导出”。

### 4.2 页面结构

建议采用顶部导航、左侧生成步骤和右侧主工作区；窄屏时步骤区折叠为顶部步骤条。

| 区域 | 主要内容 | 关键操作 |
|---|---|---|
| 顶部导航 | 主页、个人履历库、管理后台、服务状态 | 页面切换、查看状态 |
| 本次任务 | 姓名与联系方式、JD、目标岗位、模板、页数和排版密度 | 输入、分析、选择 |
| 事实选材 | Experience / Fact、分项依据、内容预算 | 本次保留、排除、恢复 |
| 生成进度 | 当前阶段、耗时、失败位置、诊断编号 | 取消、重试、继续 |
| 修订工作区 | DOCX 页面预览、内容条目、锁定状态、修订差异 | 锁定、解除、重新生成 |
| 导出区 | 当前修订版、页数、告警、DOCX/PDF 状态 | 导出、下载 |

修改 JD、事实选材、模板或排版参数后，受影响的旧修订版必须标记为“已过期”。系统不能让用户误以为旧文件使用了新参数。

### 4.3 岗位定制与事实选材

主页让用户输入本次姓名、电话、邮箱、所在地和 JD。身份信息只使用用户显式输入；不得从历史经历、模板或 AI 推测补齐。

JD 分析至少展示：

- 目标岗位；
- 必需技能、加分技能和主要职责；
- 经验偏好与关键词；
- 无法确认或材料不足的字段。

选材区按 Experience 展示：

- 被纳入或排除的 Fact；
- 时间、经历类型、语义、技能、岗位/领域等分项依据；
- 选择原因和拟议表达侧重；
- 用户本次强制保留、排除或恢复的状态；
- 预计占用的内容预算。

用户调整候选后形成新的、可序列化的 `SelectedEvidenceSet`。用户在主页对某条事实的“本次排除”不会删除个人履历库中的原始事实。

### 4.4 生成阶段与状态

首次生成至少显示以下真实阶段：

1. 校验事实与索引；
2. 分析或确认 JD；
3. 形成最终证据集合；
4. 改写简历内容；
5. 装配 ResumeDocument；
6. 生成 DOCX；
7. 将实际 DOCX 转换为预览；
8. 保存修订版与导出产物。

页面区分“尚未开始、进行中、成功、失败、已取消、结果已过期”。错误信息提供可操作建议和诊断编号，但不向普通用户展示堆栈、密钥或完整 Prompt。

V2 可以在本地单进程中增加轻量任务状态与进度通道，但不引入生产级消息队列、分布式 Worker 或跨服务器任务调度。刷新页面后的恢复语义必须在正式 PLAN 中明确。

## 5. DOCX 预览、逐条锁定与局部重新生成

### 5.1 DOCX 预览的定义

浏览器不能把 HTML 近似排版称为“DOCX 预览”。V2 的预览链路应为：

~~~text
ResumeDocument
→ 生成修订版 DOCX
→ 使用声明过的参考渲染器打开/转换这份实际 DOCX
→ 生成 PDF 或逐页图片
→ 浏览器展示页面预览
~~~

因此，用户看到的是“这份实际 DOCX 在参考渲染环境中的结果”。页面同时声明参考渲染器和转换状态，不承诺所有 Word、LibreOffice 和操作系统像素级一致。

如果预览转换失败，系统可以保留并下载已经成功生成的 DOCX，但必须明确显示“预览不可用”；不能退回 HTML 近似图后继续声称它是 DOCX 实际预览。

### 5.2 “哪行保留不动”的稳定单位

用户界面可以把它称为“行”，内部不能按视觉换行坐标识别，因为同一段文字在不同字体或软件中可能折成多行。V2 将可操作单位定义为稳定的内容条目：

- 一条工作或项目 bullet；
- 一条教育、技能或奖项条目；
- 必要时一个不可拆分的标题或 Profile 字段。

每个条目至少包含：

| 字段 | 含义 |
|---|---|
| `content_item_id` | 跨同一草稿修订稳定的条目标识 |
| `section` | 所属章节 |
| `text` | 当前显示文字 |
| `fact_refs` | 内容使用的事实来源及其 revision/hash |
| `locked` | 用户是否要求保持不变 |
| `content_hash` | 验证锁定内容未被修改 |
| `revision_id` | 当前内容所属修订版 |

预览页面将内容条目与 DOCX 中的对应位置联动高亮。用户既可以在预览旁勾选，也可以在结构化条目列表中勾选。

### 5.3 锁定与重新生成规则

- 用户勾选的条目进入 `locked` 状态；
- AI 可以把锁定条目作为上下文以避免重复，但不得返回对它们的修改；
- 后端只接受未锁定 `content_item_id` 的新内容；
- 新修订生成后，锁定条目的文本和 `content_hash` 必须与上一修订完全一致；
- 未锁定条目仍只能使用当前 `SelectedEvidenceSet` 中允许的 `fact_refs`；
- 未知条目、未知 Fact、无来源内容或对锁定条目的修改必须拒绝并告警；
- 如果材料不足以重写某条内容，应保留明确的失败状态，不用空话填补；
- 用户可以全部锁定、全部解除或按章节批量操作；全部锁定时不应产生无意义的 LLM 调用；
- 每次局部重生成产生新的 `revision_id`，不能覆盖上一版；
- 页面展示新旧修订差异，并允许返回上一版。

如果用户修改或删除了锁定条目对应的 Fact，或者更换了 JD、目标岗位，相关锁定状态必须标记为“需要重新确认”。系统不得让已失去事实依据的旧文字借由锁定继续无提示导出。

### 5.4 版式变化与锁定内容

锁定表示文字内容不变，不表示它永远位于相同物理页码或坐标。其他条目变化后，锁定条目的分页位置仍可能改变。

如果锁定内容导致超页：

1. 先尝试用户允许的排版密度调整；
2. 展示超页和容量告警；
3. 建议用户解除部分低优先级条目或回到事实选材；
4. 不得静默删除、截断或改写锁定内容。

### 5.5 DOCX 与 PDF 导出

- DOCX 与 PDF 必须来自用户当前确认的同一个 `revision_id`；
- PDF 优先由该修订版的实际 DOCX 经参考渲染器转换，而不是重新走一套独立排版；
- 导出前显示修订号、生成时间、页数、模板和未处理告警；
- 如果 DOCX 成功但 PDF 转换失败，分别显示两个产物的状态；
- 下载文件名包含目标岗位、修订号和生成时间，并过滤非法路径字符；
- 导出动作不得再次调用 LLM 或改变已经确认的内容。

## 6. 页面二：个人履历库

### 6.1 页面目标

个人履历库让用户看清“系统目前知道我哪些职业事实”，并能决定哪些内容继续保留、哪些暂时不用、哪些需要修改。它展示长期职业资产，不展示某一份生成简历的临时措辞。

### 6.2 分层展示

建议层级：

~~~text
履历概览
├── 工作经历
│   └── Experience
│       ├── 基本归属：公司、岗位、时间、地点
│       └── Facts：职责、行动、方法、结果、指标、产物
├── 项目经历
├── 教育经历
├── 技能
└── 奖项 / 其他
~~~

页面顶部显示 Experience 总数、Fact 总数、各类型数量、最近更新时间、待确认项和索引异常数。支持按类型、时间、状态和关键词过滤。

每条 Experience 可以展开查看：

- 原始归属信息和来源；
- 已确认 Fact 与原始来源文本；
- 当前状态：启用、已归档、待确认或索引异常；
- 最近修改时间；
- 被最近生成任务选中过的次数仅作辅助信息，不能替代用户判断。

### 6.3 保留、归档、修改和删除

| 操作 | 语义 |
|---|---|
| 保留 / 启用 | 默认可以参加后续预筛和选材 |
| 归档 | 保留在事实库中，但默认不参加后续生成；可随时恢复 |
| 修改 | 编辑事实并重新确认，触发相关向量失效与重建 |
| 删除 | 永久删除事实及派生索引，需要二次确认 |

用户想表达“这段经历暂时不要使用”时，页面优先提供归档，不诱导永久删除。删除 Experience 前展示受影响 Fact 数量和生成记录引用；历史修订只保留当时的来源快照或显示“原事实已删除”，不得悄悄改写历史文件。

页面不能直接编辑向量、相关性分数或模型生成措辞。用户只维护事实，向量和评分由后端根据事实变化重建。

### 6.4 导入与确认

- 允许上传 PDF 或手工新增 Experience / Fact；
- PDF 上传后显示解析、分段和 AI 提取的真实状态；
- 新提取内容先进入“待确认”，保存后才成为事实；
- 支持逐项和批量确认，但批量保存必须是可核对的事务；
- 出现重复经历或疑似重复 Fact 时展示对比，不自动覆盖；
- PDF 无可提取文本时说明可能为扫描件，并提供手工录入；OCR 是否加入 V2 待确认。

V2 是否在个人页面持久化姓名、电话、邮箱和所在地，需在正式 PLAN 前单独确认。即使持久化，也只能是用户显式保存的本地 Profile，不能从 Experience、模板或 AI 推测。

## 7. 页面三：管理后台

### 7.1 页面目标

管理后台服务于本机模型/API 配置、用量查看、应用维护、问题定位和质量回归。它不承担普通用户生成简历的主流程，也不复制个人履历库的事实编辑器。

### 7.2 页面结构

管理后台内部使用标签页或分区：

| 分区 | 展示内容 | 允许操作 |
|---|---|---|
| 总览 | 应用版本、运行时间、数据库位置、输出目录、依赖健康状态 | 刷新、复制脱敏诊断摘要 |
| 模型与 API | LLM / Embedding Provider、Base URL、模型、能力、连通性 | 新增、测试、激活、停用配置 |
| Token 用量 | 输入、缓存输入、输出、推理和总 Token；按时间、模型、任务、阶段聚合 | 筛选、查看趋势、导出脱敏汇总 |
| 数据与索引 | Experience / Fact 数量、索引状态、fingerprint、失败任务 | 重试、从事实源重建索引 |
| 生成任务 | 阶段、耗时、修订数、结果、错误码、输出状态 | 查看、重试允许阶段、清理过期记录 |
| 模板与版式 | 内置模板、TemplateSpec、参考渲染结果、容量告警 | 设默认模板、执行模板诊断 |
| 质量评测 | 固定虚构/脱敏测试集、选材指标、事实越界、版式和性能结果 | 运行评测、对比当前基线 |

## 8. 模型与 API 图形化配置

### 8.1 支持范围

V2 将图形化模型配置正式纳入管理后台。首版建议支持：

- 项目内置并经过适配的供应商；
- OpenAI-compatible 的 LLM / Embedding Endpoint；
- 本机模型服务，例如用户明确配置的 loopback Endpoint；
- LLM 与 Embedding 分开选择 Provider 和模型，不要求两者来自同一供应商。

“可替换不同 API”不等于接受任意私有协议。非兼容协议需要显式 Adapter；通过连接测试只证明网络和基础能力可用，不等于所有结构化输出、Token 统计和 Embedding 维度契约都已兼容。

### 8.2 配置字段

每份 Provider 配置至少包含：

- 配置名称和类型；
- Base URL；
- API Key 或其他受支持凭据；
- LLM model；
- Embedding model；
- 超时、有限重试和必要的能力开关；
- 结构化输出能力；
- Token usage 返回能力；
- Embedding 维度、模型 fingerprint 和最近验证时间。

页面保存前执行字段校验，支持“测试连接”和“测试结构化输出/Embedding”两层检测。检测失败不得激活配置。

### 8.3 切换语义

- 每个生成任务在开始时冻结配置快照，运行中切换模型不改变该任务；
- LLM 切换只影响后续 AI 请求，并在修订记录中保存供应商与模型标识；
- Embedding 模型或维度改变会使现有向量全部过期，必须以 SQLite Fact 全量重建；
- 重建完成前不得混用新旧向量，也不得用旧向量继续生成；
- 配置激活和索引重建是两个可见阶段，失败时保留上一个可用配置或明确进入不可用状态；
- 回滚只能回滚配置元数据，不能假定旧密钥仍然有效。

### 8.4 密钥与 Endpoint 安全

- API Key 从浏览器只发送给本地后端，不写入 `localStorage`、日志、诊断摘要或 Token 记录；
- 保存后不回显完整密钥，只显示是否已配置和末尾少量字符；
- 长期凭据优先存入操作系统凭据库；若目标系统无法提供安全存储，正式 PLAN 必须选择会话级使用或明确拒绝长期保存，不能退回明文 SQLite；
- Base URL 不允许把用户名、密码或 Token 写在 URL 中；
- 远程 Endpoint 默认要求 HTTPS；本机模型可明确允许 loopback HTTP；
- 后端负责请求供应商，前端不直接持有 Key 或绕过统一 Provider Adapter；
- 配置创建、测试、激活和停用写入不含密钥的本地审计记录。

## 9. Token 用量统计

### 9.1 记录原则

Provider Adapter 应尽量把供应商响应中的 usage 归一为本地 `UsageRecord`：

| 字段 | 含义 |
|---|---|
| `operation_id` / `task_id` | 对应任务与具体调用 |
| `stage` | JD 分析、经历提取、改写、Embedding 等阶段 |
| `provider` / `model` | 实际使用的供应商和模型 |
| `input_tokens` | 输入 Token；供应商未返回时为 unknown |
| `cached_input_tokens` | 缓存输入 Token；供应商支持时记录 |
| `output_tokens` | 输出 Token |
| `reasoning_tokens` | 推理 Token；供应商支持时记录 |
| `total_tokens` | 供应商返回或由已知分项相加 |
| `usage_source` | `reported`、`estimated` 或 `unknown` |
| `status` / `timestamp` | 请求结果与时间 |

UsageRecord 只保存用量、模型和任务元数据，不保存 Prompt、JD、履历正文、响应正文或 API Key。

### 9.2 页面展示

后台至少提供：

- 今日、近 7 天、近 30 天和自定义范围总量；
- 按 Provider、模型、业务阶段和生成任务分组；
- 输入、输出、缓存输入、推理和总 Token 的趋势；
- 每份简历及每次局部重新生成的用量；
- `reported`、`estimated`、`unknown` 的占比；
- 失败请求是否返回 usage，以及无法确定的消耗。

供应商没有返回 Token 用量时，系统不得显示伪造的精确值。若使用本地 tokenizer 估算，必须标记为 `estimated`；模型分词规则未知时标记为 `unknown`。

### 9.3 费用估算

Token 数量与实际账单不是同一概念。V2 可以在管理员配置了对应模型价格和生效日期后显示“估算费用”，但必须：

- 标记为估算值，不称为供应商账单；
- 区分输入、缓存输入、输出和推理的不同计价；
- 保留使用的价格版本和币种；
- 价格缺失或过期时只显示 Token，不猜测费用；
- 提醒供应商侧重试、批处理、赠送额度或计费规则可能造成差异。

## 10. 管理操作约束与访问边界

- 数据库和输出目录只展示规范化路径，不允许页面提交任意文件系统路径；
- 完整 Prompt、完整履历和 JD 不进入普通诊断摘要；
- 索引重建必须以 SQLite Fact 为事实源，并展示范围、进度、成功数、失败数和 fingerprint；
- 删除输出、清理任务记录或重建索引需要二次确认；事实库删除不放在后台的一键清理中；
- 失败重试必须具备幂等或去重边界，避免重复 AI 调用、重复计费和重复文件；
- 后台不得提供任意 SQL、任意命令或任意本地路径执行入口。

V2 没有账号和角色系统。管理后台默认只服务本机 loopback，并在非本机绑定或代理暴露时默认关闭管理写操作。若产品要求公网、局域网或多人共享后台，必须补充认证、授权、CSRF、审计和多用户数据隔离，并重新评估为 V3 范围。

## 11. 数据与状态边界

| 数据 | V2 规则 |
|---|---|
| Experience / Fact | 来自后端 SQLite；个人页面不建立第二事实源 |
| SelectedEvidenceSet | 本次生成的可追溯决策；可调整但不覆盖原事实 |
| ResumeDraft / Revision | 记录条目、锁定、来源、模型配置快照和产物版本 |
| 姓名和联系方式 | 本次请求显式输入；是否允许显式持久化本地 Profile 待确认 |
| JD | 本次任务输入；保存历史不能让它变成职业事实 |
| 向量和评分 | 派生数据；用户不可直接编辑，可从 Fact 重建 |
| Provider 配置元数据 | 本地后端保存；密钥单独进入安全凭据存储 |
| UsageRecord | 只保存 Token 和调用元数据，不保存用户正文 |
| 模板 | 系统内置 DOCX + TemplateSpec；不提供用户事实 |
| 页面草稿 | 只保存完成交互所需的最小状态；敏感数据不写入 `localStorage` |
| 生成文件 | 保存于 runtime output；通过稳定 artifact / revision ID 访问 |

前端缓存不能改变事实所有权。任何事实修改、生成修订、Provider 切换或管理操作，都以后端确认响应为准。

## 12. 后端能力复用与缺口

V2 优先复用现有核心服务，不允许前端重新实现 V1/V1.5 的业务规则。

| 能力 | 当前/V1.5 可复用 | V2 预计补充 |
|---|---|---|
| PDF 解析 | `/api/resume/upload` | 文件限制、任务进度、失败恢复和隐私说明 |
| 经历提取 | `/api/experience/extract` | 待确认状态、可核对的批量导入事务 |
| 经历管理 | Experience CRUD | Fact 分层读取/编辑、归档、冲突和索引状态 |
| JD 分析 | `/api/jd/analyze` | 面向页面的解释字段与输入错误契约 |
| 选材 | V1.5 `SelectedEvidenceSet` | 用户本次覆盖、内容预算和重新计算接口 |
| 首次 DOCX 生成 | `/api/resume/generate-docx` 核心链 | 稳定 Draft/Revision 与阶段任务契约 |
| 局部重生成 | V1.5 `fact_refs` 约束 | 锁定条目、未锁定目标、版本冲突和 hash 校验 |
| 预览与导出 | Renderer 与下载接口 | 实际 DOCX 转预览、同 Revision 的 DOCX/PDF artifacts |
| Provider | 当前豆包调用与配置 | 首次建立统一 Provider 边界，并完成配置 CRUD、能力测试、激活、快照和安全密钥存储 |
| Token | 当前链路无统一 UsageRecord | 统一 UsageRecord、聚合查询与可信度标记 |
| 运维 | 当前部分 service 层能力 | 脱敏健康、索引、任务、模板和评测接口 |

正式 PLAN 需要先冻结页面依赖的 OpenAPI 和修订契约。现有 deprecated Markdown 生成接口和 internal 的直接 `ResumeDocument → DOCX` 接口不得成为前端主链。

## 13. 前端技术方案草案

建议采用 React + TypeScript + Vite 构建单页应用，由 FastAPI 在本地正式运行时提供静态资源与同源 API；开发模式使用前端开发服务器代理后端。具体依赖版本在正式 PLAN 中锁定。

架构约束：

1. 只有 `/`、`/profile` 与 `/admin` 三个顶层路由；
2. API Client 从冻结的 OpenAPI 契约生成或经过强类型封装；
3. 服务端状态、表单草稿、生成修订和任务进度分层管理；
4. 用户输入、模型输出和错误文本统一按不可信文本渲染，不使用 `innerHTML`；
5. 不在浏览器长期保存 API Key、完整履历或完整 JD；
6. DOCX 页面图与结构化内容条目通过 `revision_id + content_item_id` 联动；
7. 页面组件只处理展示与交互，事实校验、选材、Builder、锁定校验和渲染仍由后端负责；
8. 桌面浏览器作为首要验收环境，窄屏保证可读和基本操作；
9. 无障碍基础要求包括键盘可达、表单标签、错误关联、可见焦点和不只靠颜色表达状态。

## 14. 质量、性能与排版收口

### 14.1 选材与表达质量

V2 建立小型、稳定、可公开或完全虚构的评测集，至少验证：

- 硬规则排除是否正确；
- 目标事实是否进入候选集合；
- 明显无关事实是否被压低；
- 用户强制保留/排除是否生效；
- bullet 是否只使用已选 `fact_refs`；
- 锁定条目在局部重生成后是否逐字不变；
- 未锁定条目是否产生有效差异且没有复制锁定条目；
- 相同履历面对不同 JD 是否产生可解释差异；
- 材料不足时是否显式提示，而不是虚构或填充空话。

权重、阈值和 Top-K 只能依据评测集与人工复核调整。正式 PLAN 先记录基线，再给出目标值。

### 14.2 性能与响应体验

分别记录 PDF 解析、经历提取、JD 分析、选材、首次改写、局部重写、构建、DOCX 渲染、预览转换和 PDF 导出的耗时。页面交互反馈与后台任务耗时分开验收。

正式 PLAN 根据固定环境和测试集冻结 P50/P95 目标，并至少覆盖首屏、履历库、后台总览、典型首次生成、局部重生成、导出及连续运行后的资源清理。

### 14.3 排版质量

- 为每个内置模板建立标准 fixture 和参考 DOCX/PDF 渲染结果；
- 验证短、典型、长履历，中英文混排、缺失字段和特殊字符；
- 一页目标使用明确的参考渲染环境，并记录跨软件差异；
- Renderer 不删除业务条目，LayoutOptimizer 不越权改写内容；
- 页数压缩先调整安全版式参数，再建议用户减少低优先级事实；
- 无法达到目标页数时明确告警，不通过不可见截断“达标”。

## 16. V2 边界

本版本拟做：

- 用户主页、个人履历库和管理后台三个顶层页面；
- 履历事实的分层查看、确认、归档、修改和删除；
- Fact 级选材解释和用户本次覆盖；
- 基于实际 DOCX 的页面预览；
- 内容条目锁定、未锁定条目局部重生成、修订历史与差异；
- 从同一修订版导出 DOCX 和 PDF；
- 模型/API 图形化配置、能力测试和安全切换；
- Token 用量记录、聚合、可信度标记和可选费用估算；
- 长任务进度、失败恢复、局部重试和过期状态；
- 相关性、生成质量、事实边界、性能和版式评测。

本版本不做：

- 登录、注册、角色、租户、多人协作或跨用户数据管理；
- PostgreSQL、对象存储、分布式 Worker、生产消息队列和公网部署；
- 订阅、额度、计费和商业运营后台；
- 浏览器本地 Vault、跨设备同步、PWA 和离线资料库；
- 任意私有模型协议无需 Adapter 即可使用；
- 云端多用户 BYOK、平台密钥下发或账号级密钥托管；
- 任意 Word 模板自动解析；后台只管理系统支持的模板；
- 在所有办公软件和操作系统上承诺像素级一致；
- 为匹配 JD 虚构事实，或让前端绕过 `SelectedEvidenceSet` 和 Builder；
- 把 Token 估算冒充供应商真实账单。

V2 已把“本地管理员图形化配置受支持模型/API”从原 V3 设想前移；V3 仍负责把这项能力生产化为账号级、权限隔离、配额和云端 Provider Gateway。

## 17. 验收草案

### 17.1 页面与履历库

- [ ] 应用只有主页、个人履历库和管理后台三个顶层页面，核心任务不依赖 Swagger 或命令行；
- [ ] 新用户可以从空事实库完成 PDF 导入或手工录入、确认和保存；
- [ ] 个人页面可以分层查看所有 Experience / Fact，并明确其启用、归档、待确认和索引状态；
- [ ] 保留、归档、修改和删除具有不同语义，永久删除必须二次确认；
- [ ] 修改 Fact 后相关向量和旧生成结果准确失效，不继续使用旧派生数据。

### 17.2 生成、锁定与导出

- [ ] 用户可以输入 JD、审核选材并生成第一版 DOCX；
- [ ] 页面预览来自该实际 DOCX 的参考渲染结果，不是未声明的 HTML 近似；
- [ ] 每个可操作内容条目都有稳定 `content_item_id` 和可回查 `fact_refs`；
- [ ] 用户可以锁定任意条目，局部重生成后其文字和 hash 逐字不变；
- [ ] AI 只返回未锁定条目的替换内容，未知、越界或修改锁定项的输出被拒绝；
- [ ] 每次迭代产生新修订版，可查看差异并回到上一版；
- [ ] DOCX 和 PDF 来自用户确认的同一 `revision_id`，导出不会再次调用 AI；
- [ ] Fact 或 JD 变化导致锁定依据失效时，页面要求重新确认；
- [ ] 一页目标不通过静默删除或截断内容实现。

### 17.3 模型/API 与 Token

- [ ] 后台可以图形化新增、测试、激活和停用受支持的 LLM / Embedding 配置；
- [ ] 运行中任务使用冻结配置，切换只影响后续任务；
- [ ] Embedding 模型变化触发全量失效与重建，新旧向量不混用；
- [ ] API Key 不回显、不进入日志或 SQLite 明文字段，非 loopback 管理写操作默认不可用；
- [ ] Provider 返回 usage 时，后台可按模型、任务、阶段和时间查看 Token；
- [ ] 未返回 usage 时显示 `estimated` 或 `unknown`，不伪造精确值；
- [ ] Token 记录不包含 Prompt、JD、履历或响应正文；
- [ ] 费用估算缺少价格依据时不可用，且始终与真实账单明确区分。

### 17.4 质量、性能与架构

- [ ] 关键页面完成浏览器 E2E、键盘操作和基础无障碍检查；
- [ ] 固定评测集覆盖事实选材、首次生成、锁定重写和越界失败；
- [ ] 每个内置模板通过短、典型、长和特殊字符的 DOCX/PDF 参考渲染测试；
- [ ] 固定环境下的首屏、履历库、首次生成、局部重生成和导出达到正式 PLAN 阈值；
- [ ] V2 收口前完成全局架构一致性审查，确认没有前端并行事实源、旧生成主链、绕过 Provider 的调用或越权内容决策。

## 18. 主要风险

| 风险 | 草案中的控制方式 |
|---|---|
| 将视觉换行当成稳定内容 | 使用 `content_item_id` 表示 bullet/条目，预览位置只做映射 |
| AI 在局部重写时修改已锁定内容 | 后端只接收未锁定 ID，并使用 hash 验证锁定文本 |
| DOCX 预览与最终文件不一致 | 先生成实际 DOCX，再由声明的参考渲染器转换预览与 PDF |
| 锁定旧文字掩盖事实变更 | Fact 或 JD 变化时使相关锁定状态待重新确认 |
| 图形化 API 配置泄露密钥 | 后端代理、系统凭据库、写后不回显、日志脱敏 |
| Embedding 切换污染检索 | fingerprint 全量失效、重建完成前禁止混用 |
| Token 统计与供应商账单不一致 | 区分 `reported`、`estimated`、`unknown`，费用单独标为估算 |
| 管理后台扩大攻击面 | loopback 默认、无任意 SQL/命令/路径、非本机禁写 |
| 三页面逐渐膨胀成复杂门户 | 只保留三个顶层路由，内部按任务与职责分区 |
| V1.5.0 未完成导致前端绑定旧契约 | 未具备 Fact、SelectedEvidenceSet 和失效语义时不进入相关 UI 实现；Provider 由 V2 自身建立 |

## 19. 正式 PLAN 前待确认

1. 个人履历库是否要持久化姓名、电话、邮箱和所在地，还是这些信息继续只在每次生成时填写；
2. “归档”是否满足“暂时不使用”的需求，永久删除后是否需要短期回收站；
3. V2 首批明确支持哪些供应商和本地模型服务，OpenAI-compatible Endpoint 的兼容范围如何定义；
4. Windows、macOS、Linux 分别采用什么凭据存储；无法安全持久化密钥的平台如何降级；
5. 参考 DOCX 渲染器选用 Microsoft Word、LibreOffice 还是受控转换服务，以及目标运行环境是否具备它；
6. 页面中的“行”是否统一按 bullet/内容条目理解；标题、教育信息和技能条目是否也允许锁定；
7. 局部重生成是否允许用户追加一次性文字要求；若允许，该要求不能成为新事实来源；
8. 是否需要展示费用估算；如需要，由谁维护模型价格、币种和生效日期；
