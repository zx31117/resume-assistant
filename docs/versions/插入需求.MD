# 插入需求：跨版本 Agent 治理状态机与规则执行器

> 文档角色：项目治理能力的需求池草稿
> 状态：候选需求；不是版本 PLAN，不构成开发授权，也不表示当前已经实现
> 记录日期：2026-09-26
> 最近修订：2026-09-26（按非串行任务图、双向拦截、规则分流、自包含返回和跨版本复用重构）
> 适用场景：项目各版本、任务与角色之间当前由人负责信息中转的协作方式

## 1. 背景与问题

项目已有较多角色、权限、反思、证据、验收和发布规则，但目前主要依赖 Agent 主动阅读全文、理解、
记忆并执行。过去已经出现 Agent 忘记、忽略或错误解释规则的情况；规则数量继续增长还会占用不必要
的上下文，降低 Agent 对当前任务的注意力和执行性能。Agent 也可能在完成当前工作后自行推断下一步，
导致目标偏离、强制 Gate 被跳过，或把本可由规则处理的问题再次升级给人。

当前尚未封装自动多 Agent 协作。不同 Agent 之间的信息中转、任务创建和启动仍由人完成。因此，本
需求不建设自动 Agent 编排器，也不要求程序自动创建、唤醒或切换 Agent。状态机的当前职责是：把
跨版本稳定规则与当前版本参数编译为最小大节点合同和依赖图，在 Agent 接收、执行、完成和交接时实施约束，
确保规则遗漏不能获得正式项目效力，同时自动确定 Gate、修正路径、责任角色和下一步动作。

## 2. 目标

建设一个项目级、跨版本复用的“规则编译器 + 状态机 + Gate 引擎 + 修正方案库 + 交接包生成器”，
把可机械化的流程复杂度交给程序，而不是要求每个 Agent 全文阅读规则、临场解释路由或自行设计
返工步骤。

本需求按以下优先级解决三个核心问题：

1. **规则执行正确性**：不依赖 Agent 记住规则；任何强制规则、Gate 或身份合同被遗漏、忽略或绕过
   时，工作不得进入正式候选、验收、集成或发布状态；
2. **最小规则上下文**：普通 Agent 只接收当前大节点及其活动依赖所需的 Role Card，不默认加载完整
   治理规则；系统必须证明适用规则没有遗漏，同时排除无关规则；
3. **减少人工依赖**：合法转换、下一责任角色、普通失败回路和修正步骤由系统确定；人只承担信息
   搬运、真实触发、主观产品判断、风险接受、新授权和不可逆操作。

系统必须实现以下结果：

1. 当前 Agent 只有通过交接检查才能生成正式交接包；
2. 下一 Agent 只有成功接收有效交接包才能开始正式工作；
3. 阻断依赖未满足时保持在当前大节点，并返回明确、可执行的修正步骤；
4. 需要人主动触发的依赖在收到真实触发事件前不能满足；
5. 只有产品判断、风险接受、新外部授权或不可逆真实数据操作才请求人作决定；
6. 规则缺失、冲突或不可执行时返回规则审查，而不是让执行 Agent 自行猜测；
7. 人继续负责 Agent 间的信息搬运，但不再负责重新解释全部规则和手工判断合法转换；
8. 新版本和新任务通过复用工作流模板并提供参数/增量 Gate 接入，不为每个版本复制规则或修改引擎；
9. 规则更新具有明确适用范围，在途工作流不会被新规则静默重新解释。

## 3. 非目标

- 状态机本身不自动创建、启动、暂停、唤醒或关闭 Agent；规则可以要求当前执行 Agent 获取一份全新
  上下文子 Agent 审查回执，实际创建动作仍由执行 Agent 按状态机返回内容完成；
- 不自动完成跨 Agent 的消息投递；
- 不替代人选择实际使用哪个 Agent、会话或执行环境；
- 不把主观产品质量判断伪装成机械 Gate；
- 不属于 ResumeAssistant 面向用户的产品功能；
- 不允许 Rules Agent、Documentation Agent 借此直接修改产品源码；
- 不把自由文本提示词作为唯一状态、事件或权限来源；
- 不承诺阻止 Agent 在状态机外输出文字或产生无效工作；它保证未经有效 Gate 和状态转换的工作不能
  获得正式项目效力；
- 不把某个版本号、某份 PLAN 的 Task ID 或当前发布阶段硬编码到状态机引擎。

### 3.1 首版部署与威胁模型

首版只支持同一台机器上的受信本地协作：各正式 Agent 会话共享同一状态机实例、事件账本和
`evidence_log_root`，人仍负责在这些会话之间搬运交接包。跨机器状态同步、远端身份服务和分布式证据
存储不属于首版范围；以后需要时另行增加规则、迁移和验收合同。

首版主要防止 Agent 遗忘、执行漂移、角色或版本误用、过期/重复令牌、错误分支、无意修改和证据身份
错配，不以防御主动窃取本机状态、签名材料或系统权限的恶意 Agent 为目标。状态文件、令牌签名和 hash
链仍必须能够发现普通篡改、重放和误用，但文档不得把它表述为可抵御拥有本机完全权限的攻击者。

## 4. 现实运行方式

状态机采用两层任务图，而不是把所有动作摊平成一条节点链：

- **大节点（major node）**：表示版本生命周期中的正式阶段和跨角色交接边界；
- **依赖项（dependency）**：表示大节点开始或完成所需的工作产物、机器检查、人工事件、外部结果或
  受保护动作。

依赖项不是默认串行的“小节点”。只有显式声明 `depends_on` 才形成先后关系；没有依赖边且没有写入
冲突的依赖项可以并行。某个依赖项满足也不自动表示大节点完成，状态机必须计算该大节点的完成表达式。

~~~text
人把包含上一节点交接令牌的大节点任务包交给当前 Agent
→ 系统加载工作流模板、版本覆盖层和冻结 Rule Bundle
→ accept-handoff 在线校验并消费交接令牌，核对目标大节点、角色、身份和开始依赖
→ Agent 获取节点执行回执、Role Card、依赖图和可执行依赖集合
→ Agent、受信工具或人分别提交结构化依赖结果与证据
→ 状态机只重算受影响依赖和大节点完成表达式
→ 依赖未齐：保持当前大节点，返回可并行项、缺失项和修正动作
→ 完成表达式成立：原子完成大节点，为每个合法后继分别签发交接令牌
→ prepare-handoff 将目标专用令牌、Role Card 和证据摘要封装为交接包
→ 人完成信息搬运；下一 Agent 再次运行 accept-handoff
~~~

### 4.1 大节点与依赖项状态

大节点使用 `NOT_READY`、`READY`、`IN_PROGRESS`、`BLOCKED`、`WAITING_HUMAN`、`COMPLETED`、
`INVALIDATED`、`NOT_APPLICABLE`。其中 `BLOCKED` 和 `WAITING_HUMAN` 是对其未满足阻断依赖的汇总，
不是要求所有内部工作停止；无冲突的其他依赖仍可继续。

依赖项使用：

| 状态 | 含义 |
|---|---|
| `NOT_EVALUATED` | 尚未计算适用性或前置关系 |
| `READY` | 可以执行或判定 |
| `IN_PROGRESS` | 指定责任方正在处理 |
| `SATISFIED` | 产出、证据和 Gate 已满足 |
| `FAILED` | 已判定不满足，附有责任角色和修正方案 |
| `WAITING_HUMAN` | 等待真实人工触发或判断事件 |
| `NOT_APPLICABLE` | 经规则判定不适用；不能由 Agent 自报跳过 |
| `INVALIDATED` | 因输入、规则或证据身份变化而失效 |

工作流必须记录 `ready_major_node_set`、`active_major_node_set`、各大节点的
`ready_dependency_set`、`failed_dependency_set` 和 `waiting_human_dependency_set`，不能伪造单一
`current_node`。一次事件只重算受影响子图，无关并行依赖保持原状态。

### 4.2 依赖图、分支与返工

依赖项按职责分为 `WORK_PRODUCT`、`AUTOMATED_CHECK`、`FRESH_CONTEXT_REVIEW`、`HUMAN_TRIGGER`、
`HUMAN_REVIEW`、`EXTERNAL_RESULT`、`PROTECTED_ACTION`、`ROUTER` 和 `JOIN_EXPRESSION`。一个依赖项必须
声明责任方、输入、产出或事件、Gate、证据、新鲜度及失效范围。

依赖关系至少支持：

- `ALL_OF`、`ANY_OF`、`N_OF_M`：计算开始条件或完成表达式；
- `CONDITION`：依据结构化事实启用依赖分支，不从自由文本猜测；
- `DEPENDS_ON`：唯一表示明确先后关系；没有该边就不能把列表顺序解释为执行顺序；
- `REWORK_EDGE`：失败后返回精确依赖项或上游大节点，并声明哪些结果失效；
- `INVALIDATION_EDGE`：输入身份变化后使依赖旧结果的依赖项、回执和下游大节点失效。

并行依赖写入同一权威对象、循环等待或要求对方未冻结输出时，模板编译必须失败。修正缺项通常重新
评估原依赖项，不为每种“补一下再提交”创建 `*_REPAIR` 伪节点。

### 4.3 双向拦截

1. **生产方完成拦截**：当前大节点的完成表达式未成立时，状态机返回未满足依赖、失败原因和修正步骤；
   生产方不得生成可供后继阶段使用的正式完成回执。
2. **消费方接收拦截**：下一 Agent 必须重新验证目标大节点为 `READY`、全部开始依赖当前仍满足、证据
   未过期、输入身份未变化、角色匹配且交接包有效。即使文件或 commit 已被人工传来，或相同依赖曾经
   PASS，当前判定不成立也必须拒绝执行。

两道拦截使用同一任务图事实，但回执和判定时点独立，不能复用旧检查绕过。

该规则适用于每一次大节点转换，包括延后进入 `PUBLICATION`：不可变历史证据无需无意义地重复生成，
但状态机必须在接收时重新验证其身份、适用性、新鲜度以及所有可变外部前置条件。任一依赖已经失效，
目标大节点恢复为 `NOT_READY` 或 `BLOCKED`，并返回必须重做的精确依赖。

### 4.4 跨版本大节点模板

一个标准版本只保留以下五个大节点：

| 大节点 | 输入 | 完成结果 |
|---|---|---|
| `VERSION.PLAN_FORMATION` | 候选草稿、当前事实和适用治理模板 | 经人批准并冻结身份的正式 PLAN |
| `VERSION.IMPLEMENTATION_DELIVERY` | 已批准 PLAN，以及存在时的适用设计基线 | clean 开发候选 H、完整 RESULT 交付和开发侧证据 |
| `VERSION.ACCEPTANCE` | 冻结候选 H 和 `DOC_ALIGNED` 交付 | 独立验收与人工产品验收均通过的候选 |
| `VERSION.CLOSEOUT` | 已验收候选 | 本地集成及 RESULT、CURRENT_STATE、索引等文档收口 |
| `VERSION.PUBLICATION` | 已收口发布候选 R | 远端 main/tag/artifact 核验通过；不发布时可合法 `NOT_APPLICABLE` |

`GOVERNANCE_REVIEW` 是跨切面的异常子流程，不是正常版本大节点。只有规则缺失、冲突、循环或不可执行
时激活；普通实现失败、证据缺失或 PLAN 变化仍回到对应版本大节点。

版本特有 Task、验收项、设计流程和产物名称只实例化为大节点内部依赖或子工作流；引擎不预先知道
T01、V2.3.0 或某个包名。复杂设计或迁移工作可以展开为嵌套子工作流，但其结果仍作为所属大节点的
一个依赖输入，不增加版本生命周期层级。

### 4.5 各大节点的标准依赖

| 大节点 | 标准完成依赖；列表本身不表示顺序 |
|---|---|
| `PLAN_FORMATION` | 草稿完整、当前事实已绑定、路径反思完成、路径反思经人审核、设计适用性已判定、命中设计变更时设计输入就绪、适用专项评估完成、PLAN 合同完整、人批准 PLAN、PLAN 身份冻结 |
| `IMPLEMENTATION_DELIVERY` | 开发接收有效、Pre-mortem 完成、PLAN Task 依赖图完成、适用真实纵切与 Architecture Check 完成、RESULT 合同完整、开发 Gate 通过、开发执行—文档全新上下文自查通过、Falsification Check 完成、候选 H 冻结 |
| `ACCEPTANCE` | 候选和 PLAN 身份有效、RESULT 语义审查为 `DOC_ALIGNED`、PLAN 要求的独立验收分支全部通过、适用源码验收的执行—文档全新上下文自查通过、人工产品验收通过 |
| `CLOSEOUT` | 已验收 H 完成本地集成、RESULT 最终化、CURRENT_STATE/版本索引/必要 README 更新、文档一致性检查通过、发布候选 R 冻结 |
| `PUBLICATION` | 人确认发布、远端基线和 fast-forward 检查通过、tag 不存在、push/tag 完成、发布后身份核验通过 |

PLAN Task、专项评估、文档更新和独立验收均可以形成并行依赖集合。只有其所属大节点的完成表达式要求
`ALL_OF` 时才必须全部汇合；条件分支可以得到规则签发的 `NOT_APPLICABLE`。

人工产品验收是标准版本进入 `CLOSEOUT` 的固定依赖，不因版本偏向后端、基础设施、文档或治理而自动
取消。验收内容可以按版本范围调整，但必须存在真实人工验收事件，Agent 或子 Agent 不能代签。

### 4.6 `PLAN_FORMATION` 的依赖图

~~~text
PLAN_REQUESTED
       ↓
DRAFT_COMPLETENESS
       ├─ CURRENT_STATE_BASELINE ───────────────────────────┐
       ├─ PATH_REFLECTION → PATH_REFLECTION_HUMAN_REVIEW ──┤
       ├─ DESIGN_SCOPE_CHECK ─┬─ NOT_APPLICABLE ────────────┤
       │                      └─ DESIGN_INPUT（条件子图）────┤
       └─ IMPACT_ASSESSMENT::<type> × 0..N（可并行）────────┤
                                                            ↓ ALL_OF
                                                     PLAN_CANDIDATE
                                                            ↓
                                                     PLAN_CONTRACT
                                                            ↓
                                                     PLAN_HUMAN_REVIEW
                                                            ↓
                                                     PLAN_IDENTITY_FREEZE
                                                            ↓
                                             PLAN_FORMATION.COMPLETED
~~~

这里仅有两条固定的局部串行关系：人工路径审核依赖路径反思，PLAN 的合同检查、人工批准和身份冻结依赖
前一步产物。`CURRENT_STATE_BASELINE`、`PATH_REFLECTION`、设计适用性检查和各专项评估之间默认可以并行。
设计不是版本固定依赖：只有规则根据范围判定涉及界面、交互或既有设计基线变化时才激活设计子图；其余
版本以可审计的 `NOT_APPLICABLE` 参与汇合，不要求创建设计稿、人工预览或 Design Snapshot。

用户明确要求“写 PLAN”“把草稿转成 PLAN”或同等含义时，即产生 `PLAN_REQUESTED` 启动事件。状态机
立即创建或恢复 `PLAN_FORMATION`、计算依赖图并返回当前可执行依赖。Documentation Agent 对返回的
`RULE_RESOLVABLE` 依赖必须直接执行、提交结果并继续重算，不为每个缺项再次向人请求许可；多个无冲突
依赖可以按任意顺序或并行完成。只有返回 `WAITING_HUMAN_TRIGGER` 或
`HUMAN_JUDGMENT_REQUIRED` 时才暂停并把精确问题交给人。自动推进在正式 PLAN 人工审批处停止，不能把
“用户要求开始写 PLAN”解释为已经批准最终 PLAN。

如果路径反思尚未通过人工审核，Documentation Agent 申请完成 `PLAN_FORMATION` 时，生产方检查返回该
未满足依赖并禁止签发正式 PLAN 回执。即使一份 PLAN 文件已经被人工交给 Development Agent，消费方
也必须因 `IMPLEMENTATION_DELIVERY` 尚未 `READY` 而拒绝执行。

### 4.7 第一个依赖合同：`PLAN_FORMATION.DRAFT_COMPLETENESS`

`PLAN_REQUESTED` 是用户要求编写正式 PLAN 时产生的启动事件，不是节点。`DRAFT_COMPLETENESS` 是
`PLAN_FORMATION` 的第一个入口依赖，
用于确认草稿足以激活后续并行依赖，不判断路线质量，也不批准 PLAN。

| 字段 | 合同 |
|---|---|
| `major_node_id` | `VERSION.PLAN_FORMATION` |
| `dependency_id` | `DRAFT_COMPLETENESS` |
| `dependency_type` | `AUTOMATED_CHECK` |
| `owner_role` | `STATE_MACHINE`；Documentation Agent 提供输入但不能自报通过 |
| `depends_on` | 有效 `PLAN_REQUESTED` 事件、唯一任务身份和候选草稿身份 |
| `input_contract` | 用户需求引用、草稿路径与 hash、项目/版本或任务身份、Rule Bundle 和当前事实入口 |
| `required_gates` | `G-DRAFT-IDENTITY`、`G-DRAFT-MINIMUM-CONTENT`、`G-DRAFT-BOUNDARY`、`G-DRAFT-BRANCH-MAP` |
| `success_state` | `SATISFIED`；计算并激活适用的并行依赖 |
| `failure_state` | `FAILED`；`PLAN_FORMATION` 保持未完成并返回字段级修正包 |
| `human_mode` | `RULE_RESOLVABLE`；本依赖不请求人判断草稿好坏 |

四个 Gate 分别检查：草稿及任务身份唯一且绑定 hash；背景、目标、范围、非目标、角色、未知项、候选
验收方向和当前/候选边界存在；草稿没有冒充当前能力、正式 PLAN 或开发授权；结构化范围能够确定设计、
安全、数据迁移和外部依赖等条件分支。无法确定某个高风险分支是否适用时，激活对应评估依赖，不静默
判为不适用。

成功响应至少包含：

~~~yaml
result: DEPENDENCY_UPDATED
major_node_id: VERSION.PLAN_FORMATION
dependency_id: DRAFT_COMPLETENESS
dependency_state: SATISFIED
major_node_state: IN_PROGRESS
ready_dependencies:
  - CURRENT_STATE_BASELINE
  - PATH_REFLECTION
  - DESIGN_SCOPE_CHECK
conditional_dependencies:
  - <impact assessments selected by rules>
not_authorized:
  - PLAN_FORMATION.COMPLETED
  - VERSION.IMPLEMENTATION_DELIVERY
~~~

失败时不创建 `DRAFT_REPAIR` 节点。状态机返回缺失项、实际观察、责任角色、修正动作、禁止绕过方式和
重新提交事件；Documentation Agent 修改草稿并提交新 hash 后，重新评估同一依赖。旧回执失效但保留在
事件账本中。

草稿 hash、核心目标/范围、任务身份或适用于当前实例的 Rule Bundle 变化时，本依赖及所有读取旧草稿
语义的下游依赖失效；无关并行工作不清空。

### 4.8 打回路径与打回包依赖

打回不是一句“未通过”直接转交给上游。`RESULT` 语义审查、独立验收或人工产品验收产生拒绝事件后，
必须先在当前工作流中激活 `RETURN_PACKAGE_QUALITY` 依赖，由 Documentation Agent 整理统一打回包；该
依赖 `SATISFIED` 前不得生成返工 `HANDOFF_READY`。

`RETURN_PACKAGE_QUALITY` 至少执行以下 Gate：

| Gate | 必须证明的内容 |
|---|---|
| `G-RETURN-SOURCE-COVERAGE` | 所有当前拒绝结论、症状、证据和来源均已纳入，没有只转述最后一条错误 |
| `G-RETURN-UNKNOWN-MAP` | 已知事实与未知项分开；每个未知项注明为何未知、调查责任角色、所需证据及是否阻断 |
| `G-RETURN-KNOWN-RECOMPOSITION` | 将分散症状重组为完整问题类别、影响范围和可能共同原因，不按发现顺序逐条转抄 |
| `G-RETURN-ONE-PASS` | 对当前已知问题一次性给出修正范围、完成条件、验证方法和所需证据；不得故意拆成多轮逐项打回 |
| `G-RETURN-ROUTE` | 明确返回的大节点和依赖、保留结果、失效结果、必须重跑的 Gate/验收及重新提交事件 |

“一次性”只覆盖打回时已经知道或依据现有证据应当知道的问题，不要求 Documentation Agent 猜测未来
才可能发现的缺陷。未知项不能被省略或伪装成结论；能够由责任 Agent 调查的未知项进入结构化调查动作，
确需产品判断或风险接受时才请求人。

标准返工路由为：

- 开发交付后的文档审查失败：只有 RESULT、证据或交付映射缺项时，返回
  `IMPLEMENTATION_DELIVERY` 中对应依赖，候选代码身份在无相关变化时可以保留；发现实现与 PLAN 不符
  时，返回受影响开发 Task 并使候选及其下游回执失效；发现合同本身需要变化时，返回
  `PLAN_FORMATION` 形成 PLAN Revision；
- 独立验收或人工产品验收失败：Documentation Agent 汇总全部验收输入后生成统一打回包，再按原因返回
  具体开发依赖、设计条件子图、路径反思或 `PLAN_FORMATION`；不得把多个验收方的零散意见原样分别
  交给开发 Agent；
- 每次返工只按显式 `REWORK_EDGE` 和 `INVALIDATION_EDGE` 重算。哪些并行结果保留、哪些失效由实际
  依赖关系决定，不按固定规则清空整个版本；
- 发布后发现问题时，状态机提供现状、影响、可选处置和风险并返回 `HUMAN_JUDGMENT_REQUIRED`，由人
  根据具体情况决定撤回、修复版本或其他处置，状态机不得自动替人选择。

### 4.9 开发与源码验收的全新上下文自查

`IMPLEMENTATION_DELIVERY` 完成前必须满足 `DEVELOPMENT_DOCUMENT_ALIGNMENT_REVIEW`；源码验收分支进入
验收汇合前必须满足 `SOURCE_ACCEPTANCE_DOCUMENT_ALIGNMENT_REVIEW`。两者均属于
`FRESH_CONTEXT_REVIEW` 依赖，由当前责任 Agent 启动一个全新上下文子 Agent 执行。

开发侧自查依赖候选 H、RESULT 草稿和开发验证结果已经冻结，是 `IMPLEMENTATION_DELIVERY` 的最后一道
完成依赖；自查发现问题并引发修改后，原候选和自查回执同时失效。源码验收侧自查依赖源码验收执行
记录和报告已经冻结，是该源码验收分支进入 `ACCEPTANCE` 汇合前的最后一道依赖；它不阻塞其他无依赖
关系的验收分支并行工作。

“全新上下文”至少要求：

- 子 Agent 不继承当前主 Agent 的对话、过程摘要、既有判断或未结构化记忆；重新读取由状态机生成的
  审查输入包；
- 输入包绑定精确的 PLAN commit/blob、候选 commit、适用 Design Baseline、RESULT/验收报告 hash、
  Rule Bundle 和审查清单；不存在的项目显式标记不适用；
- 回执记录独立的 `review_run_id`、审查角色、`parent_context_inherited: false`、输入身份、发现、结论和
  证据引用；不能只由主 Agent 转述“子 Agent 已检查”；
- 自查只读，不直接修改源码、测试、PLAN、RESULT 或验收报告。发现问题后由原责任角色修正；输入发生
  相关变化时旧自查回执失效，并必须由新的全新上下文子 Agent 重查。

开发侧自查必须从获批 PLAN、适用设计基线和 RESULT Delivery Contract 重新建立预期，再对照实际源码、
测试、产物和 RESULT，至少检查：遗漏任务、未授权实现、语义偏差、文档声称与实际不符、替换型变更未
退出旧路径、证据与候选身份错配。其通过只表示开发交付与文档合同对齐，不构成独立源码验收。

源码验收侧自查必须从 PLAN 和验收合同重新建立验收范围，再对照实际执行记录和报告，至少检查：必需
场景遗漏、只复跑开发命令、正向/反向/失败路径覆盖不足、验收环境或候选身份错误、结论超出证据、报告
与实际执行不符。其通过只证明源码验收过程与文档合同对齐，不替代该源码验收本身，也不替代人工验收。

任一自查发现偏差时，状态机按发现性质返回对应开发依赖、源码验收依赖、打回包整理或
`PLAN_FORMATION`，不得带着“已知执行与文档有出入”的结论进入下一大节点。

### 4.10 `IMPLEMENTATION_DELIVERY` 的依赖图

~~~text
已批准计划的交接令牌
          ↓
开发接收检查
          ↓
开发前风险反思（含人工触发）
          ↓
计划任务依赖图
  ├─ 无冲突任务可并行 ──────────────────────────────┐
  ├─ 首条真实纵切 → 架构检查 → 解锁适用扩展任务 ─────┤
  └─ 结果文档持续记录 ───────────────────────────────┤
                                                      ↓ 汇合
                         任务完成 + 结果合同 + 开发 Gate
                                      ↓
                              反证检查（含人工触发）
                                      ↓
                                冻结开发候选 H
                                      ↓
                       全新上下文开发—文档对齐自查
                                      ↓
                         开发与交付大节点完成
~~~

开发前风险反思在任何修改产品源码、测试、依赖、构建或运行配置的任务开始前满足。真实纵切和架构检查
只约束 PLAN 标记为需要先验证路线的任务；与纵切无依赖且无共享写入冲突的准备工作可以并行。RESULT 从
开发开始持续记录，不要求等所有代码完成后再补写，但其最终合同必须和全部开发 Task 一起参与汇合。

开发候选 H 冻结后才进行全新上下文对齐自查，使审查对象绑定精确 commit、RESULT 和证据。自查失败时
H 立即失效并按发现返回具体 Task、RESULT 依赖或 `PLAN_FORMATION`；通过后才能为 `ACCEPTANCE` 签发
交接令牌。

### 4.11 `ACCEPTANCE` 的依赖图

~~~text
冻结候选 H 的交接令牌
          ↓
候选、计划、角色及独立性检查
          ↓
结果文档语义审查
  ├─ 文档退回 ───────────────→ 统一打回包 → 开发交付
  ├─ 计划需修订 ─────────────→ 统一打回包 → 计划形成
  └─ 文档已对齐
          ↓
准备只读验收环境与隔离运行目录
          ↓
  ┌────────────┬────────────┬────────────┬────────────┐
  ↓            ↓            ↓            ↓            ↓
源码验收     集成验收     设计符合度     产物验收     其他适用专项验收
  ↓
全新上下文源码验收—文档对齐自查
  └────────────┴────────────┴────────────┴────────────┘
                               ↓ 全部适用分支汇合
                         人工产品验收
                    ├─ 打回 → 统一打回包 → 精确返工目标
                    └─ 通过
                               ↓
                         验收大节点完成
~~~

`DOC_ALIGNED` 只证明开发交付能够进入验收，不证明实现正确。独立验收分支由 PLAN 和适用规则选择，可以
并行；源码验收侧的全新上下文自查属于源码验收分支自己的结束依赖，不能替代其他验收。任一强制分支
失败时汇合不成立；Documentation Agent 先按 §4.8 形成统一打回包，再由依赖图决定返回位置和失效范围。

人工产品验收只能在全部适用独立验收分支及其自查通过后进行，并绑定同一个候选 H。候选发生相关变化
时，已完成的人工产品验收和读取旧候选的验收分支一并失效。

### 4.12 `CLOSEOUT` 与 `PUBLICATION` 的依赖图

版本收口：

~~~text
已验收候选 H 的交接令牌
          ↓
验收身份与依赖重新校验
          ↓
受保护的本地集成
          ↓
  ┌────────────┬────────────┬────────────┬────────────┐
  ↓            ↓            ↓            ↓            ↓
最终结果记录  当前状态更新   版本索引更新   必要根说明更新  重要历史记录（条件）
  └────────────┴────────────┴────────────┴────────────┘
                               ↓
                         文档一致性检查
                               ↓
                         冻结发布候选 R
                               ↓
                         版本收口大节点完成
~~~

上述文档依赖在逻辑上可以并行准备，但若写入同一仓库或同一权威文件，执行层必须根据 `write_set` 串行
落盘并统一提交。发布候选 R 相对已验收 H 只能包含获授权的收口变化；发现产品源码、测试、依赖、配置、
构建或入包内容发生变化时，不能继续发布，必须按失效图返回验收或开发。

公开发布：

~~~text
已收口候选 R 的交接令牌
          ↓
人工确认是否发布
  ├─ 不发布 → 本节点不适用，版本保持“已验收、未发布”
  └─ 发布
          ↓
重新获取并核对远端基线
          ↓
候选可快进 + 标签不存在 + 身份与依赖仍有效
          ↓
消费一次性发布授权，更新公开主线并创建标签
          ↓
远端主线、标签和公开产物身份复核
          ↓
公开发布大节点完成
~~~

发布确认不能替代远端前置检查。进入 `PUBLICATION`、执行发布动作和记录完成结论三个时点都重新验证
依赖；出现未知远端提交、非快进、同名标签或候选失效时停止，不自动 force push。发布后问题继续按
§4.8 交给人选择撤回、修复版本或其他处置。

### 4.13 标准依赖的判定等级

下表定义首版默认等级；具体版本可以增加证据或收紧等级，但不能把程序、人工、外部或独立验收降级为
普通角色声明。一个组合依赖包含不同等级的子结果时，完成表达式必须分别满足，不能用其中一种覆盖其他
等级。

| 大节点 | `PROGRAM_VERIFIED` | `ROLE_ATTESTED` | `HUMAN_DECIDED` | `EXTERNAL_ATTESTED` |
|---|---|---|---|---|
| 计划形成 | 草稿/文件身份、hash、必填结构、当前事实入口、PLAN 合同 schema、PLAN 身份冻结 | 路径反思、设计适用性声明、专项影响评估、PLAN 候选内容 | 路径反思审核、适用设计审核、PLAN 审批 | 已批准设计快照或其他外部设计回执（适用时） |
| 开发交付 | 接收身份、Git/工作树、测试与构建结果、Gate 结果、RESULT 必填结构、候选 H 冻结 | Pre-mortem、Task 完成声明、RESULT 语义内容、真实纵切说明、Architecture/Falsification 报告、开发对齐自查报告 | Pre-mortem、Architecture Check、Falsification Check 的真实触发事件 | CI、构建系统或受信工具回执（适用时） |
| 验收 | 候选/PLAN 身份、独立性记录、隔离环境、验收分支集合、汇合表达式 | RESULT 语义审查、各独立验收报告、源码验收对齐自查报告、统一打回包 | 人工产品验收 | CI、测试平台、产物扫描或其他受信验收工具回执 |
| 版本收口 | 本地集成身份、授权 diff 范围、文档必填身份、发布候选 R、clean 状态 | RESULT/CURRENT_STATE/索引/根说明的语义更新和一致性结论 | 无新增固定判断；沿用已登记人工产品验收 | 适用的构建或产物身份回执 |
| 公开发布 | 远端 main、可快进关系、tag 不存在、令牌/候选/规则新鲜度、发布后身份 | 发布记录中的非机械说明 | 是否发布及发布后异常处置 | 远端 Git 服务、发布平台和公开产物回执 |

`ROLE_ATTESTED` 仅表示获授权角色对绑定对象作出结构化声明并留下证据，不表示状态机理解了自然语言
内容。凡表中同时出现人工或外部回执的事项，缺少相应回执时不能只靠角色声明满足。

状态机至少在以下时点运行：

- 新 Agent 接收任务包时；
- 当前大节点申请完成、准备交接时；
- 人工触发事件被登记时；
- Agent 报告失败、异常、规则冲突或无法确定转换时；
- 候选冻结、验收结论登记、集成和发布等受保护动作执行前。

状态机是正式工作流状态的唯一判定入口，但不能假设 Agent 技术上无法在外部执行命令。版本 PLAN 必须
列出受保护动作及其强制接入点：候选身份登记、review 接收、验收结论登记、本地集成和正式发布至少要
消费有效状态机回执。绕过状态机产生的文件、commit 或报告可以作为无效旁路事实保留，但不得被登记为
正式候选、验收结果或发布依据；正式发布等不可逆动作应由 Gate-aware wrapper 在执行前直接拒绝。

## 5. 跨版本规则抽象与状态机内部信息

### 5.1 四层模型

现有治理内容先按效力分流：

| 类别 | 判定标准 | 权威载体与效力 |
|---|---|---|
| `ENFORCEABLE` 强制规则 | 存在明确触发时点、输入、责任角色、证据、PASS/FAIL 或允许/拒绝结果；违反后必须阻断状态转换或受保护动作 | 进入状态机的结构化规则注册表；状态机是其唯一强制判定来源 |
| `NORMATIVE` 规范内容 | 原则、解释、经验、写作规范、建议、背景或需要结合语境理解的质量指导；不能被稳定机械判定 | 保留在治理或项目文档；用于指导 Agent，不直接产生 Gate PASS/FAIL |

不能为了减少上下文而把主观规范强行改造成伪机械 Gate，也不能把本应阻断的强制要求继续只藏在长篇
文档中。一个句子同时包含两类语义时必须拆分：例如“发布必须经人确认”作为强制 Gate 进入状态机，
“人确认时重点关注真实使用体验”作为规范内容留在文档。人工判断的**存在、身份和时点**可以是强制
规则，具体主观判断标准仍可由文档说明。

强制规则与规范内容可以互相引用，但不对同一事项同时拥有强制判定权。文档可以用 Rule ID 解释某条
强制规则的背景，不得维护另一份可独立解释的强制条件；状态机可以给出 `guidance_refs`，但规范文档
不能绕过规则注册表临时新增隐藏 Gate。尚不能确定分类的内容标记为 `CLASSIFICATION_REQUIRED`，由
Rules Agent 收口后才能进入正式 Bundle。

对于已经分流为强制规则的内容，状态机还必须把稳定规则与版本事实分离，使用以下四层模型：

| 层级 | 内容 | 所有权与约束 |
|---|---|---|
| 治理基础层 | 角色权限、人工模式、通用 Gate 语义、证据等级、候选/验收/发布不变量、失败分类 | Rules Agent 维护；跨版本复用，不包含具体版本号或候选身份 |
| 工作流模板层 | 可复用大节点、依赖图、完成表达式和转换 | Rules Agent 维护；模板引用稳定 Rule/Gate ID，不复制规则正文 |
| 版本/任务覆盖层 | 批准 PLAN 身份、本版 Task、附加 Gate、证据参数、Design Baseline、候选与包要求 | Documentation Agent 在获批 PLAN 中维护；只能按基础层授权的参数点补充或收紧 |
| 运行实例层 | 大节点与依赖状态、事件、Gate 结果、证据引用、交接包、回执和 blocker | 状态机追加记录；绑定不可变 Rule Bundle，不作为规则定义来源 |

合并结果称为 `Rule Bundle`。每个 Bundle 必须具有 `bundle_id`、schema version、基础规则版本、模板
版本、PLAN/任务覆盖层身份、生成时间和内容 hash。运行实例只执行已冻结 Bundle，不在运行时重新解释
长篇自然语言文档。

覆盖层不得删除、放宽或重新定义基础层强制规则。只有基础规则明确声明为可参数化、且 PLAN 提供合法
参数时才能改变具体值；新增版本 Gate 可以收紧合同。出现同一 ID 多重定义、相反义务、多个合法转换、
未授权放宽或无法确定优先级时，编译必须失败并返回 `RULE_REVIEW_REQUIRED`，不得使用“最后写入覆盖”。

新增版本的正常接入不修改状态机引擎：选择一个已注册的 `workflow_template_id`，提供获批 PLAN/任务
覆盖层并编译新 Bundle 即可。只有出现现有抽象无法表达的新治理语义时，才由 Rules Agent 版本化基础
规则或模板。

### 5.2 规则、Gate、大节点、依赖项与转换

#### 5.2.1 Rule Definition

每条跨版本规则至少包含：

| 字段 | 要求 |
|---|---|
| `rule_id` / `rule_version` | 稳定语义身份；语义变化必须升版，不能原地改义 |
| `scope` / `applicability` | 适用的工作流类型、大节点/依赖能力、角色和条件；不得依赖版本名硬编码 |
| `effect` | `REQUIRE`、`FORBID`、`ALLOW` 或 `ROUTE` |
| `enforcement_points` | 大节点接收、依赖判定、完成、交接或受保护动作前的执行时点 |
| `evaluator` | 可复现的程序判定器或结构化声明验证器及参数；不得把无证据自由文本 PASS 当成完成 |
| `evidence_contract` | 判定所需证据类型、签发方、hash、新鲜度和完整性 |
| `failure_result` | 稳定 reason code、责任角色和 remediation 引用 |
| `human_mode` | `RULE_RESOLVABLE`、`HUMAN_TRIGGERED` 或 `HUMAN_JUDGMENT` |
| `source_ref` | 强制规则注册表中的可追溯位置和版本/hash；可另引规范背景但不改变强制语义 |
| `change_policy` | 规则更新对未来实例、在途实例和既有交接包的允许影响 |

规则应按能力和不变量表达，例如“候选冻结前所有强制开发 Gate 必须 PASS”，而不是“V2.3.0 的 T07
必须 PASS”。具体 Task/Gate 对照由覆盖层提供。

#### 5.2.2 Gate Definition

每个 Gate 至少包含 `gate_id`、目标不变量、责任角色、触发时点、输入证据、判定器、允许结果、失败
reason code、remediation、是否阻断及新鲜度要求。Gate 结果只能来自以下可登记来源：确定性判定器、
受信工具输出、绑定身份的授权角色结构化声明、独立角色回执或真实人工事件；自由文本结论只能作为说明，
且 `ROLE_ATTESTED` 不得伪装为 `PROGRAM_VERIFIED`。

#### 5.2.3 Major Node Definition

每个大节点至少包含 `major_node_id/version`、目的、主责任角色、适用性、开始表达式、完成表达式、输入
合同、接收检查、允许/禁止动作、依赖图引用、合法后继、返工目标、失效边、Rule Bundle hash 和 Role
Card 模板。大节点是正式交接单位；版本不得把一次字段检查伪装成新的生命周期阶段。

#### 5.2.4 Dependency Definition

每个依赖项至少包含：

| 字段 | 要求 |
|---|---|
| `dependency_id` / `dependency_version` | 在所属大节点内稳定且唯一的身份 |
| `dependency_type` | §4.2 注册的类型；复杂依赖可引用子工作流模板 |
| `owner_role` | 责任 Agent、人、受信工具或外部系统 |
| `verification_level` | `PROGRAM_VERIFIED`、`ROLE_ATTESTED`、`HUMAN_DECIDED` 或 `EXTERNAL_ATTESTED` |
| `execution_context_contract` | 是否要求全新上下文、允许继承的输入、禁止继承的会话信息及执行身份要求 |
| `purpose` / `applicability` | 必须证明的事实及可判定适用条件 |
| `depends_on` | 明确局部先后关系；空集合表示可与其他无冲突依赖并行 |
| `input_contract` / `required_output` | 判定所需输入、产出或事件身份 |
| `required_gates` | 必须逐项判定的 Gate ID |
| `write_set` | 可能修改的权威对象，用于发现并行冲突 |
| `rework_target` / `invalidation_edges` | 失败或输入变化时的精确影响范围 |
| `remediation_refs` | 各 reason code 对应的修正方案 |
| `applicable_rule_refs` | 引用 Rule ID，不复制规则正文 |

#### 5.2.5 Transition Definition

转换必须由“目标大节点 + 受控事件 + 完成表达式 + 受影响子图”唯一决定，并声明大节点的新状态、被激活
或失效的大节点/依赖项、目标角色、需要失效的旧回执及原子提交要求。一次事件可以满足一个依赖并使
多个无冲突依赖进入 `READY`，但不能隐式满足它们。允许返工回路，但必须有明确进入条件、退出条件、
最大次数或升级策略和 remediation；无法退出的循环、不可达大节点、无责任依赖、并行写冲突或同一
输入对应多个转换必须在编译期拒绝。

### 5.3 规则分流、真源与编译

正式形态采用分流后的两个非重叠真源：

- 状态机结构化规则注册表是 `ENFORCEABLE` 强制内容的唯一执行真源，由 Rules Agent 人工维护并版本化；
- 治理与项目文档是 `NORMATIVE` 规范内容的真源，继续由对应文档责任角色人工维护；
- 文档对强制规则只保留索引、Rule ID、背景解释或系统生成的非权威展示；状态机对规范内容只保留
  `guidance_refs`，不复制其完整语义。

这里禁止的是“同一条强制规则由人分别维护两份”，不是禁止人工维护。Rules Agent 仍负责人工新增、
修改、升版或废止强制规则；文档责任角色仍正常维护规范内容。任何规范内容升级为强制规则，或强制
规则降级为规范内容，都属于显式分类变更：必须记录原因、适用范围和对在途实例的影响，不能只改措辞。

当前 `HUMAN_AI_WORKFLOW.md` 同时包含两类内容。在获批迁移和 `ENFORCEMENT_ACTIVATED` 发生前，它仍按
现行规则承担治理真源职责。首版实施必须先形成逐条分类清单：强制内容迁入结构化注册表，规范内容继续
留在文档，混合内容拆分，并证明没有强制要求在迁移后只剩自然语言。切换完成后再删除文档中的重复
强制定义或降为明确标注的索引/解释，不能先删除后迁移。

规则编译器至少必须：

1. 解析强制规则注册表、工作流模板和版本/任务覆盖层；
2. 校验 schema、稳定 ID、引用完整性、角色权限、覆盖权限和唯一转换；
3. 检测不可达大节点、孤立依赖、无出口阻断、无修正方案、未约束循环、并行写冲突和基础规则被削弱；
4. 生成不可手改的 Rule Bundle、大节点/依赖索引、Gate 索引、remediation 索引及 Role Card；
5. 生成“适用强制规则覆盖清单”，证明每条命中规则进入了 Gate、大节点/依赖合同或明确的非适用结论；
6. 对相同输入确定性地产生相同语义内容与 hash；编译不唯一时 fail closed。

以下组合示例用于约束抽象方向，不预先冻结具体文件格式：

~~~text
基础规则 RULE.CANDIDATE.REQUIRED_GATES
  含义：候选冻结前，当前覆盖层声明的全部 mandatory development gates 必须 PASS

工作流模板 VERSION.IMPLEMENTATION_DELIVERY
  依赖：CANDIDATE_FREEZE
  引用：RULE.CANDIDATE.REQUIRED_GATES
  成功事件：CANDIDATE_SUBMITTED
  后继大节点：VERSION.ACCEPTANCE

某版本 PLAN 覆盖层
  mandatory_development_gates:
    - G-DEV-BUILD
    - G-DEV-SEMANTIC
    - G-REFLECT-FALSE
  candidate_identity_fields:
    - commit
    - plan_blob
    - clean_status
~~~

下一版本可以改变 Gate 清单和证据参数，但继续使用同一条基础规则、大节点/依赖模板和状态机代码。若某版本
试图把 `mandatory_development_gates` 设为空，编译器必须根据参数 schema 和适用规则判断是否合法，
不能仅因 YAML/JSON 语法正确而接受。

### 5.4 运行实例

每个工作流实例至少记录：

- `workflow_id`、`workflow_template_id/version`、适用版本/任务和批准 PLAN commit/blob；
- 完整任务图版本、大节点状态、每个大节点的依赖状态，以及 `ready_major_node_set`、
  `active_major_node_set`、`ready_dependency_set`、`failed_dependency_set`、
  `waiting_human_dependency_set` 和当前治理状态；
- 已接收事件及其 `event_id`、`idempotency_key` 和发生时间；
- 每个 Gate 的状态、判定原因和证据引用；
- `evidence_log_root`、每项依赖的判定等级以及对应 evidence record/hash；
- 当前使用的 `bundle_id/hash`、规则源 hash、大节点/依赖版本和已签发 Role Card hash；
- 已生成的交接包、接收回执、失败次数和未解决 blocker；
- 全新上下文审查的 `review_run_id`、输入包 hash、上下文来源声明、报告 hash、结论和失效状态；
- 人工触发或判断事件的身份、时间和适用范围。

运行记录采用追加式事件账本；当前状态由已接受事件重放得到，不能通过直接修改“当前状态”字段绕过
历史。证据只保存引用、摘要和 hash，不复制源码、长日志、真实用户正文或凭据。

### 5.5 规则升级与在途实例

运行实例默认固定创建时的 Rule Bundle；新规则不得静默改变已发生事件或把历史失败重写为通过。
Rules Agent 更新规则时必须声明以下一种适用范围：

- `FUTURE_ONLY`：只用于之后创建的实例；
- `UNSTARTED_NODES`：可升级在途实例尚未开始的大节点及依赖，升级前重新编译并作兼容检查；
- `INVALIDATE_ACTIVE`：安全或治理风险要求当前 Role Card、交接包或 Gate 失效，必须记录失效事件、
  影响范围、恢复大节点/依赖和重新验收要求。

任何升级都必须保留旧 Bundle 和事件的可审计身份。状态机不得把新规则套用到历史事件后重新生成一条
看似从未中断的状态链；升级是显式事件。PLAN Revision、候选失效和证据失效继续遵循各自规则，不能
仅通过升级 Bundle 绕过。

### 5.6 事件

事件至少包含：

~~~text
event_id
event_type
workflow_id
major_node_before
dependency_id  # 事件针对某个依赖时必填
actor_role
occurred_at
evidence_refs
context_provenance  # FRESH_CONTEXT_REVIEW 事件必填
rule_bundle_hash
idempotency_key
previous_event_hash
payload
~~~

事件类型必须来自受控枚举；自由文本只作为补充说明。相同 `idempotency_key` 不得产生两次状态转换。
事件引用的 Bundle、大节点、依赖或角色与当前实例不一致时必须拒绝，不能自动改写为最新版本。

`actor_role` 必须由有效 `accept-handoff` 回执绑定的执行身份或受信系统身份导出，不能信任事件 payload
自报角色。`HUMAN_TRIGGERED` 与 `HUMAN_JUDGMENT` 事件必须来自 PLAN 冻结的可信人工通道并携带可验证
回执；Agent 转述“人已经同意”不构成人工事件。具体身份载体由实施 PLAN 冻结，但不得使用一段可复制
的普通自然语言作为授权凭据。

首版允许 Product Owner 在当前受管聊天中的原始回复直接形成可信人工事件，不要求另建审批界面。事件
适配器必须记录来源会话/线程、原始消息 ID、发送时间、原文 hash、人工身份、关联工作流、精确审核对象
及该对象 hash。只有在状态机先给出单一明确审核请求，且回复能够唯一关联该请求时，“通过”“打回”等
简短回复才有效；Agent 复制、摘要或转述同一句话不能生成第二个人工事件。

### 5.7 证据判定等级与指定日志路径

状态机核心不调用 AI 理解自然语言证据。每个依赖必须在模板中声明以下一种判定等级，运行时不得临时
改变：

| 等级 | 状态机行为 | 对外表述 |
|---|---|---|
| `PROGRAM_VERIFIED` | 运行确定性判定器，直接验证文件、hash、Git、schema、测试结果、身份、新鲜度或其他可计算事实 | 程序已验证 |
| `ROLE_ATTESTED` | 接受获授权角色的结构化完成声明；程序只验证角色、输入绑定、证据封套、日志写入和必填字段，不判断自然语言内容是否正确 | 角色声明完成，未做程序语义验证 |
| `HUMAN_DECIDED` | 接受可信人工通道产生的限定结果并验证身份、对象和时点 | 人工已判断 |
| `EXTERNAL_ATTESTED` | 验证 CI、外部服务或受信工具签发的结构化回执 | 外部系统已证明 |

只有依赖合同明确允许 `ROLE_ATTESTED` 时，角色声明才能参与完成表达式；高风险依赖不得在运行时从
`PROGRAM_VERIFIED`、`HUMAN_DECIDED` 或独立验收降级为角色声明。全新上下文子 Agent 报告属于外部
角色证据：程序验证其运行身份、输入 hash、上下文来源声明和报告封套，但不声称已经理解报告语义。

无法由程序检查的证据信息统一写入实施 PLAN 冻结的 `evidence_log_root`，默认组织方式为：

~~~text
<evidence_log_root>/<workflow_id>/<major_node_id>/<dependency_id>/evidence.jsonl
~~~

每条记录至少包含 `evidence_id`、工作流/版本/大节点/依赖身份、判定等级、提交角色、发生时间、输入
身份、产物或外部证据引用、内容 hash、结构化声明、已知限制、敏感信息标记、前一记录 hash 和当前
记录 hash。日志采用追加写，不允许覆盖旧记录；事件账本保存对应 `evidence_id` 和记录 hash。

指定日志保存证据信息、摘要、引用和必要的小型结构化结果，默认不复制源码、长日志、真实用户正文、
凭据或其他敏感原文。具体产物仍留在其权威位置并用 hash 绑定。日志根目录不可用、记录写入失败、hash
链断裂或证据封套不完整时，该提交失败且不得签发交接令牌。

以后如引入 AI 自动复核 `ROLE_ATTESTED` 日志，必须作为新的版本化 evaluator 和显式规则变更接入，声明
模型、输入范围、输出 schema、失败语义和对在途实例的适用范围。新 evaluator 不得把历史“角色声明”
静默改写成“程序已验证”。

首版唯一强制使用 AI 子 Agent 的位置是 §4.9 已定义的开发执行—文档对齐自查和源码验收执行—文档
对齐自查。它们是工作流中的外部角色，不是状态机内部 evaluator；状态机只验证运行身份、全新上下文
声明、输入绑定、报告封套和结构化结论，并按 `ROLE_ATTESTED` 保存证据。其他不能由程序检查的内容在
首版只保存角色声明与证据信息，不自动调用 AI 进行二次解释或复核。

## 6. 自包含判定结果与打回信息

状态机输出的目标不是把 Agent 再次引回长篇文档，而是让接收方只凭本次响应即可完成当前大节点中
已就绪的依赖。来源文档用于审计、追溯和深入理解，不应成为执行普通依赖前的默认必读项。响应必须
足够丰富，但只包含当前大节点和活动依赖相关内容，不能重新注入全部治理文本。

依赖提交、大节点接收、完成和转换检查使用以下顶层结果：

| 结果 | 含义 |
|---|---|
| `HANDOFF_ACCEPTED` | 交接令牌已在线验证并消费；返回节点执行回执、大节点合同、依赖图和当前可执行依赖 |
| `DEPENDENCY_UPDATED` | 依赖结果已登记；返回依赖状态及重算后的并行可执行集合 |
| `MAJOR_NODE_COMPLETED` | 大节点完成表达式成立；原子更新受影响子图并返回新解锁的大节点 |
| `HANDOFF_READY` | 已为选定的 `READY` 目标大节点签发目标专用交接令牌，允许人转交其交接包 |
| `BLOCKED` | 大节点完成表达式尚未成立；返回失败或缺失依赖及修正方案 |
| `WAITING_HUMAN_TRIGGER` | 等待人执行明确的触发动作；不要求人重新分析规则 |
| `HUMAN_JUDGMENT_REQUIRED` | 确实需要人的产品判断、风险接受或新授权 |
| `RULE_REVIEW_REQUIRED` | 规则缺失、冲突、循环或不可执行；由人把治理事件包转给 Rules Agent |
| `INVALID_TRANSITION` | 当前状态不允许该事件，拒绝改变状态 |

### 6.1 通用响应信封

每个结果都必须返回机器字段和面向 Agent 的可执行说明，至少包括：

| 内容组 | 最低内容 |
|---|---|
| 判定身份 | `decision_id`、时间、结果、reason code、workflow/目标大节点/依赖、责任角色、Bundle/PLAN/Role Card hash |
| 当前事实 | 目标大节点状态、依赖图摘要、并行可执行/失败/等待人工依赖、Gate、事件、有效输入和 blocker |
| 判定解释 | 命中的强制 Rule ID、期望与实际、为何允许/拒绝，以及哪些状态没有发生变化 |
| 当前合同 | 大节点目标、活动依赖合同、允许/禁止动作、必需产出、受保护动作和完成表达式 |
| 行动方案 | 有序步骤、每步责任角色、前置条件、预期产物和完成判定 |
| 证据合同 | 可接受证据类型、来源、hash/身份/新鲜度要求，以及不足或禁止的替代证据 |
| 规范提示 | 当前大节点和活动依赖所需的 `guidance_items`；包含内容、来源、hash、相关原因及 `blocking: false` |
| 后继动作 | 可提交事件、可并行依赖、重试/交接接口、下一合法角色/大节点、失效时间和幂等键要求 |
| 审计信息 | 响应 hash、上一事件 hash、交接包/回执身份和可复核来源引用 |

`guidance_items` 默认直接携带完成当前大节点活动依赖所需的定向规范内容，而不只给出文件路径。每项内容由模板或
覆盖层声明的稳定 selector 从规范文档快照取得，至少包含 `source_ref`、`source_hash`、
`why_relevant`、`content` 和 `blocking: false`。它是源文档的自动投影视图，不允许手工改写后继续使用；
超出当前范围需要的背景只保留引用。若 selector 失效、来源 hash 不匹配或无法确定摘录边界，生成失败并
返回规则/配置审查，不能静默省略，也不能回退为要求 Agent 阅读全部文档。

### 6.2 各结果的专用内容

- `HANDOFF_ACCEPTED`：返回当前大节点 Role Card、依赖图、输入摘要、可执行依赖、强制规则、规范提示、
  允许/禁止动作、完成表达式、事件 schema 及绑定本次执行身份的节点执行回执；
- `DEPENDENCY_UPDATED`：返回该依赖的 Gate、产出身份、前后状态、受影响依赖及大节点完成表达式结果；
- `MAJOR_NODE_COMPLETED`：返回大节点完成依据、产出身份、新激活/失效大节点和可准备的交接目标；
- `HANDOFF_READY`：针对一个已选定的 `READY` 大节点返回目标专用交接令牌、正式交接包、下一角色、
  大节点 Role Card、有效期和在线接收方法；同一事件解锁多个大节点时分别生成令牌和包；
- `BLOCKED`：返回失败 Gate、差异、仍由谁处理、有序修正步骤、禁止绕过方式、所需产出、验证方法和
  重提事件；
- `WAITING_HUMAN_TRIGGER`：返回等待的精确人工动作、可信事件入口、触发前允许/禁止的工作，以及
  收到事件后的唯一下一步；
- `HUMAN_JUDGMENT_REQUIRED`：返回需要决定的单一问题、可选项、证据、影响、风险、安全默认状态和
  可接受的决定事件；不得让人重新阅读全部规则后自行设计流程；
- `RULE_REVIEW_REQUIRED`：返回缺失/冲突规则、受影响大节点/依赖、无法唯一判定的原因、已冻结的动作和可直接
  交给 Rules Agent 的最小治理事件包；
- `INVALID_TRANSITION`：返回被拒绝事件、当前允许事件、正确责任角色和修正入口，并明确状态未变化。

### 6.3 结构化修正包

`BLOCKED`、`INVALID_TRANSITION` 和 `RULE_REVIEW_REQUIRED` 不能只返回自然语言错误，必须生成结构化
处理包。以下是最低字段，不限制响应加入上述通用信封：

~~~yaml
result: BLOCKED
workflow_id: <id>
current_major_node: <major-node>
target_dependency: <dependency-or-null>
responsible_role: <role>
reason_code: <stable-code>
failed_gates:
  - gate_id: <gate>
    expected: <condition>
    observed: <evidence-or-missing-item>
required_actions:
  - <ordered executable action>
forbidden_actions:
  - <action that must not be used as a workaround>
required_outputs:
  - <file, field, event or evidence reference>
resubmit_event: <event type>
next_allowed_role: <role>
rule_refs:
  - <rule id>
~~~

修正方案必须告诉 Agent：为什么被打回、缺少什么、按什么顺序处理、禁止用什么方式绕过、完成后提交
什么事件，以及仍由当前角色处理还是需要转交其他角色。Agent 不需要重新设计返工流程。

## 7. Role Card 与交接包

状态机按当前大节点和已就绪依赖生成最小 Role Card，至少包含：

- 当前大节点、目标、责任角色、进入原因、依赖图摘要和合法后继大节点；
- 允许动作与禁止动作；
- 输入合同、当前可执行依赖、必需产出、Gate、大节点完成表达式和证据格式；
- 每项依赖的判定等级；`ROLE_ATTESTED` 时明确声明字段、证据封套和指定日志位置；
- 每个活动依赖的执行上下文要求；要求全新上下文时明确禁止继承的内容和回执字段；
- 可用事件、提交 schema、失败 reason code 和修正方案入口；
- 与当前大节点及活动依赖直接相关的规范 `guidance_items`，默认包含定向内容与来源/hash，而不只是文档路径；这些
  内容标记 `blocking: false`，不产生隐藏 Gate；
- Rule Bundle hash、PLAN 身份和本次交接包 hash。

正式交接包至少包含：

- 工作流、大节点、依赖图版本、版本、分支、执行路径和候选/PLAN 身份；
- 当前大节点已满足依赖的实际产出与证据引用；
- Gate 逐项结果和状态机判定；
- 允许的下一角色、下一大节点及其 Role Card；
- 未解决风险、适用偏差和必须保持的阻断项；
- 可由下一 Agent 验证的交接回执。

Role Card 和交接包都是从规则定义与运行实例生成的视图，不构成新的规则真源，不允许 Agent 手工修改
后继续使用。下一 Agent 必须通过 `accept-handoff` 验证包 hash、规则版本、角色和大节点。

### 7.1 最小上下文的完整性

“最小”不能靠人工删减。编译器必须从当前大节点、活动依赖、角色、事件和覆盖层出发，计算适用强制
规则的传递闭包，将完成当前可执行工作所必需的规则、Gate、输入、输出、禁止动作和修正入口写入 Role Card；未命中的
强制规则不放入正文。Role Card 同时携带适用 Rule ID 清单和 Bundle hash，使接收方无需阅读全文，
也能验证没有使用缓存摘要或任意删减版。

每张 Role Card 必须附机器生成的覆盖证明：命中的每条强制规则分别落到哪个字段、Gate 或受保护动作；
强制规则为何不适用只保存在编译审计中，不把全部非适用规则重新塞回 Agent 上下文。若存在命中规则无法
映射、引用闭包不完整或超出 Role Card schema 的语义，编译失败并进入规则审查，不能以长文档全文
作为静默 fallback。

规范内容不参与强制规则覆盖率，但系统应按大节点/依赖模板提供少量、定向的 `guidance_items`，默认直接给出
当前工作所需内容，使 Agent 无需另行打开文档。不得把全部规范文档拼入 Role Card；也不得因为 Agent
没有遵循一条尚未升级为强制规则的建议，就由状态机伪造 Gate 失败。若某项规范被反复违反并需要
阻断，应由 Rules Agent 将可判定部分显式升级为强制规则，而不是继续增加提示词。

实施 PLAN 必须为 Role Card 设置可复核的上下文预算和超限策略。验收同时报告：治理真源总规模、每张
Role Card 的字符或 token 规模、相对比例、适用强制规则覆盖率、无关强制规则进入数和规范文档引用
数量。适用强制规则覆盖率必须为 100%，受控样本中的无关强制规则正文进入数必须为 0；超过预算时
应推动规则拆分或依赖图重构，不能静默恢复为全文输入。

### 7.2 最小执行接口

正式实现至少提供以下命令或等价 API；名称可以由 PLAN 冻结，但语义不得合并为一个自由文本入口：

| 接口 | 作用 |
|---|---|
| `compile-rules` | 从强制规则注册表、模板和覆盖层生成并验证 Rule Bundle |
| `start-workflow` | 绑定启动事件、版本身份和 Bundle，创建运行实例并签发首节点根交接令牌 |
| `accept-handoff` | 在线验证并原子消费交接令牌，校验角色、目标大节点、身份、新鲜度和 Bundle，生成节点执行回执 |
| `submit-event` | 引用节点执行回执，按事件 schema 提交结构化完成声明、证据、人工触发或失败事件 |
| `handoff-check` | 判定大节点完成表达式；完成时为各合法后继签发目标专用交接令牌，否则返回结构化修正包 |
| `prepare-handoff` | 将一个目标大节点的交接令牌、Role Card 和证据摘要封装为独立交接包 |
| `workflow-status` | 返回大节点及依赖状态集合、Gate、blocker 和各 READY 工作项允许动作，不输出无关规则全文 |
| `replay-workflow` | 从事件账本重放并验证状态、hash 链、幂等和篡改 |

所有接口必须提供稳定结构化输出、reason code 和进程/API 失败语义。拒绝、损坏、判定不唯一或 Gate
失败不能只打印提示后返回成功；机器调用方必须能据退出码或响应状态阻止后续动作。

### 7.3 节点执行回执与交接令牌

“节点密钥”正式定义为状态机签发的**交接令牌**，它是不可伪造、可失效、目标专用的能力凭证，不是
由 Agent 保存或共同维护的共享密码。状态机签名材料和权威账本不得放在 Agent 可修改的项目工作区。

凭证链包含：

1. `start-workflow` 根据有效启动事件签发首个大节点的根交接令牌；
2. Agent 调用 `accept-handoff` 时提交交接令牌以及自己的身份、版本和目标节点声明；状态机以令牌和
   账本为权威，Agent 输入只用于核对，不能自行选择令牌未授权的版本或节点；
3. 校验成功后，状态机原子消费交接令牌并签发当前节点执行回执；之后的依赖提交必须引用该回执；
4. Agent 按状态机返回的 schema 逐项提交完成声明和证据。状态机执行可程序检查的判定，将不可程序
   检查的证据写入指定日志，并持续返回尚未满足的依赖；
5. 只有大节点完成表达式成立，`handoff-check` 才能为每个合法后继分别签发新的交接令牌；
6. 下一 Agent 必须在线调用 `accept-handoff`，由状态机结合最新账本重新验证并消费令牌；只检查字符串
   或离线签名不能开始任务。

每个交接令牌至少绑定：`token_id`、`workflow_id`、版本身份、源/目标大节点、允许接收角色、源状态
revision、PLAN 身份、适用候选身份、Rule Bundle hash、已满足依赖摘要 hash、签发/失效时间、nonce、
上一令牌或事件 hash 和状态机签名。令牌本身不携带长证据正文。

一个大节点解锁多个并行后继时必须签发多个目标专用令牌，不能用一个通用令牌进入任意分支。汇合节点
依据事件账本验证所有适用分支的完成回执，不要求 Agent 手工拼接或共享多个秘密。重复接收使用幂等键
返回原结果；被其他执行者消费、目标/角色不匹配或重复使用的令牌必须拒绝。

PLAN、候选、Rule Bundle、依赖结果或授权身份发生相关变化时，状态机按失效图撤销受影响令牌。下一
节点即使持有旧令牌，也必须因在线验证失败而停止并获得重新执行的精确依赖。没有有效交接令牌时，
Agent 可以说明已完成的工作内容，但不得获得下一节点 Role Card、提交下一节点正式事件或产生正式
项目效力。

## 8. 人的职责边界

人当前仍负责：

- 把有效交接包传递给下一 Agent；
- 创建或选择下一 Agent 的实际会话；
- 对 `HUMAN_TRIGGERED` Gate 发出真实触发事件；
- 处理 `HUMAN_JUDGMENT_REQUIRED` 中不可由规则决定的事项。

人不需要：

- 阅读全部治理规则后判断下一 Agent；
- 手工拼接 Role Card；
- 判断普通缺项应重做哪个依赖或回到哪个大节点；
- 为可机械化 Gate 重复审批；
- 代替 Agent 完成反思、证据整理或修正工作。

## 9. Rules Agent 与其他角色

- Rules Agent 负责治理内容的强制/规范分类，维护强制规则注册表、工作流模板、Gate 语义、reason code
  和修正方案，并继续维护属于全局治理的规范文档；不参与产品开发，也不把具体版本候选身份写入
  基础层；
- Documentation Agent 把获接受的规则影响同步到项目 PLAN、HISTORY、RESULT 和交接身份，并在 PLAN
  中维护本版覆盖层；覆盖层只能填写授权参数、增加或收紧版本 Gate，不修改基础规则语义；
- Development、Design 和 Acceptance Agent 只消费适用 Role Card，提交事件、产出和证据；
- Development Agent 按获批 PLAN 实现编译器、状态机、存储和受保护动作适配器，不能通过实现细节
  改变 Rules Agent 已冻结的规则语义；
- Acceptance Agent 从规则模型独立推导跨版本、遗漏、绕过、篡改、升级、恢复和最小上下文用例；
- 状态机只执行已定义规则；出现无唯一答案的治理问题时 fail closed 并返回
  `RULE_REVIEW_REQUIRED`；
- Rules Agent 更新规则后必须声明适用范围，状态机据此判断现有交接包、候选和 Gate 是否失效。

## 10. 最低验收要求

正式实现至少证明：

1. 缺少任一强制 Gate 时不能生成 `HANDOFF_READY`；
2. 未收到人的触发事件时，反思等 `HUMAN_TRIGGERED` 依赖保持等待；
3. Agent 不能通过提交无证据自由文本、把角色声明冒充程序验证或直接修改状态文件绕过 Gate；允许的
   `ROLE_ATTESTED` 必须使用结构化封套并写入指定证据日志；
4. 角色不匹配、大节点过期、PLAN 身份不一致、规则 hash 过期或交接包被修改时，`accept-handoff`
   必须失败；
5. 重复事件幂等，不产生二次转换或伪造单一“当前节点”；
6. 已定义普通失败返回同一责任角色和可执行修正包，不无条件升级给人；
7. 未定义事件、冲突转换、循环规则和无修正方案的阻断项进入 `RULE_REVIEW_REQUIRED`；
8. `HUMAN_JUDGMENT_REQUIRED` 只覆盖规则明确列出的人工判断类型；
9. 交接包能够让下一 Agent 在不全文读取治理文档的情况下确定允许动作、必需产出和退出条件；
10. 事件账本能够重放当前状态，并检测删除、重排、篡改或规则版本漂移；
11. 人工中转不会改变状态机判定；无有效回执的工作不能进入正式验收、集成或发布；
12. 状态机故障、存储损坏或判定不唯一时 fail closed，并提供可恢复的诊断信息；
13. 同一引擎在不修改代码的情况下，能够用同一模板运行至少两个不同版本/任务覆盖层，并分别生成
    正确的 Bundle、Role Card、Gate 和交接包；
14. 覆盖层试图删除、放宽、改义或以同 ID 替换基础规则时，编译失败；新增合法版本 Gate 时不要求
    修改引擎或复制整套治理规则；
15. Role Card 的适用规则覆盖清单为 100%，注入一条当前大节点或活动依赖必须适用的测试规则后能够
    自动进入卡片和 Gate；与当前工作无关的规则正文不进入卡片；
16. Rules Agent 发布新规则后，`FUTURE_ONLY`、`UNSTARTED_NODES` 和 `INVALIDATE_ACTIVE` 三种范围
    分别按定义工作，旧 Bundle、历史事件和失效回执仍可审计；
17. 普通缺项、可修复 Gate 失败和明确非法转换由系统自动返回责任角色与修正步骤，不要求人判断；
    只有登记的人工触发和人工判断类型才等待人；
18. 候选登记、验收结论登记、集成或发布尝试绕过有效回执时，受保护动作被拒绝，或其结果明确保持
    无正式效力且不能被后继 Gate 接受；
19. 编译期能够拒绝缺失引用、无责任角色、无 remediation、不可达大节点、孤立依赖、未约束循环、
    并行写冲突和相同输入对应多个转换的规则包；
20. 首次迁移清单中的每条现行治理内容都有 `ENFORCEABLE`、`NORMATIVE` 或
    `CLASSIFICATION_REQUIRED` 结论；激活时 `CLASSIFICATION_REQUIRED` 为 0，且不存在只留在文档中
    却预期阻断流程的强制要求；
21. 规范文档中的普通指导不能自行产生 Gate 失败；同一条强制条件在注册表和人工维护文档中出现两份
    可独立修改的定义时，迁移/编译检查必须阻断；
22. 将一条规范升级为强制规则、或将强制规则降级为规范内容时，必须产生分类变更事件并按声明范围
    处理在途 Bundle，不能静默改变现有工作流；
23. `HANDOFF_ACCEPTED` 返回的启动包能够让未预读治理全文的 Agent 正确说明大节点目标、当前可执行
    依赖、允许/禁止动作、证据格式、完成表达式和提交事件；不能依赖测试者凭项目记忆补全；
24. 九类顶层结果均包含适用的通用响应信封和专用内容；删除行动步骤、证据合同、禁止绕过方式或下一
    合法事件等关键字段时，schema/验收必须失败，不能降级为只有文档链接；
25. `guidance_items` 只包含当前大节点和活动依赖相关规范内容，内容与 `source_ref/source_hash` 一致；selector 失效、
    来源变化或摘录边界不唯一时 fail closed，不返回过期摘录，也不要求 Agent 改读全部文档；
26. 对同一大节点的相同活动依赖分别使用“完整治理文档输入”和“状态机启动包输入”执行受控任务，后者必须保持所有
    强制 Gate 与关键交付结果一致，同时满足 PLAN 冻结的上下文预算；
27. 同一大节点可以同时产生至少两个互不冲突的 `READY` 依赖，它们被不同责任方处理、以不同顺序
    满足时，最终完成表达式结果一致，且任一分支不能改写另一分支状态；
28. `ALL_OF` 汇合在任一适用依赖未满足时保持不成立；合法 `NOT_APPLICABLE` 可以按合同参与汇合，但
    Agent 自报“不适用”不能跳过依赖；
29. 人工审核依赖打回后，只重新激活定义的返工依赖或上游大节点；读取旧结果的下游依赖和回执按
    invalidation graph 失效，无关并行分支保持有效；
30. 文档 Agent 在阻断依赖未满足时尝试完成 `PLAN_FORMATION`，生产方检查返回精确缺失依赖；把该 PLAN 直接
    交给 Development Agent 时，消费方检查仍独立拒绝，不能复用或伪造生产方回执；
31. 同一结构化事件对应多个分支、并行依赖写同一权威对象、完成表达式循环依赖或返工边无退出策略时，
    工作流编译失败；
32. 上游 PLAN、规则、候选或证据身份改变时，只重算受影响子图，并使所有依赖旧身份的 Role Card、
    Gate 和交接包失效；已满足且无依赖关系的并行依赖不得被无理由清空；
33. `workflow-status` 分别返回大节点集合和每个大节点的依赖集合，而非伪造单一 current node；多个
    活动大节点、等待人工依赖和失败依赖同时存在时，响应仍能给出精确责任角色和下一合法事件。
34. 用户提交有效 `PLAN_REQUESTED` 后，`PLAN_FORMATION` 自动计算依赖；Documentation Agent 能依据
    响应连续完成所有 `RULE_RESOLVABLE` 依赖，并且只在真实人工触发或判断依赖处停止；
35. 不涉及界面、交互或设计基线变化的版本将设计分支判为 `NOT_APPLICABLE`，不会因缺少设计稿、人工
    预览或 Design Snapshot 阻塞 PLAN；命中设计变化时才展开设计子工作流；
36. RESULT 语义审查失败时，系统在返工交接前强制执行 `RETURN_PACKAGE_QUALITY`；仅文档/证据缺项、
    实现不符和 PLAN 合同变化分别路由到正确依赖或大节点，并具有不同的失效范围；
37. 多个独立验收分支同时打回时，Documentation Agent 生成一个统一打回包，覆盖全部当前已知问题，
    而不是向开发 Agent 分批转发互相割裂的报告；
38. 打回包能够区分已知事实和未知项，把已知症状重组为问题类别，并为每个问题给出修正范围、完成
    条件、验证方法和证据要求；缺少任一部分时不能生成返工 `HANDOFF_READY`；
39. 返工只使 `REWORK_EDGE` / `INVALIDATION_EDGE` 可达且依赖旧结果的部分失效；无关并行依赖保持有效。
40. 每次 `accept-handoff` 都重新验证目标大节点的开始依赖、证据身份和新鲜度；延后发布时已有旧 PASS
    但远端基线、候选身份或其他可变前置条件变化，`PUBLICATION` 仍不能进入；
41. 每个标准版本进入 `CLOSEOUT` 前都有绑定版本与候选身份的真实人工产品验收事件，Agent 或子 Agent
    生成的结论不能代签；
42. 开发申请完成 `IMPLEMENTATION_DELIVERY` 时，缺少合格的全新上下文子 Agent 对齐审查、子 Agent
    继承了主对话、审查输入身份不完整或发现尚未处理的文档偏差，转换必须失败；该自查 PASS 不能被
    登记为独立源码验收；
43. 适用源码验收进入验收汇合前，必须由另一个全新上下文子 Agent 核对实际验收执行、报告与 PLAN/
    验收合同；遗漏必需场景、身份错配、结论超出证据或只复跑开发命令时不能汇合；
44. 候选、PLAN、适用设计基线、RESULT 或源码验收报告发生相关变化后，绑定旧输入的全新上下文自查
    回执自动失效，必须生成新的 `review_run_id` 后重新检查。
45. `PROGRAM_VERIFIED` 依赖由确定性判定器实际检查；将相同输入篡改为不同文件、hash、commit、测试
    结果或身份时能够稳定失败，不能退化为接受 Agent 自报；
46. `ROLE_ATTESTED` 依赖明确显示“未做程序语义验证”，同时把完整证据封套写入指定日志；缺少日志、
    角色不匹配、输入身份不完整或 hash 链异常时依赖不能满足；
47. 状态机核心在不调用任何 AI 的情况下，能够仅凭 Rule Bundle、结构化事件、程序判定结果、角色声明
    封套和人工/外部回执确定性重放相同状态；
48. 指定证据日志路径不可写、记录被覆盖或删除、事件账本中的 evidence hash 与日志不一致时 fail closed，
    且不能签发交接令牌；
49. 下一 Agent 缺少交接令牌，或令牌属于错误版本、源/目标节点、角色、PLAN、候选、Rule Bundle、状态
    revision 时，`accept-handoff` 必须拒绝；已消费或已撤销令牌不能重放；
50. 一个大节点解锁两个并行后继时分别签发目标专用令牌；任一令牌不能进入另一分支，汇合节点根据账本
    等待全部适用完成回执；
51. 新增 AI 证据复核器后，旧 `ROLE_ATTESTED` 记录仍保持原判定等级；没有显式升级事件时不能被追溯
    改写为 `PROGRAM_VERIFIED`。
52. 首版两个本地 Agent 会话能够通过同一状态机实例和共享治理运行目录完成令牌交接、证据读取和状态
    重放；使用未配置的远端机器或另一份本地状态副本时必须拒绝，不能静默分叉状态；
53. Product Owner 在受管聊天中对精确审核请求的原始回复能够生成一次人工事件；删除消息 ID、审核对象
    hash 或来源会话后事件必须无效，Agent 转述相同文字不能通过；
54. 除 §4.9 两类全新上下文子 Agent 外，首版状态机处理 `ROLE_ATTESTED` 证据时不产生 AI 调用；核心
    状态可在关闭全部模型能力后重放得到相同结果；
55. 安全测试覆盖令牌误用、重放、过期、普通篡改和错误身份，但不以抵御拥有本机完全权限并主动窃取
    状态或签名材料的恶意 Agent 作为首版通过条件。

验收必须包含反向场景：伪造 Gate PASS、跳过反思、使用旧交接包、交给错误角色、重复提交事件、修改
证据后复用旧回执、直接开始下一大节点、覆盖层削弱基础规则、版本名称硬编码、缺失规则被 Role Card
静默漏掉、只返回文档路径或一句“请按规则修正”、规范摘录过期/错配，以及 Rules Agent 更新规则后
继续使用旧 Role Card。还必须包含：不涉及设计的版本被错误要求提供设计稿、文档审查只打回最后一个
缺项、多个验收报告被分批转交、未知项被遗漏、已知症状未重组、返工时无依据清空全部并行结果、复用
旧节点 PASS 进入新节点、主 Agent 自报完成全新上下文审查、子 Agent 继承主对话、审查输入变化后复用
旧回执、把开发侧对齐自查冒充独立源码验收、把角色声明伪装成程序验证、证据日志不可写后继续签发
令牌、跨版本或跨分支复用令牌，以及撤销后离线接受旧令牌。

验收报告必须分别给出三类结果，不能用功能可运行替代目标达成：

- **规则执行正确性**：强制规则命中、Gate 判定、受保护动作和绕过反证；
- **上下文减负**：Role Card 适用强制规则完整性、无关规则排除、定向规范引用及相对全文输入的可复核
  规模；
- **人工依赖降低**：测试矩阵中由系统自动路由/修正的事件数量，以及仍需人的事件是否全部属于已批准
  的 `HUMAN_TRIGGERED` / `HUMAN_JUDGMENT` 类型。

## 11. 落地边界

本需求是治理基础设施候选，不进入 `CURRENT_STATE.md`，也不因本草稿存在而约束当前已批准 PLAN。
正式实施前必须由 Rules Agent 确认规则包和适用范围，由 Documentation Agent 将实施任务、交付合同、
bootstrap 例外和独立验收要求写入获批 PLAN，再由 Development Agent 实现、Acceptance Agent 独立
验证。

在程序完成前，不得宣称状态机已经运行。现阶段仍只能使用人工交接检查。首版 PLAN 必须冻结一次性
bootstrap 合同，至少写明：哪些开发大节点/依赖暂由现行人工规则约束、谁核对 bootstrap 证据、状态机完成
哪些正向与负向验收后触发 `ENFORCEMENT_ACTIVATED`、从哪个精确大节点开始所有新交接必须机器校验，
以及激活前交接包何时失效。不得用“开发状态机需要先绕过状态机”建立永久例外。

激活后发生引擎故障或账本损坏时默认 fail closed。恢复不能直接编辑当前状态；必须依据最后一个可验证
快照和事件 hash 链生成恢复事件、说明丢失范围并重新执行受影响 Gate。只有获批 PLAN 明确列出的紧急
人工恢复权限可以介入，且其使用本身必须追加审计并在恢复后接受独立复核。

本机制首先作为项目级治理基础设施独立演进，不绑定 V2.3.0 或任一产品版本的完成状态。选择首个承载
实施的版本只决定交付时间和覆盖层身份，不得把引擎、基础规则或模板退化为该版本专用实现。

### 11.1 需求文档收口

剩余大节点依赖合同和首轮强制规则映射补齐后，Documentation Agent 必须执行一次整体去重：同一约束只
保留一个权威定义，其他位置改为稳定引用；概念说明、数据 schema、验收矩阵和反向场景分层组织，避免
在正文与验收条款中重复维护相同语义。压缩前后必须建立要求映射，证明强制规则、失败路径和已确认人工
边界没有因删减而丢失。完成该收口前，本文件仍保持候选需求状态，不进入正式 PLAN。
