# 插入需求：Agent 交接状态机与规则执行器

> 文档角色：项目治理能力的需求池草稿
> 状态：候选需求；不是版本 PLAN，不构成开发授权，也不表示当前已经实现
> 记录日期：2026-09-26
> 适用场景：当前由人负责多 Agent 信息中转的协作方式

## 1. 背景与问题

项目已有较多角色、权限、反思、证据、验收和发布规则，但目前主要依赖 Agent 主动阅读、理解并
执行。规则可能被忽视，Agent 也可能在完成当前工作后自行推断下一步，导致目标偏离、强制 Gate 被
跳过，或把本可由规则处理的问题再次升级给人。

当前尚未封装自动多 Agent 协作。不同 Agent 之间的信息中转、任务创建和启动仍由人完成。因此，本
需求不建设自动 Agent 编排器，也不要求程序自动创建、唤醒或切换 Agent。状态机的当前职责是：在
Agent 交接前和下一 Agent 接收时执行规则约束，确保交接内容、Gate、角色和下一步动作都已经确定。

## 2. 目标

建设一个项目级的“状态机 + Gate 引擎 + 修正方案库 + 交接包生成器”，把可机械化的流程复杂度交给
程序，而不是要求每个 Agent 全文阅读规则、临场解释路由或自行设计返工步骤。

系统必须实现以下结果：

1. 当前 Agent 只有通过交接检查才能生成正式交接包；
2. 下一 Agent 只有成功接收有效交接包才能开始正式工作；
3. Gate 未完成时保持在当前节点，并返回明确、可执行的修正步骤；
4. 需要人主动触发的节点在收到真实触发事件前不能继续；
5. 只有产品判断、风险接受、新外部授权或不可逆真实数据操作才请求人作决定；
6. 规则缺失、冲突或不可执行时返回规则审查，而不是让执行 Agent 自行猜测；
7. 人继续负责 Agent 间的信息搬运，但不再负责重新解释全部规则和手工判断合法转换。

## 3. 非目标

- 不自动创建、启动、暂停、唤醒或关闭 Agent；
- 不自动完成跨 Agent 的消息投递；
- 不替代人选择实际使用哪个 Agent、会话或执行环境；
- 不把主观产品质量判断伪装成机械 Gate；
- 不属于 ResumeAssistant 面向用户的产品功能；
- 不允许 Rules Agent、Documentation Agent 借此直接修改产品源码；
- 不把自由文本提示词作为唯一状态、事件或权限来源。

## 4. 现实运行方式

~~~text
人把任务包交给当前 Agent
→ 当前 Agent 运行 accept-handoff，校验交接身份、角色、规则版本和允许节点
→ Agent 按 Role Card 完成当前节点
→ Agent 提交节点事件、产出和证据引用
→ 状态机运行 handoff-check，计算 Gate 和合法转换
→ HANDOFF_READY：生成标准交接包，注明允许的下一节点与角色
→ 人把交接包传给下一 Agent
→ 下一 Agent 再次运行 accept-handoff；校验失败则不得开始
~~~

状态机不负责替人传递消息。它约束的是“上一个 Agent 在什么条件下可以把什么内容交给谁，以及下一
Agent 在什么条件下可以开始”。

状态机至少在以下时点运行：

- 新 Agent 接收任务包时；
- 当前节点申请完成、准备交接时；
- 人工触发事件被登记时；
- Agent 报告失败、异常、规则冲突或无法确定转换时；
- 候选冻结、验收、集成和发布等受保护节点切换前。

## 5. 状态机内部信息

### 5.1 规则定义

每个节点必须包含：

| 字段 | 要求 |
|---|---|
| `node_id` / `node_version` | 稳定节点身份和版本 |
| `owner_role` | 当前节点唯一责任角色 |
| `purpose` | 本节点必须实现的结果 |
| `input_contract` | 开始节点必须具备的输入与身份 |
| `allowed_actions` | 本角色在该节点允许执行的动作 |
| `forbidden_actions` | 明确禁止的越权动作 |
| `required_outputs` | 节点结束前必须形成的产出 |
| `required_gates` | 必须逐项判定的 Gate ID |
| `transitions` | 各事件和 Gate 组合对应的唯一合法转换 |
| `remediation_refs` | 每种失败 reason code 对应的修正方案 |
| `human_mode` | `RULE_RESOLVABLE`、`HUMAN_TRIGGERED` 或 `HUMAN_JUDGMENT` |
| `rule_source_hash` | 本节点所依据的规则真源版本/hash |

### 5.2 运行实例

每个工作流实例至少记录：

- `workflow_id`、适用版本/任务和批准 PLAN commit/blob；
- 当前节点、当前责任角色和当前治理状态；
- 已接收事件及其 `event_id`、`idempotency_key` 和发生时间；
- 每个 Gate 的状态、判定原因和证据引用；
- 当前使用的规则源 hash、节点版本和 Role Card hash；
- 已生成的交接包、接收回执、失败次数和未解决 blocker；
- 人工触发或判断事件的身份、时间和适用范围。

运行记录采用追加式事件账本；当前状态由已接受事件重放得到，不能通过直接修改“当前状态”字段绕过
历史。证据只保存引用、摘要和 hash，不复制源码、长日志、真实用户正文或凭据。

### 5.3 事件

事件至少包含：

~~~text
event_id
event_type
workflow_id
node_before
actor_role
occurred_at
evidence_refs
rule_source_hash
idempotency_key
payload
~~~

事件类型必须来自受控枚举；自由文本只作为补充说明。相同 `idempotency_key` 不得产生两次状态转换。

## 6. 判定结果与打回信息

状态机只返回以下顶层结果：

| 结果 | 含义 |
|---|---|
| `HANDOFF_READY` | 当前节点完成，允许人把生成的交接包转给指定角色 |
| `BLOCKED` | 当前节点尚未完成；原责任 Agent 按修正包继续处理 |
| `WAITING_HUMAN_TRIGGER` | 等待人执行明确的触发动作；不要求人重新分析规则 |
| `HUMAN_JUDGMENT_REQUIRED` | 确实需要人的产品判断、风险接受或新授权 |
| `RULE_REVIEW_REQUIRED` | 规则缺失、冲突、循环或不可执行；由人把治理事件包转给 Rules Agent |
| `INVALID_TRANSITION` | 当前状态不允许该事件，拒绝改变状态 |

`BLOCKED`、`INVALID_TRANSITION` 和 `RULE_REVIEW_REQUIRED` 不能只返回自然语言错误，必须生成结构化
处理包：

~~~yaml
result: BLOCKED
workflow_id: <id>
current_node: <node>
responsible_role: <role>
reason_code: <stable-code>
failed_gates:
  - gate_id: <gate>
    expected: <condition>
    observed: <evidence-or-missing-item>
required_actions:
  - <ordered executable action>
forbidden_actions:
  - <action that must not be used as a workaround>
required_outputs:
  - <file, field, event or evidence reference>
resubmit_event: <event type>
next_allowed_role: <role>
rule_refs:
  - <rule id>
~~~

修正方案必须告诉 Agent：为什么被打回、缺少什么、按什么顺序处理、禁止用什么方式绕过、完成后提交
什么事件，以及仍由当前角色处理还是需要转交其他角色。Agent 不需要重新设计返工流程。

## 7. Role Card 与交接包

状态机按当前节点生成最小 Role Card，至少包含：

- 当前节点、目标、责任角色和允许的下一节点；
- 允许动作与禁止动作；
- 输入合同、必需产出和 Gate；
- 可用事件、失败 reason code 和修正方案入口；
- 规则源 hash、PLAN 身份和本次交接包 hash。

正式交接包至少包含：

- 工作流、节点、版本、分支、执行路径和候选/PLAN 身份；
- 当前节点的实际产出与证据引用；
- Gate 逐项结果和状态机判定；
- 允许的下一角色、下一节点及其 Role Card；
- 未解决风险、适用偏差和必须保持的阻断项；
- 可由下一 Agent 验证的交接回执。

Role Card 和交接包都是从规则定义与运行实例生成的视图，不构成新的规则真源，不允许 Agent 手工修改
后继续使用。下一 Agent 必须通过 `accept-handoff` 验证包 hash、规则版本、角色和节点。

## 8. 人的职责边界

人当前仍负责：

- 把有效交接包传递给下一 Agent；
- 创建或选择下一 Agent 的实际会话；
- 对 `HUMAN_TRIGGERED` Gate 发出真实触发事件；
- 处理 `HUMAN_JUDGMENT_REQUIRED` 中不可由规则决定的事项。

人不需要：

- 阅读全部治理规则后判断下一 Agent；
- 手工拼接 Role Card；
- 判断普通缺项应退回哪个节点；
- 为可机械化 Gate 重复审批；
- 代替 Agent 完成反思、证据整理或修正工作。

## 9. Rules Agent 与其他角色

- Rules Agent 维护节点定义、转换、Gate、reason code 和修正方案，不参与产品开发；
- Documentation Agent 把获接受的规则影响同步到项目 PLAN、HISTORY、RESULT 和交接身份，不修改
  规则语义；
- Development、Design 和 Acceptance Agent 只消费适用 Role Card，提交事件、产出和证据；
- 状态机只执行已定义规则；出现无唯一答案的治理问题时 fail closed 并返回
  `RULE_REVIEW_REQUIRED`；
- Rules Agent 更新规则后必须声明适用范围，状态机据此判断现有交接包、候选和 Gate 是否失效。

## 10. 最低验收要求

正式实现至少证明：

1. 缺少任一强制 Gate 时不能生成 `HANDOFF_READY`；
2. 未收到人的触发事件时，反思等 `HUMAN_TRIGGERED` 节点保持等待；
3. Agent 不能通过提交自由文本、自报 PASS 或直接修改状态文件绕过 Gate；
4. 角色不匹配、节点过期、PLAN 身份不一致、规则 hash 过期或交接包被修改时，`accept-handoff`
   必须失败；
5. 重复事件幂等，不产生二次转换或两个并行“当前节点”；
6. 已定义普通失败返回同一责任角色和可执行修正包，不无条件升级给人；
7. 未定义事件、冲突转换、循环规则和无修正方案的阻断项进入 `RULE_REVIEW_REQUIRED`；
8. `HUMAN_JUDGMENT_REQUIRED` 只覆盖规则明确列出的人工判断类型；
9. 交接包能够让下一 Agent 在不全文读取治理文档的情况下确定允许动作、必需产出和退出条件；
10. 事件账本能够重放当前状态，并检测删除、重排、篡改或规则版本漂移；
11. 人工中转不会改变状态机判定；无有效回执的工作不能进入正式验收、集成或发布；
12. 状态机故障、存储损坏或判定不唯一时 fail closed，并提供可恢复的诊断信息。

验收必须包含反向场景：伪造 Gate PASS、跳过反思、使用旧交接包、交给错误角色、重复提交事件、修改
证据后复用旧回执、直接开始下一节点，以及 Rules Agent 更新规则后继续使用旧 Role Card。

## 11. 落地边界

本需求是治理基础设施候选，不进入 `CURRENT_STATE.md`，也不因本草稿存在而约束当前已批准 PLAN。
正式实施前必须由 Rules Agent 确认规则包和适用范围，由 Documentation Agent 将实施任务、交付合同、
bootstrap 例外和独立验收要求写入获批 PLAN，再由 Development Agent 实现、Acceptance Agent 独立
验证。

在程序完成前，不得宣称状态机已经运行。现阶段仍只能使用人工交接检查；如果后续 PLAN 要求“机器
强制交接”，则状态机本身必须在该产品开发节点开始前完成 bootstrap 和负向验收。
