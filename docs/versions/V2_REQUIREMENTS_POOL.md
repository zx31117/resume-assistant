# AI Career Resume Assistant V2 阶段需求池

> 文档角色：V2 剩余工作、迁移去向与 V3 前硬门禁的唯一需求池
> 状态：非版本计划、非开发指令；只有获批并进入对应版本 PLAN 的条目才构成开发要求
> 重整日期：2026-09-25
> 适用发布列车：V2.3.0 多用户服务器底座 → V2.4.0 生成质量冻结 → V3.0.0 免费多用户首发

## 1. 本次重整结论

旧需求池以 V2.0.0 的完整设想为主体，混合了已完成能力、已被产品方向否定的交互、V3 候选和仍待
实现的底层工作，已经不能继续作为排期输入。本次不再给旧正文叠加状态说明，而是按以下规则重整：

1. 已由 V2.0.0—V2.2.0 完成的能力只保留归档索引，不重复排期；
2. 与当前产品目标冲突的要求直接移除，不换一种措辞继续占用范围；
3. 多用户、数据库/向量隔离、服务器运行与公共契约归入 V2.3.0；
4. 召回、润色、内容预算、一页纸闭环和最终文件质量归入 V2.4.0；
5. 浏览器助手、模拟面试、多模板和高级编辑不阻断 V3.0.0 首发；
6. V3.0.0 若不能稳定生成可直接投递的一页纸专业简历，就必须延期，不得用插件、增长或发布包装
   替代生成质量。

## 4. V2.3.0：多用户服务器底座

V2.3.0 不承担生成算法重写，但必须为 V2.4.0 和 V3.0.0 提供不可绕过的数据、权限和运行契约。

### 4.1 必须完成

| ID | 要求 | 最低完成定义 |
|---|---|---|
| V2R-23-01 | 账号与会话 | `account_id` 只来自可信服务端会话，普通请求不能自报身份 |
| V2R-23-02 | PostgreSQL 业务真源 | 服务器模式不以 SQLite 作为活动业务真源 |
| V2R-23-03 | pgvector 派生向量 | 向量可重建，先按账号过滤，再做相似度排序 |
| V2R-23-04 | 数据、向量、任务和文件隔离 | RLS 默认拒绝；请求、后台任务、连接池、Range/HEAD、清理和恢复均覆盖 |
| V2R-23-05 | ApplicationCase | 绑定账号、岗位快照、选材、生成修订、产物、权益和埋点 |
| V2R-23-06 | 生成公共契约 | 预留并版本化 `EvidenceSelection`、`ResumeContentPlan`、`ResumeRevision`、`LayoutPlan`、`Artifact` |
| V2R-23-07 | UsageRecord 与权益账本 | 模型用量用于成本和公平使用；权益按完整任务幂等结算，不按调用次数向用户扣减 |
| V2R-23-08 | 三类埋点 | 产品、运行、质量事件分流，禁止正文、直接身份、密钥和完整模型响应进入事件 |
| V2R-23-09 | 服务器运行 | HTTPS、密钥、迁移、备份恢复、回滚、限流、资源清理和环境隔离具备实操证据 |
| V2R-23-10 | 关键业务不变量 | 账号归属、内容来源、状态、产物、权限、隐私、权益和资源生命周期进入模型、接口、运行时证据与验收 |

### 4.2 可随 V2.3.0 完成但不阻断

- 浏览器助手“当前标签页岗位 → 用户确认 → ApplicationCase”的协议探针；
- 导入去重 L1（文件字节）与 L2（规范化文本）；
- 受控测试账号之外的运营页面；
- 站点适配器原型。

若三天范围发生冲突，先完成账号/数据/向量隔离、ApplicationCase、公共生成契约、服务器恢复和埋点，
不得用插件原型换掉这些底座。

## 5. V2.4.0：生成质量冻结

V2.4.0 是 V3.0.0 前最后一次允许系统性重塑生成内核的版本。它既是召回/润色调优版，也是“一页纸
可直接投递成品”的冻结版。V3.0.0 只允许把这套内核迁入公开运行环境并做有界参数调优。

### 5.1 硬用户结果

每个被系统标记为成功的最终结果必须同时满足：

1. **事实可信**：所有内容可追溯到当前账号允许的 Fact；无虚构指标、身份、经历或技能；
2. **岗位相关**：优先呈现目标岗位最有价值的事实，不是通用经历堆叠；
3. **可直接投递**：无占位符、空章节、重复 bullet、调试文字、未完成提示或需要用户大段返工的正文；
4. **一页纸**：批准参考环境中的最终 DOCX 为一页，由该 DOCX 转换的最终 PDF 也恰好一页；
5. **专业排版**：使用获批生产模板，标题、层级、间距、换行、强调和中英文混排达到可读性下限；
6. **同一修订**：预览、DOCX 和 PDF 来自同一冻结 `ResumeRevision` 与 `LayoutPlan`；
7. **失败诚实**：不能满足事实、页数或可读性门禁时，不得把多页、截断或不可读文件标为可投递成功。

“一页纸”不得通过静默删除必要事实、裁切溢出、隐藏内容、局部极小字号或生成与下载不同的文件实现。

### 5.2 冻结生成流水线

~~~text
JobModelSnapshot
→ EvidenceSelection
→ ResumeContentPlan（章节、优先级、内容预算）
→ ResumeRevision（逐条 fact_refs）
→ LayoutPlan（版本化模板与全局排版参数）
→ DOCX
→ 批准 Word 参考环境实际渲染
→ PDF 与真实页数/换行/溢出测量
→ 超页时受控压缩或重新选材
→ 重新渲染，直到通过或明确失败
→ 冻结并发布同源 Artifact
~~~

`ResumeContentPlan` 必须在生成前分配章节和条目预算；`LayoutPlan` 必须记录模板、字体、字号、行距、
段距、页边距和版本。字符数只能作预约束，最终页数和换行以真实参考渲染结果为准。

### 5.3 超页处理顺序

发生超页时按固定顺序收敛，不允许随机缩字：

1. 删除同义重复与空泛修饰；
2. 压缩超长 bullet，保留动作、方法、结果与事实边界；
3. 合并相邻重复表达；
4. 降低低优先级 Fact 的表达篇幅；
5. 移除当前岗位价值最低且非必要的 Fact；
6. 在批准下限内依次调整全局段距、行距、字距和字号；
7. 重新由 Word 渲染并复测 DOCX/PDF；
8. 仍不能通过时明确失败或要求用户确认取舍，不静默输出两页成品。

### 5.4 召回与润色

- `Person Model × Job Model` 只改变召回、排序和表达重点，不改变用户事实命题；
- JD 明示、Role Prior 与 Company Context 分层保存，先验和公司材料不能冒充招聘方硬要求；
- Company Context 只使用批准来源、版本和 TTL，失败时可退回 JD/Role Prior；
- Stable Evidence 可以复用，Adaptive Evidence 按岗位重算；缓存键必须覆盖 Fact、岗位族、规则、
  Prompt 和模型版本；
- 混合召回以固定评测集验证 Recall@K、Precision@K、nDCG 或批准等价指标；
- 润色以事实越界、岗位覆盖、重复/套话、可读性、篇幅和人工偏好共同判定；
- 模型自评只能辅助，不能单独宣布质量通过。

### 5.5 单一生产模板

V3.0.0 前只冻结一套稳定生产模板，不把多模板、用户自选字体、密度滑杆或逐项排版配置作为发布前
目标。系统负责在事实和可读性边界内完成专业判断。多模板只能在生成内核稳定后作为后续增强。

### 5.6 评测与人工验收

正式 PLAN 必须冻结有代表性的质量集，至少覆盖：

- short / typical / long Career Memory；
- 中文、英文与中英文混排；
- 完整、宽泛、噪声和缺少关键信息的 JD；
- 多行业、多岗位、旧经历、弱相关事实与负样例；
- 长公司名、长岗位名、长 bullet、特殊字符、粗体关键词和字体替代；
- cold/warm、缓存命中/未命中、正常/失败/重试路径；
- 双账号与负向哨兵，证明质量调优没有放宽隔离和事实边界。

除了机械门禁，还必须由 Product Owner 对代表性真实岗位执行盲评或人工验收。正式 PLAN 应冻结样本、
判分表、基线、通过阈值和失败处置，不能在结果出来后改变标准。

### 5.7 V2.4.0 阻断规则

以下任一项未通过，V3.0.0 不得首发：

- 成功任务不能稳定生成可直接投递的一页纸 Word/PDF；
- 一页依赖截断、隐藏内容或突破可读性下限；
- 召回/润色提升以事实越界、跨账号数据或不可复现模型自评为代价；
- 预览、DOCX、PDF 或下载文件不是同一冻结修订；
- 代表性质量集或 Product Owner 人工验收未达到批准阈值。

浏览器助手、自动上传、模拟面试、多模板、完整修订 diff UI、OCR、BYOK 和本地模型不在上述阻断项中。

## 6. V3.0.0 之后允许与禁止的变化

### 6.1 允许持续调优

- 召回权重、top-k、rerank 阈值和负样例；
- Role Profile 与 Company Context 内容、权重和缓存；
- Prompt、模型版本、表达风格和去重规则；
- 章节内容预算与条目长度预算；
- 已批准下限内的全局排版参数；
- 性能、缓存、成本和检索效率。

### 6.2 不应再大改

- Experience / Fact 的事实真源与用户确认边界；
- Person Model 与 Job Model 的职责边界；
- EvidenceSelection、ResumeContentPlan、ResumeRevision、LayoutPlan 与 Artifact 的身份关系；
- DOCX/PDF 同源和真实渲染测量；
- 一页纸闭环与失败语义；
- 多用户数据库、向量、任务和文件隔离；
- 产物来源追踪和发布原子性。

若 V3.0.0 后仍需改变上述合同，说明 V2.4.0 未完成冻结，不得把它包装成普通微调。

## 7. 延后或移出的需求

| 需求 | 去向 | 原因 |
|---|---|---|
| 浏览器助手 L1/L2/L3、自动上传 | V3-CANDIDATE / RESEARCH | 长期方向保留，但不阻断生成质量和免费多用户首发 |
| 模拟面试、开放题 Agent | V3-CANDIDATE | 需要独立价值、成本和事实回流验证 |
| 多套生产模板和高级排版编辑 | DEFERRED | 先冻结单一可靠模板 |
| 逐条锁定、完整 diff/回滚 UI、任意局部重生成 | DEFERRED | 可用意图级修改替代首发复杂交互 |
| OCR 扫描件导入 | DEFERRED | 不阻断文本 PDF/手工录入主链 |
| L3 经历/Fact 语义去重 | DEFERRED | 需要人工冲突处理与可撤销合并设计 |
| 多 Provider、BYOK、本地模型、完整离线 PWA | V3-CANDIDATE / RESEARCH | 与服务端首发主线不一致 |
| 手机完整深度编辑 | V3-CANDIDATE | PC 工作台优先 |

## 8. 已移除要求

以下内容不再作为需求候选：

- 首屏要求用户选择模板、页数、排版密度或理解模型参数；
- 默认让用户逐项勾选锁定、审核所有选材后系统才做专业判断；
- 固定“主页/履历库/管理后台恰好三个入口”的信息架构约束；
- V2 必须一次支持多个 Provider、任意 Base URL 和用户自带 Key；
- 面向普通用户展示 Token 单价或按模型调用次数收费；
- 把本地 loopback 安全规则当作服务器公开运行方案；
- 与当前路线不一致的旧 A—E 实施阶段和旧版完成清单。
