# V2.0.1 PLAN：本地流程可观测性与问题定位

> 当前状态：已批准执行；可以按本 PLAN 向开发 Agent 交接
> 计划与批准日期：2026-08-31
> 版本性质：V2.0.0 上的开发诊断与运行可见性补丁；项目尚未正式上线，本版本不区分用户界面与开发界面
> 发布基线：公开 `main@e914aaf4cf797048100e3b8e1e0f6ca408817241`，annotated tag `v2.0.0` 指向该发布链

## 1. 版本目标

V2.0.0 已把配置、维护、履历和生成做成三页本地图形交互，但生成、经历提取、Experience 写入、迁移和 Embedding 重建等长耗时请求主要只显示“执行中”。V2.0.1 要让当前操作、真实阶段、每阶段耗时、失败位置和脱敏后台日志在现有界面中可见，使开发和问题复盘可以回答：

1. 当前执行的是什么操作，进行到哪个真实步骤；
2. 当前步骤已耗时多久，完整操作结束后各步骤分别耗时多久；
3. 时间花在本地数据库、文件、计算、LLM 还是 Embedding；
4. 是否正在正常等待、内部重试/退避、已经超时、失败、断连或被进程中断；
5. 刷新页面或事后复盘时，如何用同一 `operation_id` 取得脱敏诊断证据；
6. 本次耗时与近期同类操作相比是否异常。

本版本先建立可观测性，不把观测结果直接等同于性能优化。该诊断能力作为开发基础设施贯穿整个 V2；V2.1.0 预计重新设计整个界面，V2.0.1 只要求现有页面可用，不提前实施 V2.1.0 的页面分层、视觉重构或最终信息架构。

## 2. 当前源码证据与问题边界

开发开始前必须现场复核以下基线，不得只照抄本文：

- `backend/services/resume_generation_service.py` 已有请求内 `GenerationContext` 和阶段耗时，但阶段只随成功响应返回，长请求执行中、失败后和页面刷新后不可查询；
- `frontend/src/pages/GeneratePage.tsx` 当前只显示“生成中…”，无法看到生成服务已存在的阶段；
- `frontend/src/pages/ProfilePage.tsx` 的提取、单条 CRUD 和批量保存只有忙碌/结果状态，批量保存是顺序调用单条 create；
- `backend/core/concurrency.py` 只保存共享门禁的操作名，冲突只能返回 `holder`，没有操作编号、开始时间和当前阶段；
- `backend/api/routes/system.py` 的迁移、重建和重试在共享门禁内同步执行；状态接口没有活动操作和历史日志；
- Python `logging` 中现有自由文本可能包含 Experience ID、绝对输出路径或异常详情，不能直接原样暴露给前端；
- 当前没有跨请求的统一操作记录、刷新后复盘、轮转留存、近期阶段耗时对比或脱敏诊断摘要。

如果现场源码已经变化，开发 Agent 必须先把差异记录进 `RESULT.md`，再按本 PLAN 的行为契约实现，不得为迁就本文文件名而复制第二套机制。

## 3. 已冻结的产品与架构选择

### 3.1 当前不区分用户与开发者

项目尚未正式上线，V2.0.1 不建立账号、角色、权限、开发模式开关或两套诊断页面。现有三页中的当前操作和详细耗时，以及本地系统页中的运行日志，对当前本机使用者直接可见。

这不等于允许泄露敏感数据。日志仍只服务 loopback 本地应用，并继续受现有 Host、Origin、CSRF、Cookie 和路径边界约束。

### 3.2 与 V2.1.0 界面重设计的边界

- V2.0.1 复用 `/`、`/profile`、`/system`，不新增第四个顶层页面；
- 生成页和履历页显示本页发起操作的当前状态与阶段时间线；
- 本地系统页增加“运行活动”和“后台日志”，负责跨页面查看与事后复盘；
- 不为当前布局建立复杂设计系统或稳定公开 UI 契约；
- 操作、阶段、耗时、日志和诊断 API 与 React 展示解耦，供 V2.1.0 重做界面时复用；
- V2.1.0 可以重新安排诊断信息的位置、层级和界面分离方式，但整个 V2 阶段必须继续保留同等问题定位能力；
- 是否在 V2 阶段结束后长期保留该诊断设施，届时根据实际价值、隐私与维护成本另行决定。

### 3.3 同步业务请求不变

生成、提取、CRUD 和维护请求仍使用现有同步服务和事务，不引入消息队列、Worker、任务调度或第二业务链路。前端在发起请求前生成合法 UUID 作为 `X-Operation-ID`，后端校验、注册并在响应头和错误详情中回传；非页面客户端未提供时由后端生成。

批量导入保存可以额外使用 `X-Operation-Group-ID` 关联多个顺序 create 子操作，但每个数据库事务仍有独立 `operation_id`，不能把部分失败伪装成整个批次成功。

### 3.4 进度读取与留存

V2.0.1 使用短轮询，不引入 SSE 或 WebSocket：

- 活动操作期间前端约每 1 秒读取增量事件；
- 页面不可见时降低频率，操作结束后停止轮询；
- 进程内注册表保存活动操作；
- runtime data root 下保存结构化 JSONL 轮转日志，用于刷新和进程异常后的复盘；
- 默认最多保留 7 天且总量不超过 10 MiB，任一上限先到即清理最旧记录；
- 最近操作接口默认返回 20 条、最大 100 条；日志按事件序号增量读取，不重复返回完整文件。

日志不是 Experience / Fact、任务恢复或业务结果的第二事实源。应用启动时发现上次仍为“进行中”的记录，应收口为“进程中断”，不得永久保留幽灵状态。

### 3.5 状态与时间事实源

后端是操作状态、阶段和耗时的唯一事实源；前端不得依靠定时切换文案猜测阶段。操作状态只使用：

- `RUNNING`；
- `SUCCEEDED`；
- `FAILED`；
- `TIMED_OUT`；
- `INTERRUPTED`。

并发门禁拒绝的请求没有开始业务执行，不得创建成 `RUNNING`；可以记录为一次安全的拒绝事件，并返回真实占用操作的编号、类型和已运行时长。

阶段事件至少区分 `STARTED`、`COMPLETED`、`FAILED`、`ROLLED_BACK`。耗时使用 `time.perf_counter()` 等单调时钟计算；墙上时间只用于展示。系统时钟调整不能产生负耗时、倒序事件或改变阶段结果。

## 4. 统一操作、阶段和日志契约

### 4.1 OperationRecord

每次可观测操作至少保存和返回：

| 字段 | 契约 |
|---|---|
| `operation_id` | 与业务正文无关的 UUID；单次操作唯一 |
| `group_id` | 可选；只关联批量界面操作，不改变子事务边界 |
| `operation_type` | 稳定枚举，不使用任意用户输入 |
| `status` | 上述五种状态之一 |
| `stage_code` / `stage_name` | 稳定机器码与中文阶段名 |
| `resource_type` | `LOCAL_DB`、`LOCAL_FILE`、`LOCAL_CPU`、`LLM` 或 `EMBEDDING` |
| `started_at` / `last_event_at` / `ended_at` | 展示与复盘时间点 |
| `elapsed_ms` / `stage_elapsed_ms` | 后端单调时钟计算的总耗时与当前阶段耗时 |
| `attempt` / `max_attempts` | 仅在底层确有重试契约时记录；无重试时为 1/1 |
| `diagnostic_code` | 稳定失败/异常分类，不包含正文 |
| `safe_counts` / `safe_summary` | 只含白名单计数与结果，不含正文或私有路径 |

完成记录保留按顺序排列的阶段列表。总耗时允许包含框架开销，不要求机械等于阶段耗时之和；无法归入业务阶段的时间明确记为 `unattributed_ms`，不能静默丢失。

### 4.2 结构化日志事件

日志事件至少包含事件序号、时间、级别、组件、操作编号、分组编号、操作类型、阶段码、资源类型、事件码和脱敏消息。循环处理可以记录总数、已处理数、成功数与失败数，但不记录 Experience / Fact 正文。

脱敏必须在写入前按字段白名单完成，不能先写原始日志再由前端替换。以下内容禁止进入 JSONL、API、页面、诊断摘要和测试快照：

- API Key、Authorization、Cookie 和凭据库内容；
- 完整 Prompt、模型完整请求/响应；
- PDF 正文、JD 全文、Experience / Fact 原文；
- 姓名、电话、邮箱、所在地和可能包含身份信息的原始文件名；
- 本机用户名、源码目录、数据库和输出目录绝对路径；
- 未处理的请求体、响应体、异常对象或堆栈。

允许记录安全事件码、稳定组件名、阶段、计数、耗时、异常类型白名单、HTTP/领域错误分类、非敏感模型兼容标识及 Embedding fingerprint/维度。

### 4.3 诊断设施故障

诊断写入失败不得破坏 Experience 事务、生成结果或 DOCX 文件，也不能吞掉原业务异常。进程内状态仍可用时继续服务，并把诊断健康状态置为 `DEGRADED`；文件和内存均不可用时，现有请求按原业务契约完成或失败，同时系统状态明确报告诊断不可用。

不得只打印 warning 后继续向页面声称日志完整。`RESULT.md` 必须分别证明业务成功/失败和诊断完整/降级两种结果。

## 5. 必须覆盖的真实阶段

### 5.1 JD → DOCX

至少映射现有生成服务的真实边界：

1. 迁移检查；
2. Embedding/索引就绪检查；
3. JD 分析；
4. SQL Experience 回读；
5. 第一层 Experience 选择；
6. 第二层 Fact 证据选择；
7. LLM 受约束改写；
8. ResumeDocument 构建与来源校验；
9. DOCX 渲染与版式处理；
10. 输出文件保存；
11. 响应组装与下载就绪。

现有 `GenerationContext` 可以收束为统一机制或适配到统一机制，不能保留一套“仅成功响应可见”的阶段列表和另一套后台阶段列表而产生冲突。最终响应中的阶段耗时与后台同一 `operation_id` 查询结果必须一致。

### 5.2 PDF 提取与 Experience 写入

经历提取至少记录输入校验、LLM 提取等待、结构化结果校验和返回待确认结果。Experience create/update/delete 至少记录：

1. 请求与目标记录校验；
2. 开启数据库事务；
3. Experience 变更；
4. Fact reconciliation；
5. 旧 Embedding 失效或派生状态更新；
6. 事务提交或完整回滚；
7. 最终安全摘要读取。

事务内的“子步骤执行完”不等于数据已成功保存。页面只能在 commit 和最终状态核验后显示成功；回滚时，已经执行的写步骤必须标为 `ROLLED_BACK`，不能继续显示为已完成写入。批量导入保留逐项结果和分组总数，部分失败不得被合并为全部成功。

### 5.3 维护写操作

- 迁移：前置检查、SQLite/旧派生数据备份、应用迁移、后置核验、资源释放；
- Embedding 重建：就绪检查、读取 Fact、模型请求、分批写入、数量/fingerprint/维度核验；
- 失败重试：读取失败项、每次尝试、退避等待、结果提交和系统状态刷新。

若 LLM/Embedding 客户端或适配层已有自动重试，必须显示当前 `attempt/max_attempts`、上次失败分类、退避时长和累计耗时。不得为满足界面而新增未经批准的自动重试，也不得把底层重试隐藏为一段原因不明的等待。

## 6. 五项补充阻断要求

### R1 诊断读取不能随业务一起卡住

`GET` 诊断接口不得获取生成/维护共享门禁，也不得等待正在执行的长事务、模型连接或日志清理锁。受控 Stub 让生成或重建阻塞时，活动状态、增量日志和单操作详情仍须在 1 秒内响应。

如果实际同步实现会阻塞整个 ASGI 服务，开发侧必须调整执行隔离，使诊断读取可用，但不得借机建立后台任务链或改变业务事务边界。只在单元测试中证明 tracker 可读、没有通过真实 API 并发验证，不算完成。

### R2 重试与退避可见

既有重试的次数、失败分类、退避时间和累计耗时进入阶段事件。重试最终成功、耗尽失败、退避期间刷新页面和进程中断均须有不同结果；日志不得记录模型请求正文。

### R3 事务语义准确

Experience 写入的“处理完成、等待提交、已提交、已回滚”必须可区分。任何 reconciliation、Embedding 失效、commit 或最终摘要失败都要按真实事务结果收口，不能用日志先行成功替代数据库后置条件。

### R4 资源类型明确

每个阶段必须标明本地数据库、本地文件、本地计算、LLM 或 Embedding。等待外部调用时显示当前耗时和配置的超时上限；无真实百分比时不显示百分比、剩余时间或伪心跳。

### R5 近期同类耗时对比

后端基于已保留的完成记录，按 `operation_type + stage_code` 计算最近 20 次的样本数、中位数和最大值；样本不足时明确显示，不猜测基线。当前操作完成后，本地系统页可以对比本次值与近期值，帮助判断异常慢。该统计只用于本机 V2 调试，不形成远程监控或长期性能承诺。

## 7. 本地系统页与诊断 API

### 7.1 页面行为

`/system` 增加：

| 区域 | 展示 | 操作 |
|---|---|---|
| 运行活动 | 活动与最近操作、当前阶段、资源类型、总耗时、结果、诊断码 | 查看详情、按类型/结果筛选 |
| 阶段时间线 | 阶段顺序、状态、尝试次数、阶段耗时、近期中位数/最大值 | 选择同类记录对比 |
| 后台日志 | 时间、级别、组件、操作/分组编号、阶段、事件码、脱敏消息 | 增量刷新、筛选 |
| 诊断摘要 | 版本、操作时间线、错误码、索引/诊断健康和安全计数 | 一键复制脱敏摘要 |

清理历史日志需要二次确认，并继续经过现有本地管理写操作安全校验。页面不得接受任意日志路径、任意文件名、任意 SQL 或命令。

### 7.2 固定 API 范围

在现有 `/api/system` 下增加只读诊断接口：

- `GET /api/system/operations`：活动/最近操作，支持固定枚举筛选和有上限的 `limit`；
- `GET /api/system/operations/{operation_id}`：单次操作与完整阶段；
- `GET /api/system/logs`：按事件序号增量读取白名单日志；
- `GET /api/system/diagnostics/{operation_id}`：同一次操作的脱敏诊断摘要；
- `DELETE /api/system/logs`：受保护的历史日志清理。

路径参数必须严格验证 UUID；筛选参数使用白名单和数量上限。API 只返回结构化投影，不能读取或下载任意本地文件。404、日志已轮转、诊断降级和非法参数分别返回稳定错误码。

## 10. 独立源码验收要求

本版本新增跨线程状态、持久化日志、管理读取/清理 API，并触及事务、并发门禁、异常路径和隐私边界，属于高风险结构变更，T8 必须由未参与候选实现、自测或修复的验收 Agent 独立完成。

验收 Agent至少独立复核：

1. tracker、计时和 JSONL 只有一套事实机制，没有生成专用与系统专用双轨；
2. 诊断读取在真实同步长请求期间可响应，不只验证 mock 对象；
3. Experience commit/rollback、迁移 fail-closed 和 Embedding 失败没有因打点改变；
4. 日志写入失败不会破坏业务，也不会被伪装成诊断健康；
5. 日志、API、前端、测试和包内容无凭据、正文、PII、绝对路径或原始堆栈；
6. 读取/清理 API 不提供任意文件、SQL、命令或安全绕过；
7. 刷新、断连、重启、轮转、清理失败和 409 冲突均有负向证据；
8. 版本元数据、前端类型、同源托管和便携启动退出一致；
9. V1.5.0 与 V2.0.0 核心回归通过。

验收结论必须绑定冻结候选 commit，并在 `RESULT.md` 分别写“功能验收”和“结构变更验收”。验收后任何相关源码、测试、配置或构建变化都会使结论失效并需重验。

## 11. RESULT 与开发交接要求

开发 Agent 使用 `version/v2.0.1` 分支，开始前核验基线、分支和工作区；交接时提供：

1. 基线 commit、候选 commit、分支和干净工作区状态；

开发 Agent 不操作公开 `main`、tag 或远端发布。诊断截图、长日志和机读产物放临时目录或 runtime data root，不在版本目录新增第三份文档。

## 12. 完成定义与发布门禁
