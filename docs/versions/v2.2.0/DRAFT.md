## 1. 暂定版本目标

V2.2.0 不再按 V2.1.0 的补丁版本规划，而作为功能与体验升级版本。当前暂定四条主线：

1. 让同一生成任务跨应用内页面切换，并在浏览器页面生命周期变化后保持可识别、可回到、可取消；
2. 让 JD 分析、Fact 召回、经历润色和排版生成成为真实、可回看的渐进过程；
3. 在不降低事实约束和产物质量的前提下，缩短首次有效结果与整份简历生成时间；
4. 修正联系方式、教育字段、技能摘要和 Fact 呈现，使最终简历从“字段错位或内容堆砌”转向准确、
   可扫读、有重点的职业表达。

V2.2.0 仍属于本地 V2 的最后阶段，不为即将由 V3 服务器架构替代的本地应用进程建设完整的崩溃、
关机或后端重启续跑系统。账号、权限、服务器持久任务与跨设备恢复仍属于 V3。

Product Owner 已确认第 4 节范围清单完整并冻结用户目标、可观察结果、明确不做项和既有不变量。
该冻结是目标导向的实施基线，不表示当前技术实现、组件划分或候选路线永远不可改变。Design Snapshot、
当前版本性能基线和流式最小纵切仍须完成；开发前证据任务可以与 Design Agent 并行，但它不构成
产品源码实施授权。只有相应 PLAN Revision 形成并记录批准身份后，Development Agent 才可开始该
Revision 明确授权的产品实施。

## 2. 已确认产品方向

### V220-UX-01 工作台任务连续性与最小生命周期管理

#### 当前问题

用户在工作台上传、解析、填写 JD、生成或查看结果期间切换到“我的经历”或开发者后台，再返回
工作台时，页面重新初始化，当前输入、阶段或生成进度不可见。这破坏任务连续性，也会让用户无法
判断后台任务是否仍在运行。

#### 目标行为

工作台的一次任务会话不能以页面组件挂载周期作为生命周期。应用内路由切换不得影响任务；浏览器
刷新或关闭页面后，只要本地后端仍在运行，也必须重新识别正在执行的 operation，避免用户既看不到
进度、又因后台占用而无法重新开始。

本版本新增上层 `task_id` 作为一次完整生成任务的身份，覆盖身份/JD 草稿、上传与解析、生成
operation、各经历生成子任务、最终 ResumeRevision 及 DOCX/PDF artifact。`operation_id` 继续表示
某次后台操作，但不能再被当作整个工作台任务的唯一身份。

至少覆盖以下状态：

1. 上传后的解析进行中与解析完成状态；
2. 已解析履历、身份摘要和尚未提交或已提交的 JD；
3. 生成进行中的同一 `operation_id`、已完成阶段、当前阶段和各阶段明细；
4. 用户离开期间任务完成时，返回后直接显示该任务的真实结果；
5. 用户离开期间任务失败时，返回后显示原任务的失败位置、保留输入和既有重试入口；
6. 已生成的预览、事实依据选择状态和 Word/PDF 下载入口，直到用户明确开始新任务；
7. 浏览器刷新或重新打开页面后，恢复同一 `task_id` 已保存的未提交身份/JD 草稿、后台 operation、
   真实进度或终态，并提供明确的等待/返回与取消入口。

#### 行为约束

- 路由切换不得取消、重新提交或复制后台任务，也不得触发第二次 LLM/API 调用；
- 返回工作台后的轮询、事件流恢复或状态查询必须继续绑定原 `task_id` 及其 operation，具备幂等、
  revision 隔离和去重边界；
- 已完成阶段和历史明细继续可点击回看，当前阶段继续显示最新真实事件；
- 只有用户明确执行“开始新任务”或等价重置操作，才清空当前工作台任务；普通导航不得隐式重置；
- “取消生成”必须由用户显式触发并由后端确认；页面刷新、关闭或事件连接断开不得被当作可靠取消
  信号。取消必须停止本系统内尚未开始的经历队列、关闭正在读取的模型流、终止本任务拥有的 Word
  转换子进程、停止发布新事件/Fact/artifact，并以 task/revision fence 丢弃迟到结果；
- 后端确认本地任务已进入不可继续发布结果的取消状态后，立即释放活动任务位置并允许用户开始新
  任务。系统可以关闭对模型 Provider 的连接，但不得承诺第三方一定立即停止其内部计算或计费；
- 不得为了页面恢复把 API Key、完整履历、完整 JD 或生成正文新增写入不受控的浏览器长期存储；
- 状态承载方式、前端状态库和组件拆分由 Development Agent 设计，但验收以外部行为为准。

#### 任务草稿与输入 revision

V2.2.0 使用后端临时任务记录作为工作台状态真源，不使用 `localStorage`/IndexedDB 保存完整联系方式、
JD 或生成正文：

1. 用户开始填写后建立 `DRAFT` 状态的 `task_id`；姓名、联系方式和 JD 以防抖、失焦和提交前强制
   flush 的方式保存，并显示“保存中/已保存”；
2. 显示“已保存”的字段在浏览器刷新或页面重开后必须恢复；处于“保存中”且浏览器被强制关闭时，
   只允许丢失尚未被后端确认的最后修改，不得把未确认内容显示为已保存；
3. 点击生成时原子冻结当前 `input_revision`。后台所有阶段、经历子任务和最终 artifact 只读取该
   revision，后续迟到的草稿写入不能改变正在生成的输入；
4. 用户明确开始新任务时创建新 `task_id`，姓名、电话、邮箱、所在地和 JD 重新为空，不自动复用
   上一任务；开始新任务只切换工作台任务，不删除“我的简历”中已经发布的最终简历和 artifact；
5. 当前后端仍在运行时，活动中的 `DRAFT/RUNNING` 不得被定时清除；超过 24 小时没有后端确认修改
   的未提交草稿，以及进入 `FAILED/CANCELLED` 后超过 24 小时的临时任务状态可以清理；成功任务的
   工作台状态保留到用户开始新任务，最终简历继续按“我的简历”规则保存；
6. 提供“清除当前草稿”入口；清理临时任务不得级联删除已发布的 ResumeRevision、DOCX 或 PDF。
   临时任务的物理容量上限由正式 PLAN 根据冻结 schema 与容量估算确定，不得通过静默删除当前活动
   任务来满足限额；
7. V2 本地实现可使用本地数据库承载临时任务；V3 在相同任务模型上增加 `owner_user_id`、认证授权、
   服务端数据库与正式保留策略。V2.2.0 不承诺后端进程退出后的运行任务续跑；若本地记录恰好仍在，
   也只能作为尽力恢复，不能把中断任务伪装成仍在运行。

#### 正向验收

对解析中、JD 已填写、生成中、生成完成、生成失败五类状态分别执行：

~~~text
进入工作台并建立当前任务
→ 记录任务/operation 身份、输入、当前阶段和已有明细
→ 切换到“我的经历”
→ 返回工作台
→ 再切换到开发者后台
→ 返回工作台
~~~

每次返回都必须保持同一任务身份、输入、阶段、明细和结果；后台调用次数不得增加。任务在用户
离开期间继续推进时，返回后应补齐真实进度，不得倒退、伪造或重新开始。

另对未提交草稿执行：填写身份和 JD → 等待页面显示“已保存” → 刷新 → 核对同一 `task_id`、字段及
`input_revision`；随后修改字段但在“保存中”强制刷新，页面不得谎称未确认修改已经保存。

#### 反向验收

- 路由往返后出现初始欢迎页、空白 JD、阶段归零或结果丢失，失败；
- 同一用户操作产生第二个 operation、重复上传、重复生成或额外模型计费，失败；
- 已完成任务因轮询重连退回“生成中”，或失败任务被静默清空，失败；
- 刷新后已确认保存的身份/JD丢失、恢复到错误 revision，或旧任务迟到结果覆盖新任务，失败；
- 取消后旧任务仍能发布 Fact/artifact、继续占用唯一任务位置，或阻止用户立即开始新任务，失败；
- 单纯依赖页面不卸载、隐藏组件或写死 Mock 规避状态恢复，失败；
- 通过 `localStorage` 等长期保存敏感完整正文，却没有明确数据边界和清理规则，失败。

#### 当前范围边界

本项只要求前端页面生命周期内的任务重新识别，不建设本地进程级断点续跑。以下能力当前明确不做，
后续可重新评估，但不得在正式 PLAN 中自动扩大范围：

- 关闭整个 ResumeAssistant 或后端进程后恢复未完成任务；
- 应用崩溃、操作系统重启或设备关机后的断点续跑；
- 同时保留或运行多个生成任务；
- 在其他页面增加全局悬浮进度条、通知或后台任务中心。

若现有持久状态可能在后端重启后留下永久 `RUNNING` 锁，开发只需提供不会永久阻塞用户的最低限度
失效清理；这不等于实现任务恢复。

### V220-STREAM-01 四阶段渐进输出与历史回看

本版本确认使用 SSE 传输真实生成增量，并以“任务状态优先”而不是“保存全部事件”恢复页面。SSE 是
观察通道，后端临时 `GenerationTask` 及其阶段/结果快照才是任务真源：

| 阶段 | 面向用户的渐进结果 |
|---|---|
| P1 JD 分析 | 岗位、职责、硬性要求与加分项按已经完成并通过结构校验的条目逐项出现 |
| P2 Fact 召回 | 被选中的经历与 Fact 按检索/筛选完成顺序出现，同时给出可解释的匹配依据 |
| P3 经历润色 | 完整 Fact 校验通过后一次写入生成中预览；选择该 Fact 的理由在旁侧逐字渐进显示 |
| P4 排版与产物 | 只展示 Word 构建、Word→PDF、锚点与产物发布等真实步骤和耗时，不伪造内容流 |

- 当前阶段变化时，右侧切换到新阶段；旧阶段的最终产品化结果必须保存，用户可点击左侧阶段重新
  查看，但不要求重播当时的逐字动画；
- 每个 SSE 增量必须绑定 `task_id`、`operation_id`、阶段、单调 `seq` 及适用的
  `experience_id`/`fact_id`，重复接收不得重复写入界面；
- 后端持久化任务业务状态、阶段状态、已完成 JD条目、SelectedEvidence、完整 Fact、最终选择理由、
  失败/取消信息和 artifact 身份；这些是恢复与最终结果真源，不是诊断日志；
- 正在逐字显示的产品化理由只维护一份覆盖式 `display_snapshot`，按有界时间/字符间隔更新并在 Fact
  完成后替换为最终结构化结果；不得为每个字符新增数据库记录；
- 单个字符/token delta 只通过 SSE 发送，不长期持久化。不得存储或展示模型私有思维链；“选择理由”
  必须是面向用户、可由事实与 JD 支持的产品解释；
- 页面离开或 SSE 断开不取消后台任务。重新连接时先获取当前任务权威快照，再从最新 `seq` 继续；
  若发现序号缺口，重新获取快照而不是猜测或拼接缺失字符，也不得重新调用模型；
- 任务重置和保留期限到达后清理临时显示快照；完整 JD、简历正文和逐字 delta 不得复制到普通运行
  日志或浏览器长期存储；
- “流式”必须区分真实上游增量、后端阶段事件和前端逐字呈现。正式 PLAN 必须声明每一种信息的真实
  来源，禁止把任务完成后播放的动画伪装成模型正在实时生成；
- 生成中的 HTML 使用与当前固定 Word 模板相同的内容层级和近似视觉骨架，完整 Fact 校验通过后
  逐条写入；它只承担结构化过程预览，不承诺与 Word/PDF 的逐行换行、分页或像素完全一致，也不得
  被标为最终成品；
- 最终产物真源仍是 ResumeDocument→DOCX→Microsoft Word COM→PDF。P4 发布成功后，前端切换到
  真实 PDF artifact 作为最终预览与下载来源；不得恢复独立手绘 PDF 或把 HTML 转成第二份 PDF。

### V220-PERF-01 按经历并行生成与真实性能优化

P3 以经历而不是单条 Fact 作为并行边界。例如两个不同实习，或实习与项目，可以并行生成；同一经历
内的 Fact 保持共享上下文，不在本版本继续拆成相互独立的并发请求。

确认采用以下执行模型：

1. P1 完成 JD 结构化，P2 按 `experience_id` 对入选 Fact 分组；
2. P3 建立有界经历队列，V2.2.0 默认最多同时处理 2 个经历；本版本不因单次测试较快自动提高到 3；
3. 每个经历任务只接收紧凑 JD 摘要、统一风格约束和该经历的入选 Fact；完成顺序不改变模板中的最终
   经历顺序；
4. 一个经历失败、超时或用户要求重试时，只重试该经历，不重复已经完成的其他经历；
5. 幂等边界改为“每个 `operation_id + experience_id + input_revision + prompt/model version` 恰好
   一个逻辑生成任务”。V2.1.0 的“整份简历一次 rewrite/provider 请求”不再直接作为 V2.2.0 门禁；
6. 同一经历内可逐个提交已经完成并校验的 Fact，同时持续输出对应选择理由；全部经历完成后再统一
   组装 Word/PDF；任一必要经历未完成时不得把部分结果伪装成完整最终简历；
7. 所有经历任务共享同一份 JD 摘要、事实约束和风格规范；默认不增加一次“全简历统一润色”模型
   调用，先用结构化输出与确定性规范保证风格一致，只有真实质量证据证明仍不满足时才重新提案；
8. Provider 正常调用计数改为“1 次 JD 分析＋N 个入选经历生成请求”。只有可重试失败或用户显式
   重试可以增加尝试次数；每次逻辑请求、HTTP attempt、Token 和费用必须分开计数。

性能优化不能只靠流式动画。正式 PLAN 至少要覆盖：缩减传入模型的 JD/履历上下文、避免重复分析和
Embedding、可重建派生索引缓存、经历级有界并发、单经历失败隔离，以及 Word/PDF 本地阶段的真实
耗时。缓存不得跨用户泄露数据，也不得让旧 revision 覆盖新任务。

最近一次 V2.1.0 真实 E2E 可作为待复测参考：P1 约 24.1 秒、P2 约 0.2 秒、P3 约 39.1 秒、P4
约 12.6 秒、总计约 76.0 秒。该单次数据不是 V2.2.0 冻结基线。

正式 PLAN 按以下方法建立真实性能基线：

1. 使用短、典型、长三组固定脱敏履历/JD，在同一机器、同一网络区域、同一模型和同一配置下测试；
2. 冷启动与热启动分开，每组至少完成 3 次真实模型主链，报告中位数和最大值；样本量不足时不得把
   最大值或单次结果包装成 P95；
3. 分别记录首个真实状态、首个 JD 条目、首个召回 Fact、首个完成 Fact、P1～P4、总耗时、经历
   排队时间、每个 Provider 请求延迟、逻辑调用/HTTP attempt、Token/费用、重试与取消收敛时间；
4. 使用确定性 fixture 做高频性能回归，真实模型样例负责验证端到端收益，二者不得互相替代；
5. 优化顺序固定为删除重复工作与缓存失效 → 缩减无关上下文 → 经历级有界并行 → 模型/参数对照 →
   本地 Word/PDF 冷启动；不得先靠降低内容量、跳过事实校验或更换低质量模型换取数字；
6. 同时冻结事实不虚构、必要经历覆盖、标题/正文/依据一致、经历间文风一致和最终 artifact 质量门禁。

当前候选目标仍为：真实状态反馈不晚于 1 秒、首个完成 Fact 不晚于 15 秒、同样例总耗时中位数相对
V2.1.0 降低至少 25%。这些数字必须在基线实验后由 Product Owner 随正式 PLAN 一并批准，现阶段不
冒充已经证实可达的硬门禁。

### V220-TECH-01 流式路线先证伪再扩展

正式开发不得先铺开全部页面再验证流式协议。第一条真实纵切必须先证明：目标模型支持所需增量响应，
经历/Fact/理由边界可稳定解析，任务状态、完成结果和当前展示快照能够恢复，SSE 增量带有可去重的
顺序号且序号缺口会触发权威快照重取，并行任务不会重复计费或交叉覆盖。逐字/逐 token 增量本身不作为
必须持久化或逐条补发的业务记录。
若单次结构化流无法可靠产生可消费事件，应在预先规定的最迟决策点切换为经历级分批返回或缩小实时
粒度，不得用前端假动画掩盖路线失败。

### V220-CONTENT-01 联系方式必须确定性进入最终简历

当前真实生成结果出现“用户已有联系方式，但最终简历未显示”的问题。现阶段不预判是模板占位、
ResumeDocument 填充、字段映射还是 Word/PDF 投影问题；正式 PLAN 必须先沿真实数据链定位断点，再
选择修复位置，不能只在最终页面硬补文字。

- 姓名、电话、邮箱、所在地等直接身份字段的唯一来源是生成简历前“身份摘要”表单中的用户显式
  输入；姓名必填，其他字段选填，均不经过 LLM 推断、补全或改写；
- V2.2.0 不建立持久化个人 Profile，也不从上传简历、履历库、上一生成任务、模板或 AI 自动回填。
  每个新 `task_id` 均要求重新填写；同一任务内按 V220-UX-01 的临时草稿规则保存和恢复；
- 点击生成时冻结的身份字段必须从该任务 `input_revision` 确定性进入 ResumeDocument、DOCX、
  Word 转换后的 PDF、
  最终预览和下载文件，各端内容一致；
- 确实缺失的字段保持为空，不得伪造；页面应在生成前给出可理解的缺失提示，模板不得留下空标签、
  多余分隔符或错位占位；
- 验收必须使用包含姓名、电话、邮箱和所在地的固定脱敏样例，对输入、结构化文档、DOCX、PDF 与
  viewer 逐字段核对；任一已确认联系方式在后续链路丢失均为阻断问题。

### V220-CONTENT-02 技能区从关键词堆砌改为岗位相关能力摘要

当前技能区使用“技术/产品/其他”等粗分类，并把大量关键词和项目内部实现术语直接堆入简历，信息
虽然多，但缺乏优先级、证据边界和候选人的职业表达。V2.2.0 应把技能区改为有限、可读、与目标岗位
相关的能力摘要，而不是检索命中词或系统标签的转储。

- 技能必须来自用户事实、已确认经历或可由事实直接支持的能力，不得仅因 JD 出现某个词就写入；
- 按目标岗位动态选择有意义的 2～4 类，例如产品与研究、数据与实验、工具与技术、业务/行业能力；
  没有事实支持的分类直接省略，不强行凑满；
- 每类内部按 JD 相关性和证据强度排序，合并同义项、删除重复项，并控制为容易扫读的短语；
- `Experience / Fact 两层选材`、`fact_refs`、内部状态机、受约束生成机制等系统实现名不得作为候选人
  技能直接出现，除非用户事实明确证明其本身就是候选人的工作成果且已转换为行业通用表达；
- 信息量应高于当前的简单标签，但不能靠扩大“其他”栏堆满页面。正式设计需同时验证普通内容、
  技能很多、技能很少和目标岗位变化后的分组、换行、留白与一页简历效果；
- 生成结构应保留“技能分类—技能项—事实依据”映射，最终简历只展示简洁分类和技能项，依据用于
  质量检查与后续解释，不直接把内部引用标识输出给用户。

### V220-CONTENT-03 每条润色 Fact 使用结构化加粗小标题

每条进入简历的润色 Fact 应呈现为“加粗小标题＋正文”，例如：

~~~text
● 需求分析：访谈目标用户并整理核心场景，形成需求优先级与原型方案……
~~~

其中“需求分析：”加粗，后续正文使用常规字重。该要求不是在生成文本前拼接 Markdown，而是把每条
Fact 的展示结果建模为至少包含 `headline` 与 `body` 的结构化字段：

- 每条入选 Fact 都生成一个简短、可扫读、能概括该条贡献类型的小标题，通常为 2～8 个中文字或
  等价长度；
- 小标题只概括原 Fact，不得新增事实、夸大职责或用空泛标题代替具体内容；同一经历内应避免所有
  条目重复使用“项目成果”“工作内容”等无区分度标题；
- 流式生成时，只有 `headline + body` 均完成事实校验后，整条 Fact 才一次写入简历预览；旁侧选择
  理由仍可独立逐字呈现；
- `headline`、`body`、技能分类和选择理由均属于当前 JD 下的 ResumeRevision/ResumeDocument 输出，
  不回写、不替换职业经历库中的原始 Experience/Fact；Career Memory 继续保持用户确认事实真源；
- HTML 生成中预览、ResumeDocument、DOCX、Word 转换 PDF 与最终 viewer 必须保持相同标题和正文；
  Word/PDF 只加粗标题及其冒号，不得把整条正文一起加粗，也不得出现 Markdown 标记；
- 标题会增加行宽和换行压力，性能与版式验证必须覆盖长短 Fact、中文/英文/数字混排及临界换行，
  不能以删除事实或缩小到不可读字号作为默认解决方案。

### V220-CONTENT-04 教育经历字段必须按语义规范化

当前最终简历出现 `本科（）`，而部分履历库原始内容实际为 `（本科）`。这表明学历、专业或组合展示
字段可能在抽取、存储、ResumeDocument 映射或模板渲染阶段被错误拆分。正式 PLAN 必须先确认真实
字段和值经过了哪条路径，不得只在模板中针对当前截图删除括号。

- 学校、专业、学历/学位、起止时间必须保持独立语义；已经带括号的 `（本科）`、`(本科)` 等值不得
  被当作专业后再额外拼接一个空学历槽；
- 展示组合暂按以下规则冻结，后续 Design Snapshot 若调整位置，可以改变布局但不能改变字段语义：

| 专业 | 学历 | 展示内容 |
|---|---|---|
| 有 | 有 | `专业（学历）` |
| 无 | 有 | `（学历）` |
| 有 | 无 | `专业` |
| 无 | 无 | 整个组合字段不显示 |

- 禁止输出空括号、重复括号、半角/全角混搭、仅有分隔符的占位，以及 `本科（）` 这类字段错位结果；
- 若现有履历把组合文本错误存入专业或其他字段，应在保留原始来源的前提下定义兼容读取或迁移规则，
  不得静默覆盖用户原始材料；
- 验收至少覆盖 `计算机科学与技术＋本科`、仅 `（本科）`、仅专业、两者为空、半角括号、首尾空格及
  历史异常数据，并逐项核对履历库、ResumeDocument、DOCX、PDF 和最终预览一致。

## 3. V2.2.0 起试行的提速与防误放行工作流

### 3.1 适用目标与并行边界

V2.2.0 开始试行“工作可以并行，事实合并与门禁转换串行”的工作方式。但结合当前仓库规模、
前后端耦合度和候选恢复成本，**暂不启用多个 Development Agent 并行修改产品源码**。默认仍由
一个 Development Integrator 负责本版本源码、测试、集成和候选冻结；它仍属于 Development Agent，
不得兼任独立 Acceptance Agent。

当前允许的并行仅限：

- Design Agent 持续推进未来设计，Documentation Agent 同时维护下一版本需求草稿；
- 同一开发工作树中互不写入同一资源的机器任务并发执行，例如 Python 回归、前端 build、PDF
  fixture 和独立端口的浏览器场景；
- 候选冻结后，由满足独立性的多个 Acceptance Agent 在各自临时副本和隔离 runtime 中分项验收；
  若当前仍只使用一个 Acceptance Agent，则按相同分项顺序执行，不改变 Gate；
- 最终源码集成、完整候选验证、候选 SHA 冻结、文档放行、人工验收和发布决定保持串行。

未来是否启用多个 Development Agent，必须根据 V2.2.0 实际交付数据另行决定，不因“可以并行”
自动扩张角色数量。

### 3.2 强制状态机

版本工作不再使用笼统的“开发完成”，而按以下单向状态推进：

~~~text
IMPLEMENTING
→ DEV_VERIFYING
→ DEV_VERIFIED
→ FROZEN
→ DOC_ALIGNED
→ INDEPENDENT_ACCEPTED
→ HUMAN_ACCEPTED
→ RELEASED
~~~

- `IMPLEMENTING`：源码、测试或 runner 仍可能修改；
- `DEV_VERIFYING`：实现已基本完成，但仍有开发侧强制验证未结束；
- `DEV_VERIFIED`：PLAN 要求的开发侧必做项目全部得到 PASS 终态；
- `FROZEN`：形成 clean、不可变的源码候选 commit；
- `DOC_ALIGNED`：Documentation Agent 在机械前置检查通过后，只依据 PLAN、RESULT、机械身份和
  证据入口完成 RESULT 语义交付审查，确认开发在 RESULT 中声明的理解、交付、范围、技术路线、
  偏差和开发证据摘要相互一致；它只表示可以进入独立验收，不表示实现已经被证明正确；
- `INDEPENDENT_ACCEPTED`：未参与实现、自测或修复的 Acceptance Agent 对同一候选独立通过；
- `HUMAN_ACCEPTED`：Product Owner 使用同一候选完成人工产品验收；
- `RELEASED`：文档收口、远端核对和发布完成。

任何源码、测试、runner、依赖、配置或构建文件修改都会使当前验证失效，状态至少退回
`IMPLEMENTING`；不得在旧候选名称下继续补丁。后台任务尚未结束、日志为空或缺少退出码时，状态
只能是 `DEV_VERIFYING`，不得写成 `DEV_VERIFIED`、`FROZEN` 或“已完成”。

### 3.3 三档验证

#### 快速档：开发内循环

每次相关修改后只运行受影响的快速集合，目标是尽早发现编译、契约和明显回归问题：

- 类型/语法检查、相关单元测试和定向 fixture；
- frontend build、Hooks lint 和受影响页面 smoke；
- runner 自检、服务 readiness 与一个最小浏览器场景；
- 修改模块对应的正向、反向和失败路径。

快速档不产生发布候选，也不要求每次重建 onedir。

#### 集成档：冻结候选前

准备形成候选时一次性完成当前 PLAN 的全部开发门禁：

- 完整统一预检和固定计数；
- 全部浏览器场景矩阵；
- 与改动相关的 API、状态、PDF/Word、视觉、三视口和错误注入矩阵；
- clean production build、最终 onedir 重建与包内资产/hash 验证；
- RESULT 中每个必做项目都有命令、退出码、PASS/FAIL、候选输入和偏差。

只有集成档全部通过，才能进入 `DEV_VERIFIED` 并分配正式候选编号。

#### 发布档：独立复验与人工验收

Acceptance Agent 绑定同一冻结候选，独立复跑 PLAN 指定的高风险、集成、失败和包门禁；它复核
开发已经完成的工作，不替开发补跑缺失项目。随后 Product Owner 使用同一候选执行完整人工流程。

### 3.4 早期人工结构检查与全状态展台

涉及界面和流程的版本在完整业务接通前增加一次**非正式早期检查**：Development Agent 先完成
页面框架、关键布局和主要状态映射，提供可点击 Preview；Product Owner 只确认结构方向、布局、
滚动、固定区域、信息取舍和对冻结设计的还原，不在此时宣称功能验收通过，也不因检查本身解冻
Design Baseline。

开发测试环境应使用无真实数据、无真实 Key、不会进入正式包的 fixture 展台快速切换主要状态，
至少覆盖适用的初始、加载、进行中、完成、失败、空数据、超长内容和恢复状态。Product Owner 每轮
尽量走查全部可达页面后集中反馈，避免只发现一个问题就结束整轮；P0 白屏或流程完全不可达除外。

### 3.5 候选冻结与命名

开发过程只使用 `working/rN` 或普通开发提交，不提前占用 H 编号。正式 `Hn-SRC` 仅在以下条件全部
满足后产生：

1. PLAN 强制开发任务全部完成；
2. 所有必跑矩阵已经结束且成功；
3. 后台任务数为 0；
4. 不存在“待运行、后台执行中、未执行、交给验收补跑、环境限制跳过或 SUSPEND”；
5. runner 已在干净 checkout 按文档入口完成 smoke 和规定矩阵；
6. 最终 onedir 已从同一 clean 源码构建并完成包验证；
7. RESULT 如实记录证据和偏差；
8. 工作树 clean，冻结后不再修改源码、测试或构建输入。

冻结后的任何相关修改形成新的候选编号；产品字节未变但测试/runner 改变时同样适用。仅修改授权
文档的开发交接提交可以晚于 `Hn-SRC`，但必须通过精确路径 diff 证明没有改变被验收源码。

### 3.6 runner 与“环境限制”协议

runner 本身属于需验证的测试代码。涉及本地服务或浏览器时必须：

1. 从仓库根按文档命令启动，并自行解析仓库与 `frontend` 等工作目录；
2. 捕获子进程 stdout/stderr 和退出码；
3. 先检查进程是否提前退出，再进行端口和 HTTP readiness；
4. readiness 成功后才启动浏览器场景，失败应快速输出根因，不能累计无意义的长超时；
5. 使用动态或显式隔离端口，结束时终止全部子进程并验证无残留；
6. 先通过 harness smoke，再运行完整矩阵。

Agent 只有提供原始命令、stdout/stderr、进程状态、端口、HTTP readiness、独立启动对照、最小复现
和清理结果后，才能把失败归类为环境限制。即使方案 A 的一次全量连跑受真实环境影响，逐场景
方案 B 仍由原 Development Agent 完成；执行方式可以替换，责任不能转移给 Acceptance Agent。

### 3.7 变更影响矩阵与缓存边界

正式 PLAN 应为每类修改指定开发内循环的最小受影响测试集合，例如 CSS、React 状态、API、PDF
Renderer、runner、打包或数据迁移分别执行相应定向门禁；最终候选仍执行 PLAN 规定的完整集成档。

测试必须隔离 runtime、数据库、输入输出、日志、artifact、端口、`.env` 和凭据。依赖下载缓存、
Python wheel、npm cache、浏览器二进制和按 lockfile/hash 管理的构建缓存可以复用，不要求为了隔离
业务数据而反复下载相同依赖。

### 3.8 强制反思、互相纠错与技术路线挑战

V2.2.0 起，反思不再依赖 Agent 在执行主线时“顺便想到”，而作为有时间、输入、输出和阻断权的
正式任务。流程冻结的是 Product Owner 已确认的产品目标和不变量；未经真实证据证明的技术路线只
能标记为暂定方案，不因写入 PLAN、用户批准或开发已经投入时间而自动成为不可推翻的事实。

#### 3.8.1 明确主责，同时允许所有角色挑战

- Product Owner 对产品目标、优先级、可接受偏差和发布决定主责；其批准表示基于已披露风险作出
  决定，不替其他角色承担未披露的技术风险；
- Documentation Agent 对原始需求保真、目标/方案/风险/验收可追溯和门禁状态主责；不得擅自把
  “结果必须成立”降级成“沿用某种实现尽量逼近”；
- Development Agent 对技术路线能否实现已冻结目标主责；发现当前方案不能从机制上保证结果时，
  必须停止局部修补并提出路线挑战，不得以“PLAN 已指定”为由继续声明完成；
- Design Agent 发现实现约束将破坏已批准体验时可以提出设计偏差或路线风险；
- Acceptance Agent 对独立证伪主责；必须寻找“测试通过但用户目标仍失败”的路径，可以否决候选并
  要求重开技术路线，但不得代替 Development Agent 实现或补跑其缺失工作。

任何角色均有指出问题和触发暂停的权利与义务，但“所有人可挑战”不等于“无人主责”。问题提出后，
Documentation Agent 负责登记，技术可行性由 Development Agent 给出证据，涉及产品取舍或扩大范围
时由 Product Owner 决定，Acceptance Agent 对修正后的同一候选重新验证。

#### 3.8.2 执行与反思分离

同一个 Agent 不得被要求一边持续实现、一边自行保持发散反思。每个高风险任务至少设置三个显式
暂停点，并把 Agent 从“完成方案”切换为“尝试证明方案会失败”：

1. **开发前 Pre-mortem**：假设版本最终失败，列出最可能的三个原因、每项最小证伪实验、最迟决策
   时间和失败替代方案；
2. **第一条真实纵切后的 Architecture Check**：暂停继续扩展，使用真实或代表性真实路径检查架构
   是否兑现产品不变量，是否存在双真源、只能调参逼近或 fixture 与真实结果冲突；
3. **冻结候选前 Falsification Check**：不再补充正向完成证明，集中寻找仍会失败的真实路径、代理
   指标、缺失负向和 Product Owner 最可能打回的结果。

反思回合默认只读，不修改源码。提示必须明确“当前不要继续原计划；唯一任务是寻找当前路线无法达到
产品目标的证据”。同一 Agent 可以在独立回合执行；P0/P1、架构、隐私、迁移、artifact 真源等高风险
事项可由新的只读 Review/Acceptance 任务顺序复核，但这不授权多个 Development Agent 并行改源码。

#### 3.8.3 有边界的反思问题

每次反思必须逐项回答，避免无限发散或只写“注意风险”的套话：

1. 用户真正要求、不能被实现细节替代的不变量是什么？
2. 当前方案依赖的最弱且尚未证实的假设是什么？
3. 在什么情况下所有现有测试都通过，用户仍会判定失败？
4. 当前证据是在验证最终用户结果，还是只验证中间指标/内部 fixture？
5. 是否存在更简单、能够从机制上保证结果的路线？
6. 出现什么证据必须停止、降级或切换路线？

有效反思至少给出一个可信失败模式和对应证伪方法。“未发现风险”“测试全过”或重复开发结论不算完成，
不能解除反思门禁。

#### 3.8.4 假设台账与证据优先级

正式 PLAN 对关键技术判断至少标记一种状态：

- `UNKNOWN`：尚未验证；
- `ASSUMPTION`：暂按该假设推进，已写明证伪实验和失败预案；
- `EVIDENCED`：已由可寻址真实证据支持；
- `REJECTED`：证据已经推翻，不得继续作为实现基础。

每个高风险假设必须记录：产品不变量、当前路线、为何可能失败、最小实验、完成期限、责任角色和回退
路线。未经验证的判断不得因为进入 PLAN 就改写为 `EVIDENCED`。

冲突证据按以下顺序裁决：

1. Product Owner 的真实操作路径与真实输出；
2. 最终 onedir/目标部署环境产生的真实 artifact；
3. 脱敏后的代表性真实样例；
4. 完整链路 fixture；
5. 单元测试、源码检查和局部技术指标。

高层证据失败时，低层 PASS 数量不能覆盖失败。例如真实 Word/PDF 明显不一致时，内部坐标、画布尺寸、
固定计数或 fixture 全绿均不能单独关闭问题。

#### 3.8.5 Architecture Challenge 与 Stop-the-line

出现以下任一情况，发现者必须登记 `Architecture Challenge`，当前工作进入 `CHALLENGE_OPEN`：

- 当前技术路线无法从机制上保证产品不变量，只能反复调参逼近；
- P0/P1 修复一次后仍在真实路径复现，或 Product Owner 第二次指出同一根问题；
- 真实 artifact/最终包推翻 fixture、源码检查或开发自测结论；
- 同一结果出现两个可能漂移的真源、Renderer、状态源或 artifact；
- 为继续原路线开始增加大量特殊常量、坐标、条件分支或静默回退；
- “环境限制”准备替代根因定位，或 Development 工作准备移交 Acceptance 补做；
- 技术依赖、隐私边界、成本或工期相对批准时发生实质变化。

Challenge 至少记录：原始用户反馈、受影响不变量、最小复现、当前方案不能保证结果的原因、继续修补
风险、候选替代方案和建议决定。P0/P1、架构真源、数据安全或不可逆变更适用 stop-the-line：任何角色
可以暂停后续门禁，无需先实现替代方案。

`CHALLENGE_OPEN` 是对 §3.2 状态机的阻断态，可从 `IMPLEMENTING` 至 `HUMAN_ACCEPTED` 前任一阶段
进入；进入后不得推进、冻结或沿用旧候选编号。它只允许通过以下一种方式关闭：

1. 新证据证明原路线能够保证目标；
2. 修改或替换技术路线并退回 `IMPLEMENTING`；
3. Product Owner 在风险、用户影响和替代方案全部披露后，明确批准缩小目标或接受限制。

关闭记录必须包含决策人与证据；沉默、继续编码、已有投入、时间紧迫或测试数量不能自动关闭 Challenge。

#### 3.8.6 原始反馈与闭环追踪

P0/P1、技术路线推翻、同类问题重复发生、候选或包身份错误、路径/工作区事故、跨角色职责错误，
以及能够提炼出跨版本规则的问题，必须建立闭环记录。普通、一次性且已经由测试覆盖的 Bug 不单独
扩张历史档案。闭环至少包含：

| 字段 | 要求 |
|---|---|
| 用户原话 | 保留原始结果描述，不先改写成技术任务 |
| 症状 | 当前可观察到的错误 |
| 产品不变量 | 修复后必须始终成立的结果 |
| 当前架构与假设 | 哪些环节被认为能够保证该结果 |
| 真实复现材料 | 操作路径、输入、截图、日志和实际 artifact |
| 修复/替代路线 | 为什么能够保证不变量 |
| 正向与反证 | 既证明正常，也尝试推翻方案 |
| 最终判定 | Development、Documentation、Acceptance、Product Owner 各自结论 |

任何角色交接时都必须沿此记录回看用户原话。技术测试不能只覆盖文档 Agent 转写后的子问题；真实问题
仍未满足时，子任务完成不等于 Bug 关闭。

#### 3.8.7 时间预算与紧急任务

普通版本默认预留约 10% 时间用于开发前风险验证、10% 用于真实纵切后的架构复查、5% 用于冻结前
反证检查。具体比例可按风险调整，但 PLAN 不得把反思时间隐含为“有空再做”。

紧急演示或热修可以缩短反思，但不能删除：至少执行 5 分钟 Pre-mortem、一个最高风险最小探针、一次
真实主路径和冻结前 5 分钟反证，并设置硬停止/回退时间。紧急包只能按其真实门禁命名，不得用时间
压力把 `ASSUMPTION` 改成 `EVIDENCED` 或冒充正式发布候选。

### 3.9 开发交付与 RESULT 语义审查

#### 3.9.1 开发前冻结 RESULT Delivery Contract

V2.2.0 正式 PLAN 必须在 Product Owner 批准、Development Agent 开始实现之前，包含一份本版本
`RESULT Delivery Contract`。它至少列出：本版本全部 PLAN ID、每项用户结果、开发必须解释的理解
要点、强制开发 Gate、证据摘要字段、候选与最终包身份字段、已知偏差格式，以及“待独立验收问题”
模板。Documentation Agent 后续只能依据这份合同检查 RESULT，不得在开发声称完成后临时增加交付
栏目或把新的源码验收发现倒推成开发原本应写的文档要求。若新增要求会改变强制交付合同，按 PLAN
Revision 处理。

#### 3.9.2 RESULT 当前门禁摘要与交付映射

V2.2.0 的 RESULT 顶部必须维护唯一的当前门禁摘要，至少包括：

~~~yaml
Current Phase: DEV_VERIFYING
Working Commit: <sha-or-uncommitted>
Frozen Candidate: NONE
Plan Blob: <sha>
Mandatory Dev Gates:
  fast_checks: PASS
  integration_precheck: NOT_RUN
  browser_matrix: RUNNING
  final_onedir: NOT_RUN
Ready For Review: NO
Blocking Reason: browser_matrix 尚未完成
~~~

开发 Agent 只有在所有由开发负责的强制 Gate 已得出终态、最终包和候选身份已经冻结、工作区 clean
时，才可把 `Ready For Review` 改为 `YES`。只要存在未执行、运行中、缺退出码、以环境限制跳过或
准备交给验收补跑的强制项，状态仍是 `DEV_VERIFYING`，固定 review 不移动，也不得使用“开发完成”
作为交接标题。

正式交付必须在 RESULT 提供完整映射表，而不是只列提交和测试总数：

| PLAN ID | 用户要求/产品结果 | 开发理解 | 实际交付 | 可复核证据 | 已知偏差 |
|---|---|---|---|---|---|
| `<id>` | `<用户最终看到或依赖的结果>` | `<开发采用的行为解释>` | `<代码/页面/包中的实际状态>` | `<命令、artifact 或截图入口>` | `<无，或明确差异>` |

RESULT 还必须单列“待独立验收问题”，记录哪些完成声明需要验收 Agent 从源码、失败路径、原始运行
证据或最终包中确认。这里记录的是独立真实性问题，不得把开发尚未执行的强制自测、构建、包验证或
缺失的开发证据转交验收补跑。

| 验收问题 ID | PLAN ID | 待核实声明 | 为什么必须独立核实 | 建议检查对象 |
|---|---|---|---|---|
| `A-xx` | `<id>` | `<开发已经声明但尚未独立证明的事实>` | `<需要源码/失败路径/最终包的原因>` | `<源码、测试、artifact 或运行场景>` |

#### 3.9.3 Documentation RESULT 语义审查

机器检查只负责在交接前挡住缺 Gate、缺证据、缺文件、身份错误和工作区不 clean，不能取代
Documentation Agent。Documentation Agent 只依据 PLAN、RESULT、机械身份和证据入口，核对“开发
在 RESULT 中声明做的东西是不是用户和 PLAN 要的东西”，必须一次性检查：

1. 每项 PLAN 要求是否在 RESULT 中有对应交付声明，是否存在缺项、擅自扩缩范围或用内部指标替代用户结果；
2. RESULT 表达的开发理解是否符合用户需求、Design Baseline、流程状态和失败边界；
3. RESULT 声明的技术路线是否符合当前批准 PLAN，是否已经声明并提供旧路线退出的开发证据入口；
4. RESULT 的完成声明、已知偏差和开发证据摘要是否内部一致，是否把明确未执行的内容写成完成；
5. 候选 commit、最终包、PLAN Revision/blob、分支和 clean 状态是否绑定同一交付对象。

Documentation Agent 不读取源码、测试实现或原始运行日志来判断上述声明是否真实，也不从 RESULT
没有提供的信息推断代码事实。开发本应填写的映射、强制自测或证据缺失时，结论为
`DOC_RETURNED`；RESULT 完整但仍需验证的源码与运行事实，进入“待独立验收问题”。

Documentation Agent 接到完整交付后应完成一轮集中审查，不得发现一个问题就立即结束并串行打回。
本轮审查只能给出以下一种结论：

- `DOC_ALIGNED`：RESULT 完整且其中声明的开发理解与当前 PLAN 一致，可以进入独立源码验收；这不表示实现已经被证明正确；
- `DOC_RETURNED`：PLAN 没变，但 RESULT 存在缺项、理解偏差、内部矛盾、明确错误完成声明或开发交付缺口；必须一次列出本轮
  能够发现的完整问题集合；
- `PLAN_REVISION_REQUIRED`：原 PLAN 的产品目标、技术路线、设计基线或门禁本身必须实质改变，旧
  候选及受影响证据按修订范围失效。

返工后的 Documentation 复核以打回项及其影响范围为主。若第二次才发现第一次同一审查范围内本应
发现的问题，记为 Documentation 审查遗漏；若 Development Agent 没有完成已经明确列出的打回项，
记为 Development 交付缺陷；用户改变目标或证据推翻既有技术路线，记为 Baseline/PLAN 变化。三者
不得混称为笼统“继续补证”。RESULT 语义审查确认的是交付文档完整性与开发声明的需求理解，不替代
Acceptance Agent 对源码正确性、失败路径和最终包行为的独立证明。

### 3.10 PLAN Revision 与版本 HISTORY

V2.2.0 起，开发轮次与 PLAN Revision 分开：开发漏做现有要求、测试未完成或证据不足，继续执行同一
PLAN，不产生新 Revision；只有产品范围、技术路线、Design Baseline 或强制验收合同发生实质变化，
才由 Documentation Agent 形成新的完整 PLAN Revision 并重新提交 Product Owner 批准。

`PLAN.md` 永远只保存一份可独立执行的当前有效合同。新 Revision 必须标明 `Plan Revision` 与
`Supersedes`，保留仍有效要求，直接移除失效路线，并同步更新任务、风险、Gate 和旧候选/证据失效
范围；不得继续在文件末尾堆叠“第 N 轮返工补充”。旧 PLAN 全文由已批准 commit/blob 和 Git 历史
保存。

本版本目录新增 `HISTORY.md`，只记录会影响理解本版本演进的重要事件：P0/P1、技术路线推翻、同类
问题重复发生、候选或包身份错误、路径/工作区事故、跨角色职责错误，以及能够提炼出跨版本规则的
问题。每项记录包含触发事实、根因、影响、处置、PLAN/candidate 身份变化和最终去向；不粘贴长日志，
不记录普通 Bug 流水账，也不作为当前开发合同或当前 Gate 状态真源。

事件的版本事实留在 HISTORY；由此形成且对后续版本持续有效的产品/技术选择写入 `DECISIONS.md`，
通用协作规则写入 `HUMAN_AI_WORKFLOW.md`。同一事实可以被提炼，但不得把 HISTORY 原文整段复制到
全局文档。

## 4. 目标导向的范围冻结基线（Product Owner 已确认）

本节是对前述要求的范围复述，不新增功能。Product Owner 已于 2026-09-13 确认冻结。冻结对象是
用户目标、可观察结果、事实/安全边界、明确不做项和验收底线，不是对某个实现方案的永久承诺：

- 不影响上述目标和边界的组件拆分、数据结构细节、工具选择与实现优化，由 Development Agent 在
  PLAN 技术约束内决定并在 RESULT 如实说明，不需要为了普通实现调整反复修改范围；
- 若最小纵切、真实运行或验收证据表明既定技术路线难以稳定达到目标，任何角色都必须发起
  Architecture Challenge，暂停受影响实现，提出根因、替代路线、迁移影响和验证办法；不得因“已经
  冻结”继续局部修补，也不得静默降低目标；
- 仅当用户目标、可见交互、明确不做项、Design Baseline 或强制 Gate 发生实质改变时，才需要形成
  范围/PLAN Revision 并重新取得 Product Owner 批准。路线切换可以保留同一产品目标，但仍须按
  Challenge 和 PLAN 规则显式记录，不能在 RESULT 中事后解释；
- 正式 PLAN 形成前若证据否定当前暂定路线，Documentation Agent 更新 DRAFT/HISTORY 中受影响部分，
  只提交变化摘要供 Product Owner 批准；正式 PLAN 形成后则使用唯一完整 PLAN Revision。

- 最终 DOCX 是可编辑产物真源，PDF 必须由同一 DOCX 经 Microsoft Word COM 转换；viewer 与 PDF
  下载读取同一 artifact，Word/PDF 失败保持 fail closed，不恢复手绘回退；
- 固定模板、照片框、字体授权、锚点、下载 GET/HEAD/Range、MIME/hash、404/405 负向、Word 进程
  清理和 P4 全程无控制台/Word 闪窗继续构成回归门禁；
- 支持视口下整页不出现滚动条，固定卡片不随内容量跳变；必要滚动只发生在明确的卡片内容区；
- 失败、刷新、取消、重试或并发返回不得静默丢失用户已经确认的输入，也不得把不完整产物标为成功。

### 4.3 V2.2.0 明确不做

- 关闭整个应用/后端、应用崩溃、系统重启或关机后的未完成任务续跑；
- 同时运行或保留多个活动生成任务，以及跨页面全局悬浮进度、通知或任务中心；
- 持久化个人 Profile，或从上传简历、履历库、上一任务、模板、JD 或 AI 自动回填身份信息；
- 保存每个字符/token 的完整事件日志、回放逐字动画，或展示/保存模型私有思维链；
- 单 Fact 并行、并发自动提高到 3，或默认增加一次全简历 LLM 统一润色；
- 新增模板选择、任意 Word 模板解析、HTML 预览的逐行/分页/像素级 Word 一致承诺；
- 恢复 ReportLab/手绘 PDF，或让 HTML 预览成为第二最终产物真源；
- 简历上传查重、OCR、Fact 锁定、单 Fact 局部重新生成、修订差异/回退；
- 关键词富文本加粗、按内容自动调整全局字体/字号/行距/字距及一页美化适配；
- 登录、用户隔离、云端数据库、对象存储、分布式队列、跨设备恢复和公网部署。

### 4.4 已明确延期

  字体、字号、行距、字距和一至两行 Fact 约束的一体化排版优化；
- **V3**：登录与用户隔离、网页服务端持久任务、应用/服务中断恢复、跨设备数据、对象存储及正式
  清理/容量策略；
- **V2.1.1**：只保留给 V2.1.0 的必要紧急修复，不承载上述 V2.2.0 功能。

### 4.5 写 PLAN 前必须用证据确定

以下不是开放式产品需求，而是不得留到全面开发后才发现错误的技术/数据门禁：

1. 当前目标模型能否稳定输出 P1/P3 所需的可解析增量，以及逐字理由是否能与最终 Fact 正确绑定；
2. 权威任务快照、覆盖式 `display_snapshot`、SSE `seq` 去重/缺口重取和刷新恢复能否形成最小纵切；
3. 经历并发 2 相对串行的延迟、限流、Token/费用、顺序稳定性和内容质量；
4. 当前 V2.1.0 在短/典型/长、冷/热样例下的真实基线，以及候选 1 秒/15 秒/中位数降低 25% 是否
   可作为最终硬门禁；
5. 联系方式与教育字段在现有输入、数据库、ResumeDocument、DOCX、PDF/viewer 链路中的真实断点；
6. 固定模板 HTML 过程预览的 Design Snapshot，以及生成中和最终 PDF 切换时的布局稳定性；
7. 临时任务冻结 schema 的容量估算、物理上限和不会误删活动任务/最终 artifact 的清理实现。

### 4.6 技术证据轨收口（2026-09-13）

本节只记录开发前证据，不授权产品源码开发，也不把候选参数提前写成已批准合同。证据来自正式
`v2.1.0` 发布基线的隔离运行，原始入口位于
`validation-artifacts/v2.2-preplan/`：

- `deepseek-v4-pro-ga-260813` 对 `reasoning_effort=minimal` 的行为稳定，3/3 Fact 输出通过
  typed parse，并保持 `experience_id / fact_id` 绑定；`reasoning_effort=low` 在本次探针中未按预期
  关闭 reasoning，不能作为冻结参数；
- “单次复杂结构化流同时携带 Fact 与 reason”只有 1/3 能稳定绑定 reason，且不能满足“Fact 整条出现、
  旁侧理由逐字输出”的交互语义，因此该路线已被证据否定；
- 可行路线为“紧凑 JD 结构化 → 本地召回与 JD 阶段重叠 → 按经历两阶段”：每个经历先返回不含
  reason 的结构化 `headline + body`，完整校验后整条进入预览，再以单独普通文本流输出绑定该
  `fact_id` 的 reason；reason 流失败时保留已完成 Fact，并以完整 reason 事件补偿或显示明确失败；
- 上述紧凑路线按点击生成计时，包含 JD 分析与首个 Fact，3/3 为 12.26 / 12.86 / 13.02 秒；当前
  V2.1.0 同步路线首个 Fact 为 50.57～114.24 秒，不能达到 15 秒目标。3 次样本证明路线可行但余量
  只有约 2 秒，最终集成仍须重新执行同口径门禁；
- V2.1.0 基线：典型 cold `n=5, median=89.49s, max=111.21s`，典型 warm
  `n=4, median=84.48s, max=105.78s`；长样例 cold `n=4, median=94.32s, max=122.82s`，
  warm `n=3, median=97.92s, max=125.24s`。短样例 cold 4/4、warm 3/3 均在
  `TemplateRenderer.render` 触发 `TemplateError`，因此短样例当前只形成正确性阻断，不能伪造成功
  耗时或纳入成功中位数；
- 经历级最大并发 2 的 Provider 对照明显快于串行，且本轮绑定与顺序检查通过；并发 3 未验证，也不在
  V2.2.0 范围；
- 权威快照、SSE `seq` 去重/缺口重取、刷新恢复与旧 revision fence 已形成确定性最小纵切；联系方式
  能进入 ResumeDocument、DOCX 与 PDF，教育字段仍存在 `（本科）（）` 断点，后者必须作为开发任务
  修复；
- 长任务状态峰值实测约 26.9 KiB，活动/取消中任务、当前页面引用对象以及已发布 revision/artifact
  的保护测试为 0 违规。测量支持为状态与事件设置 256 KiB 级硬上限，但 artifact 文件正文必须与状态
  字节分开计算。

据此，正式 PLAN 的参数冻结必须消除以下歧义：

1. 逻辑 LLM 调用预算写成 `1 + 2N`（一次 JD，N 次 Fact，N 次 reason），Embedding 调用与缓存命中
   单独计数，不能把 Embedding 隐藏在该公式里；
2. retry 必须同时写明“最多几次重试”和“最多几个 HTTP attempt”，不能只写“上限 2”；
3. Token 上限分别冻结 JD、Fact、reason 的单次 attempt 与整个任务总预算；不能把“每经历 800”同时
   当成 Fact、reason 和重试后的总量；
4. 页面离开只触发状态保存/断开 SSE，不触发任务或 artifact 删除。清理只在启动、任务终态和容量阈值
   扫描执行；`RUNNING / CANCELLING`、当前任务、已发布 ResumeRevision 引用的 DOCX/PDF 永不因临时
   状态清理被删除；
5. 一次本地 profile 只允许一个前台活动任务；“最多 20 条”只用于终态/孤立临时记录的容量保护，不能
   被实现成 20 个可同时运行的生成任务；
6. 真实性能统计使用固定样本、`n >= 3`、中位数和最大值，不在小样本上报告 P95；人民币单价在当前
   证据不可得时，以逻辑调用、HTTP attempt、prompt/completion token 作为本版本可执行成本门禁，并
   在 RESULT 如实标注人民币成本不可得。

以上路线结论属于证据驱动的技术收口；15 秒、总耗时降低 25%、具体 Token/容量/保留数字仍须由
Product Owner 随 PLAN Revision 1 一次批准。

## 5. 范围冻结后的 PLAN 准备动作

当前不再把已确认事项继续列为开放需求。Product Owner 于 2026-09-13 批准把 PLAN 准备拆成可并行
但具有串行汇合门禁的两条轨道：

1. **Design 轨**：为新建/草稿已保存/刷新恢复/生成中/历史阶段回看/取消/失败/完成等关键状态形成
   唯一 Design Snapshot，并由 Product Owner 批准。当前 `D-003` 仍是可变工作稿，未获批准前不得
   被 Development Agent 当作实现输入；
2. **技术证据轨**：由 Development Evidence Agent 在不修改正式产品候选的隔离环境中，对正式
   `v2.1.0` 发布基线（tag `v2.1.0`，commit `5d72a2e08ebd4fa416b4b1dcdd79c1d08dfc7cfd`）
   完成短/典型/长、冷/热基线，并验证 SSE 状态恢复、逐字理由边界、经历并发 2、联系方式/教育字段
   断点和任务容量的最小真实纵切。该任务属于开发前证据，不是 Acceptance，不产生产品候选或发布
   结论；
3. **参数冻结**：Documentation Agent 根据上述证据冻结任务物理记录/字节上限、目标模型、最终
   延迟、成本、调用次数和质量阈值。若证据否定当前路线，必须在产品实施前发起 Architecture
   Challenge 并提交路线变化摘要；
4. **分批 PLAN 授权**：若技术证据轨先完成，可以形成只授权设计无关产品工作的完整 PLAN
   Revision 1；它必须列出允许范围和 Design Gate，禁止实现或猜测布局、可见交互、响应式和设计文案。
   Design Snapshot 获批后形成完整 PLAN Revision 2，`Supersedes` Revision 1、导入并绑定对应
   `DS-xxx`，再授权设计相关实现和最终集成。仓库始终只有一份当前有效 PLAN；这是预先批准的两批
   开发，不记为返工轮次；
5. **统一交付契约**：在首个产品实现 Revision 获批前，将已批准的跨版本工作流规则一次性迁入全局
   文档，写入 RESULT Delivery Contract、测试矩阵、发布关系、干净开发基线和停止条件，再由
   Product Owner 批准。两批产品源码仍由同一 Development Integrator 负责；Acceptance Agent 只在
   冻结候选形成后启动，不能代替开发前证据任务。
