# 架构与产品决策记录

> 文档角色：跨版本决策及其演进  
> 说明：只保留已有依据；没有证据的理由不补写

## 状态定义

- Accepted：当前仍有效；
- Partially Superseded：部分被后续调整；
- Superseded：已被后续决策替代；
- Rejected：评估后明确不采用；
- Planned：尚未通过实现验收。

## D-001 经历是资产，简历是输出

- 版本：V1.0.0
- 状态：Accepted
- 背景：产品需要支持不同 JD、模板以及后续面试和画像能力。
- 决策：Experience 独立持久化，简历按任务实时生成。
- 依据：如果把逻辑绑定到简历文件，新增模板、投递和面试能力会反复解析和迁移简历。
- 影响：SQL Experience 成为长期事实源。

## D-002 隔离 AI 框架

- 版本：V1.0.0
- 状态：Accepted
- 演进：实际边界比初始方案更严格。
- 决策：业务模块不直接依赖 LangChain，通过适配服务调用 AI。
- 初始方案：llm_service 和 rag_service 两个模块允许导入 LangChain。
- 实际结果：因 Embedding 特殊协议，rag_service 改用原生 HTTP，当前仅 llm_service 导入 LangChain。
- 影响：业务、API 和数据库不感知具体 AI 框架。

## D-003 豆包 Embedding 改用多模态模型

- 版本：V1.0.0
- 状态：Accepted
- 原计划：doubao-embedding-text-240715。
- 实际选择：doubao-embedding-vision-251215，使用纯文本输入。
- 依据：原计划模型不存在或不可用，旧文本模型已下线；当时平台可用的是多模态 Embedding。
- 影响：模型通过环境变量配置，向量维度变为实际模型维度。

## D-004 Embedding 使用原生 HTTP

- 版本：V1.0.0
- 状态：Accepted
- 原计划：LangChain OpenAIEmbeddings。
- 决策：rag_service 使用 urllib 调用 embeddings/multimodal。
- 依据：
  - LangChain 会将文本转成 token ID，而豆包接口要求原始字符串；
  - 豆包使用专属 endpoint；
  - 请求是对象数组；
  - 响应 data 是对象而不是 OpenAI 风格数组。
- 影响：rag_service 不再导入 LangChain。

## D-005 Chroma 不可用时提供 numpy 回退

- 版本：V1.0.0
- 状态：Superseded
- 后续决策：D-012 曾恢复 Chroma 为主后端；V1.5.0 的 D-026 最终以 SQLite `fact_embeddings` 取代 Chroma 与 numpy + JSON 活动持久化，numpy 只保留为内存计算库。
- 背景：Windows 环境的 Chroma Rust 扩展/DLL 加载失败。
- 决策：保持统一存储接口，失败时使用 numpy 余弦检索和 JSON 持久化。
- 依据：V1 单用户、少量经历场景需要先跑通。
- 影响：上层不感知后端变化，但出现双后端和迁移需求。

## D-006 程序确定结构，AI 理解内容

- 版本：V1.1.0
- 状态：Accepted
- 背景：V1 全文经历提取耗时 201.5 秒，LLM 同时承担清洗、章节识别、定位和结构化。
- 决策：程序预处理和章节切分，分段并发调用 AI，再合并去重。
- 结果：经历提取实测降至 39.8 秒。

## D-008 结构化输出失败后的默认兜底

- 版本：V1.1.0
- 状态：Partially Superseded
- 决策：Structured Output → JSON + Pydantic → 降温重试 → 默认空模型。
- 当时依据：优先保证固定 Pipeline 不因格式错误中断。
- 后续问题：关键阶段可能把真实失败伪装成空成功。
- V1.3.0 演进：JD 和定制内容等关键阶段已经改为 strict failure；默认空模型只可保留在非关键旧路径或调试功能。

## D-009 放弃任意 Word 模板解析

- 版本：V1.2.0
- 状态：Rejected
- 被否决方案：用户上传 Word → 解析文本框 → 识别章节 → 按坐标写入。
- 实测依据：
  - 多个章节共享相同坐标；
  - 家族识别按内容会漏识别，按坐标会误合并；
  - 标题和内容框容易混淆；
  - 坐标去重会删除其他章节；
  - 复杂度接近实现 Word 渲染器子集。
- 结论：该能力不属于 V1.2.0。

## D-011 模板视觉参照改用用户 PDF

- 版本：V1.2.0
- 状态：Accepted
- 适用范围：V1.2.0 系统参考模板。
- 背景：初版模板参照 Word 文本框布局，与用户实际 PDF 的页边距、bullet、照片框和对齐差异较大。
- 决策：使用 pdfplumber 提取用户 PDF 的布局参数，重建系统标准模板。

- 注意：这些是 V1.2.0 模板验收，不等于严格跨软件像素级渲染。

## D-012 恢复 Chroma 原生后端并保留迁移能力

- 版本：V1.2.1
- 状态：Superseded
- 后续决策：V1.5.0 的 D-026 用 SQLite `fact_embeddings` 统一向量持久化；本节继续保留 V1.2.1 当时恢复 Chroma 的原因和结果。
- 背景：环境已经可以正常加载 Chroma；默认 onnx embedding 路径仍可能触发 DLL 问题。
- 决策：
  - 使用 PersistentClient；
  - 所有写入显式传 embeddings；
  - 所有查询显式传 query_embeddings；
  - 保留 numpy 回退；
  - 增加 numpy → Chroma 幂等迁移和状态快照。
- 影响：V1.0.0 的“当前运行在 numpy”状态被更新，但历史原因保留。

## D-020 运行数据与源码仓库物理解耦

- 版本：V1.4.0
- 状态：Accepted
- 背景：当前项目准备公开到 GitHub。若用户输入、生成输出、数据库、向量索引、日志和缓存仍与源码目录混放，每次发布都需要重新人工筛选和整理，既增加维护成本，也容易遗漏敏感数据。
- 决策：
  - 所有可变运行数据统一存放在一个可配置的 runtime data root 下，默认位置必须在 Git checkout 之外；
  - 源码仓库只保留代码、不可变产品资产、公开文档、虚构测试数据和配置样例；
  - 测试使用临时目录和虚构 fixture，不读写开发者的真实 runtime 数据；
  - 因旧 Git 历史曾包含 PII，V1.4.0 首次公开时只执行一次干净历史迁移；之后以新仓库为开发基线，正常提交和推送，不再逐版本制作人工发布快照；
  - 后续提交仍保留自动 Secret、PII 和运行产物检查，作为安全兜底，而不是人工整理流程。
- 依据：用物理边界消除长期混放风险，比每次发布人工筛选文件更稳定，也能降低人和执行 Agent 的重复工作与上下文负担。
- 影响：V1.4.0 已统一路径配置，并对既有本地数据完成可验证、可回滚的迁移和向量重建；数据迁移、持久化和安全边界已由验收 Agent 独立复核。未改变 API、事实模型或 V1.3.0 业务行为。
- 验收：2026-08-18 完成 Public 首发、`v1.4` tag 与匿名 clone 复核，决策由 Planned 转为 Accepted。

## D-021 GitHub 项目介绍与开发档案分层

- 版本：V1.4.0 发布后文档修正
- 状态：Accepted
- 背景：根 README 最初同时承担项目介绍、文件分类和内部版本状态入口，普通读者需要先理解开发流程才能抓住项目本身；这与 V1.4.0 PLAN 已确认的“精简根 README + `docs/` 完整版本档案”不一致。后续措辞又被理解为要刻意抹掉 Agent 驱动开发痕迹，也偏离用户希望用完整开发历程展示项目能力的目的。
- 决策：
  - 根 `README.md` 按正常开源项目的信息结构介绍用途、能力、安装、运行、配置、数据隐私、目录结构、限制和 License；
  - `docs/README.md` 是完整开发档案入口，`CURRENT_STATE`、`DECISIONS`、PLAN、RESULT、Agent 分工和验收记录继续如实保留；
  - 根 README 设置自然的“开发历程与设计文档”入口，可以明确说明本项目保留完整人机协作开发记录，供架构学习、复用和求职展示；
  - 是否在根 README 出现 PLAN、RESULT 或 Agent 等词，按普通读者是否需要该信息判断，不制定“隐藏开发方式”的禁令，也不把内部状态流水账作为首页主叙事；
  - 后续版本只在公开用途、安装、配置、用户可见能力或隐私边界变化时更新根 README，不把它当作内部版本状态看板。
- 依据：用户文档与开发档案的受众和任务不同。分层用于改善信息层级，不是伪装开发方式；公开完整的决策与验收过程本身也是项目成果。
- 影响：普通读者从根 README 了解项目，再按兴趣进入开发档案；人和开发 Agent 默认从 `docs/README.md` 进入。两者互相链接，但不重复承担事实真源职责。

## D-022 功能验收与结构变更验收分离

- 版本：V1.4.1 流程复盘
- 状态：Accepted
- 背景：V1.3.0 的身份来源主流程和 E2E 行为正确，但与 D-019 冲突的经历正则提取死代码及旧测试契约仍然存在；V1.4.0 的公开文档和 Stub 已更新，FastAPI 元数据仍保留旧版本。两项问题都不阻断核心功能，因此仅靠正常 E2E 无法证明代码结构已经完成迁移。
- 决策：
  - RESULT 分别记录功能验收和结构变更验收；动态测试通过不等于死代码、旧配置或旧实现已经消失；
  - 替换型变更必须明确新真源、必须退出的旧状态，并提供正向、反向和回归证据；
  - 开发验证、独立源码验收和发布结论绑定具体 Git commit；验收后的相关修改必须重验；
  - 普通版本做定向结构检查，V1/V2/V3 阶段收口或重要公开发布前按 PLAN 安排全局架构一致性审查。
- 依据：项目以文档驱动多个 Agent 协作，文档 Agent 不读取源码，验收 Agent 又受 PLAN 范围约束。只有同时验证可观察行为和本次结构迁移，并把证据绑定到实际实现，才能避免把局部 PASS 扩大为整个项目无问题。
- 影响：不新增交接或验收文档；规则写入既有 PLAN / RESULT 工作流。阶段性全局审查用于发现 PLAN 范围外的并行旧路径、重复真源和文档—源码偏差，不替代每个版本的定向验收。

## D-023 公开仓库采用固定基线和正常增量发布

- 版本：V1.4.2
- 状态：Accepted
- 背景：V1.4.0 为切断含 PII 的旧 Git 历史，合理地执行了一次单 commit 干净首发；V1.4.1 继续沿用冻结仓库思路后，本地候选、远端 main 和 tag 曾出现不一致。随机 worktree、临时构建目录和验收副本又缺少稳定的版本身份，四方可能读取不同代码。
- 决策：
  - 公开 `main` 是后续开发的唯一长期 Git 基线，后续版本保留正常父子提交关系，不再逐版本重建 orphan/single-commit 仓库；
  - 本机区分 `<canonical-repo>`、`<current-worktree>` 和 `<review-worktree>` 三种固定角色；交接必须提供基线 commit、候选 commit、分支和 clean 状态；
  - 开发 Agent 只交候选和 RESULT，不操作公开 main/tag；文档 Agent 在用户确认后执行远端 preflight、fast-forward main 和新的 annotated tag；
  - 正常发布禁止 force push；远端非预期变化、非 fast-forward 或 tag 已存在时停止。只有明确事故且用户单独授权时才按精确旧 SHA 保护条件处置，并在 RESULT 留痕；
  - 历史 tag 不因文档补记而移动。发布后才能确认的事实，以后续 main 上的有标记附录追加。
- 依据：固定路径解决“在哪里工作”，commit 身份解决“看到的是哪一版”；正常增量历史同时保留开发经验、缩小 diff 和审查范围，并避免每次发布都依赖覆盖远端。
- 影响：V1.4 的干净首发工具退出常规工具链；全局工作流增加路径角色、commit 交接和最终发布责任。公开仓库 URL 属于用户入口，不按个人隐私删除；本机路径、用户名、凭据和用户数据仍必须脱敏。

## D-024 基础设施改动按完整生命周期验收

- 版本：V1.4.2 发布后流程复盘
- 状态：Accepted
- 背景：V1.4.2 Stub E2E 的业务断言连续 20/20，且真实 runtime 未变化，但第一轮仍因 SQLite/Chroma 句柄未释放、临时目录删除失败被静默吞掉而产生假通过；第一次返工只闭合正常成功路径，随后又在依赖导入失败路径发现 cleanup 注册过晚。小版本因此经历多轮返工，根因不是产品功能复杂，而是生命周期验收标准在每轮后才逐步补全。
- 决策：
  - 测试、迁移、发布、临时目录和资源清理工具不按功能大小判断风险，必须在 PLAN 中定义跨正常与异常退出路径的不变量；
  - 适用时覆盖成功、初始化/导入失败、异常或提前退出、重复 cleanup、资源占用、cleanup 失败和隔离边界；
  - 检测到后置条件失败时必须非零退出，warning 或业务断言通过不能作为整体成功；
  - 首次打回后，文档 Agent 将症状上升为完整问题类别并一次补齐返工矩阵，开发 Agent 完成该矩阵自验后再进入独立源码验收。
- 依据：功能正确、结构正确和资源生命周期正确是不同证明对象。若只修验收现场看到的症状，后续 Agent 会继续发现同一类别的其他路径，造成重复轮次和上下文浪费。
- 影响：不增加新文档或固定验收轮次；详细矩阵写入 `HUMAN_AI_WORKFLOW.md`，具体版本只选择适用场景。小补丁仍可定向验收，但不能因“不增加产品功能”省略失败路径。

## D-025 内容决策采用两层选择并冻结来源

- 版本：V1.5.0
- 状态：Accepted
- 背景：旧链路由检索、生成和 Builder 多处决定内容集合，难以证明“哪些经历入选”和“每条表达使用了什么事实”。
- 决策：
  - 第一层按确定性规则生成 `CandidateExperienceSet`：工作/实习取日期可解析的最近最多 3 次；项目/论文在三年窗口共享候选池并按 JD 相关性取最多 2 项；两类合计少于 2 项时只补最匹配的 1 项校园经历；
  - 正式教育背景保持确定性结构，不与校园活动混池；
  - 第二层只在第一层入选经历中选择版本匹配的 Fact 和表达侧重，生成 `SelectedEvidenceSet`；

  - Builder 只按冻结结果确定性装配并保留来源映射，Renderer 只展示。
- 依据：把经历名单、事实选择、表达和展示拆开，才能对固定槽位、事实边界、过期判断和最终来源进行独立验证。
- 影响：D-016 被取代；召回质量、权重和措辞效果仍属于 V2，不因结构闭环被宣称为已优化。

## D-026 Fact 与 SQLite 向量派生成为唯一活动持久化链路

- 版本：V1.5.0
- 状态：Accepted
- 背景：Experience 粒度过粗，Chroma 与 numpy + JSON 双后端又具有不同的 CRUD、失效、迁移和失败语义，无法形成单一可追溯生命周期。
- 决策：
  - SQL Experience / Fact 是职业事实源；Fact 保存稳定 ID、来源、revision 与 hash；
  - `fact_embeddings` 是唯一活动向量持久化表，保存 fingerprint、dimension、dtype、BLOB、Fact revision/hash 和状态；numpy 只负责内存精确相似度计算；
  - Experience create/update 与 Fact reconciliation 同事务，Fact 修改与旧 Embedding 失效同事务；失败必须回滚或进入明确可重试状态；
  - Chroma 与 numpy + JSON 活动后端、依赖和配置退出；旧向量字节不迁移，统一从当前 Fact 重建；
  - `manage.py migrate/status/rebuild/retry` 是唯一受支持的本地维护入口；既有库迁移前备份并核对，全新不存在的 SQLite 路径按空库初始化，备份、核对或 cleanup 失败时 fail closed。
- 依据：事实身份、派生数据状态和恢复入口必须共享同一事务与持久化语义，才能让增删改、失败、重试、重建和生成阻断一致。
- 影响：D-005 与 D-012 被取代；V1.4.0 的 runtime data root 和源码—数据物理隔离继续有效。

## D-029 本地管理接口采用同源写安全边界

- 版本：V2.0.0
- 状态：Accepted

## D-031 本地长操作使用统一可观测性机制

- 版本：V2.0.1
- 状态：Accepted
- 背景：生成和写入操作可能长时间等待外部模型，原界面只能看到笼统的“处理中”，无法判断当前阶段、已经等待多久、失败位置或各步骤实际耗时。
- 决策：
  - 生成、提取、Experience CRUD、迁移、Embedding 重建和失败重试统一使用一个操作记录机制，不为页面、生成链或系统维护分别建立进度真源；
  - 每次操作使用 `operation_id` 关联当前状态、真实阶段、资源类型、单调耗时、重试信息、最终状态和脱敏诊断摘要；不伪造百分比或预计完成时间；

- 依据：长操作首先需要可定位、可复盘，才能区分外部模型等待、本地计算、数据库、向量检索和文件渲染；统一、脱敏且非阻塞的记录比页面临时状态更可靠，同时避免形成第二业务真源。
- 影响：新增本地诊断 API、运行活动、阶段时间线、近期同类耗时和脱敏摘要；不包含生产 APM、云端遥测、任务取消、断点续跑或 LLM/Embedding 性能优化。

## D-032 开发与源码验收使用固定隔离工作树

- 版本：协作流程修订（2026-09-05）
- 状态：Superseded
- 后续决策：D-033 将固定 linked worktree 改为三个固定、独立 `.git` 的 workspace，并补齐权限、PLAN 冻结和候选流转。
- 背景：按版本或返工轮次不断创建验收目录会造成路径膨胀和入口混乱；让开发 Agent 与验收 Agent 同时共享一个目录，又会使文件、Git index、构建产物和测试现场互相污染，验收无法稳定绑定同一 clean commit。
- 决策：
  - 长期只维护一个固定开发路径 `<current-worktree>` 和一个固定源码验收路径 `<review-worktree>`；路径名称不随版本或轮次变化；
  - 开发路径检出活动版本分支，验收路径保持 detached、clean，每轮只把验收路径更新到新的冻结候选 commit；
  - 开发与验收不得并发共享同一工作目录；候选冻结后开发停止修改，验收结束后才允许进入下一轮返工；
  - 验收 Agent 全程只读，不修改源码、测试、配置、构建文件或文档，只把绑定 commit 的验收报告交给文档 Agent；文档 Agent 统一写入 RESULT；
  - 只有默认路径缺失、损坏、被其他活动任务占用或用户明确要求保留并行现场时，才创建临时工作树，且不把临时路径升级为新的默认入口。
- 依据：路径保持稳定便于人和 Agent 记忆，commit 保持可变才能指向每轮真实候选；将“固定路径”与“固定内容”分开，同时保留角色隔离，能够减少目录管理成本而不牺牲验收可追溯性。
- 影响：后续版本和返工不再默认创建新的 review 目录；历史工作树可以保留为旧证据，但不再作为活动入口。验收报告由文档 Agent 归并到版本 RESULT，避免验收工作树因文档写入而变脏。

## D-033 开发、验收与发布使用固定独立仓库和冻结身份

- 版本：协作流程修订（2026-09-05）
- 状态：Accepted
- 背景：D-032 解决了按轮次增加目录和开发/验收共用 checkout 的问题，但 linked worktree 仍共享 object database、refs、remote、hooks 和 worktree 注册表；同一 Windows 账户下的文件只读属性也不能区分 Agent。仅凭路径和 `git status` clean，无法阻止跨角色 Git 误操作，也不能排除 ignored 构建物、`.env` 或真实 runtime 对验收结果的影响。
- 决策：
  - 长期维护 `<canonical-repo>`、`<current-workspace>`、`<review-workspace>` 三个固定独立 Git 仓库，各自拥有独立 `.git`；不因版本或返工轮次增加默认路径，也不再用 linked worktree 共享 Git 控制面；
  - canonical 是文档集成、候选接收和唯一发布入口；本地 `main` 是待发布集成线，`publish/main` 是 GitHub 当前公开主线，annotated tag 的目标 commit 是正式版本唯一发布身份；只有 canonical 配置具有 GitHub push 能力的发布 remote；
  - 用户批准 PLAN 时冻结版本、路径、批准 commit 和 blob。开发 Agent 与验收 Agent 对 PLAN 只读；返工补充只能由文档 Agent 追加并形成新的批准身份，不覆盖原始批准内容；
  - 开发 Agent 只在 current 的活动版本分支修改 PLAN 范围内的源码、测试、依赖和构建配置，并只在候选冻结前更新 RESULT 的实施、自测和偏差；不得修改全局文档、canonical 本地 `main`、正式 tag 或 GitHub remote；
  - 开发候选以 clean commit `H` 冻结，经本地 Git 进入 canonical 的未发布候选引用，再由 review detached 到 `H`。验收只绑定 `H`，分支后续 commit 不继承结论；review 更新前后必须核对同一 HEAD；
  - 验收 Agent 不修改 PLAN、RESULT、源码、测试、依赖、配置、构建或 Git 历史，只返回绑定 commit 的报告；会产生写入的测试从冻结 commit 建立一次性临时副本，并隔离 runtime、数据库、输出、日志、缓存和依赖目录，cleanup 或 review clean 后置条件失败即验收失败；
  - 源码和人工验收通过后，文档 Agent 将 `H` 纳入 canonical 本地 `main` 并完成最终文档；最终发布候选 `R` 相对 `H` 只能有授权文档变化，否则相关源码验收失效。用户明确批准后，文档 Agent 才执行远端 preflight、fast-forward main 和 annotated tag；
  - 真实绝对路径只保存在本机项目配置和任务交接中，公开文档使用语义别名。正常 Agent 任务仅以自己的固定仓库作为可写 workspace root；该方案用于防误操作，不冒充同一 Windows 账户下的硬安全隔离，后者必须使用独立系统账户、凭据和 ACL；
  - 迁移旧工作树前先检查 clean、引用可达性和独有证据；无 branch/tag 的 detached commit 在确认结论已归并前使用临时迁移引用和可验证 bundle 保护。迁移后只保留三个固定仓库，依赖、构建物和测试缓存重新生成，真实 runtime 与凭据不随源码仓库迁移。
- 依据：固定父目录解决入口记忆，独立 `.git` 缩小跨角色 Git 误操作半径，commit/blob 冻结解决版本身份，临时测试副本解决“只读验收”与动态测试写入的冲突；四者缺一都不能形成稳定、可复核的版本流转。
- 影响：D-032 被取代；D-023 的正常增量发布、禁止常规 force push 和历史 tag 不移动继续有效，但其中本地路径角色改由本决策定义。全局工作流采用“PLAN 批准 → current 开发并冻结 H → canonical 接收 → review 只读验收 H → 人工验收 → canonical 文档收口为 R → 用户批准后发布”的单向流转。
