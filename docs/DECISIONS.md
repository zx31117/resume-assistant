# 架构与产品决策记录

> 文档角色：跨版本决策及其演进  
> 说明：只保留已有依据；没有证据的理由不补写

## 状态定义

- Accepted：当前仍有效；
- Partially Superseded：部分被后续调整；
- Superseded：已被后续决策替代；
- Rejected：评估后明确不采用；
- Planned：尚未通过实现验收。

## D-001 经历是资产，简历是输出

- 版本：V1.0.0
- 状态：Accepted
- 背景：产品需要支持不同 JD、模板以及后续面试和画像能力。
- 决策：Experience 独立持久化，简历按任务实时生成。
- 依据：如果把逻辑绑定到简历文件，新增模板、投递和面试能力会反复解析和迁移简历。
- 影响：SQL Experience 成为长期事实源。

## D-002 隔离 AI 框架

- 版本：V1.0.0
- 状态：Accepted
- 演进：实际边界比初始方案更严格。
- 决策：业务模块不直接依赖 LangChain，通过适配服务调用 AI。
- 初始方案：llm_service 和 rag_service 两个模块允许导入 LangChain。
- 实际结果：因 Embedding 特殊协议，rag_service 改用原生 HTTP，当前仅 llm_service 导入 LangChain。
- 影响：业务、API 和数据库不感知具体 AI 框架。

## D-003 豆包 Embedding 改用多模态模型

- 版本：V1.0.0
- 状态：Accepted
- 原计划：doubao-embedding-text-240715。
- 实际选择：doubao-embedding-vision-251215，使用纯文本输入。
- 依据：原计划模型不存在或不可用，旧文本模型已下线；当时平台可用的是多模态 Embedding。
- 影响：模型通过环境变量配置，向量维度变为实际模型维度。

## D-004 Embedding 使用原生 HTTP

- 版本：V1.0.0
- 状态：Accepted
- 原计划：LangChain OpenAIEmbeddings。
- 决策：rag_service 使用 urllib 调用 embeddings/multimodal。
- 依据：
  - LangChain 会将文本转成 token ID，而豆包接口要求原始字符串；
  - 豆包使用专属 endpoint；
  - 请求是对象数组；
  - 响应 data 是对象而不是 OpenAI 风格数组。
- 影响：rag_service 不再导入 LangChain。

## D-005 Chroma 不可用时提供 numpy 回退

- 版本：V1.0.0
- 状态：Partially Superseded
- 后续决策：D-012 恢复 Chroma 为主后端，但保留本决策定义的 numpy 故障回退。
- 背景：Windows 环境的 Chroma Rust 扩展/DLL 加载失败。
- 决策：保持统一存储接口，失败时使用 numpy 余弦检索和 JSON 持久化。
- 依据：V1 单用户、少量经历场景需要先跑通。
- 影响：上层不感知后端变化，但出现双后端和迁移需求。

## D-006 程序确定结构，AI 理解内容

- 版本：V1.1.0
- 状态：Accepted
- 背景：V1 全文经历提取耗时 201.5 秒，LLM 同时承担清洗、章节识别、定位和结构化。
- 决策：程序预处理和章节切分，分段并发调用 AI，再合并去重。
- 结果：经历提取实测降至 39.8 秒。

## D-008 结构化输出失败后的默认兜底

- 版本：V1.1.0
- 状态：Partially Superseded
- 决策：Structured Output → JSON + Pydantic → 降温重试 → 默认空模型。
- 当时依据：优先保证固定 Pipeline 不因格式错误中断。
- 后续问题：关键阶段可能把真实失败伪装成空成功。
- V1.3.0 演进：JD 和定制内容等关键阶段已经改为 strict failure；默认空模型只可保留在非关键旧路径或调试功能。

## D-009 放弃任意 Word 模板解析

- 版本：V1.2.0
- 状态：Rejected
- 被否决方案：用户上传 Word → 解析文本框 → 识别章节 → 按坐标写入。
- 实测依据：
  - 多个章节共享相同坐标；
  - 家族识别按内容会漏识别，按坐标会误合并；
  - 标题和内容框容易混淆；
  - 坐标去重会删除其他章节；
  - 复杂度接近实现 Word 渲染器子集。
- 结论：该能力不属于 V1.2.0。

## D-011 模板视觉参照改用用户 PDF

- 版本：V1.2.0
- 状态：Accepted
- 适用范围：V1.2.0 系统参考模板。
- 背景：初版模板参照 Word 文本框布局，与用户实际 PDF 的页边距、bullet、照片框和对齐差异较大。
- 决策：使用 pdfplumber 提取用户 PDF 的布局参数，重建系统标准模板。

- 注意：这些是 V1.2.0 模板验收，不等于严格跨软件像素级渲染。

## D-020 运行数据与源码仓库物理解耦

- 版本：V1.4.0
- 状态：Accepted
- 背景：当前项目准备公开到 GitHub。若用户输入、生成输出、数据库、向量索引、日志和缓存仍与源码目录混放，每次发布都需要重新人工筛选和整理，既增加维护成本，也容易遗漏敏感数据。
- 决策：
  - 所有可变运行数据统一存放在一个可配置的 runtime data root 下，默认位置必须在 Git checkout 之外；
  - 源码仓库只保留代码、不可变产品资产、公开文档、虚构测试数据和配置样例；
  - 测试使用临时目录和虚构 fixture，不读写开发者的真实 runtime 数据；
  - 因旧 Git 历史曾包含 PII，V1.4.0 首次公开时只执行一次干净历史迁移；之后以新仓库为开发基线，正常提交和推送，不再逐版本制作人工发布快照；
  - 后续提交仍保留自动 Secret、PII 和运行产物检查，作为安全兜底，而不是人工整理流程。
- 依据：用物理边界消除长期混放风险，比每次发布人工筛选文件更稳定，也能降低人和执行 Agent 的重复工作与上下文负担。
- 影响：V1.4.0 已统一路径配置，并对既有本地数据完成可验证、可回滚的迁移和向量重建；数据迁移、持久化和安全边界已由可读取源码的高性能 Agent 独立复核。未改变 API、事实模型或 V1.3.0 业务行为。
- 验收：2026-08-18 完成 Public 首发、`v1.4` tag 与匿名 clone 复核，决策由 Planned 转为 Accepted。

## D-021 GitHub 项目介绍与开发档案分层

- 版本：V1.4.0 发布后文档修正
- 状态：Accepted
- 背景：根 README 最初同时承担项目介绍、文件分类和内部版本状态入口，普通读者需要先理解开发流程才能抓住项目本身；这与 V1.4.0 PLAN 已确认的“精简根 README + `docs/` 完整版本档案”不一致。后续措辞又被理解为要刻意抹掉 Agent 驱动开发痕迹，也偏离用户希望用完整开发历程展示项目能力的目的。
- 决策：
  - 根 `README.md` 按正常开源项目的信息结构介绍用途、能力、安装、运行、配置、数据隐私、目录结构、限制和 License；
  - `docs/README.md` 是完整开发档案入口，`CURRENT_STATE`、`DECISIONS`、PLAN、RESULT、Agent 分工和验收记录继续如实保留；
  - 根 README 设置自然的“开发历程与设计文档”入口，可以明确说明本项目保留完整人机协作开发记录，供架构学习、复用和求职展示；
  - 是否在根 README 出现 PLAN、RESULT 或 Agent 等词，按普通读者是否需要该信息判断，不制定“隐藏开发方式”的禁令，也不把内部状态流水账作为首页主叙事；
  - 后续版本只在公开用途、安装、配置、用户可见能力或隐私边界变化时更新根 README，不把它当作内部版本状态看板。
- 依据：用户文档与开发档案的受众和任务不同。分层用于改善信息层级，不是伪装开发方式；公开完整的决策与验收过程本身也是项目成果。
- 影响：普通读者从根 README 了解项目，再按兴趣进入开发档案；人和开发 Agent 默认从 `docs/README.md` 进入。两者互相链接，但不重复承担事实真源职责。

## D-022 功能验收与结构变更验收分离

- 版本：V1.4.1 流程复盘
- 状态：Accepted
- 背景：V1.3.0 的身份来源主流程和 E2E 行为正确，但与 D-019 冲突的经历正则提取死代码及旧测试契约仍然存在；V1.4.0 的公开文档和 Stub 已更新，FastAPI 元数据仍保留旧版本。两项问题都不阻断核心功能，因此仅靠正常 E2E 无法证明代码结构已经完成迁移。
- 决策：
  - RESULT 分别记录功能验收和结构变更验收；动态测试通过不等于死代码、旧配置或旧实现已经消失；
  - 替换型变更必须明确新真源、必须退出的旧状态，并提供正向、反向和回归证据；
  - 开发验证、独立源码验收和发布结论绑定具体 Git commit；验收后的相关修改必须重验；
  - 普通版本做定向结构检查，V1/V2/V3 阶段收口或重要公开发布前按 PLAN 安排全局架构一致性审查。
- 依据：项目以文档驱动多个 Agent 协作，文档 Agent 不读取源码，高性能验收又受 PLAN 范围约束。只有同时验证可观察行为和本次结构迁移，并把证据绑定到实际实现，才能避免把局部 PASS 扩大为整个项目无问题。
- 影响：不新增交接或验收文档；规则写入既有 PLAN / RESULT 工作流。阶段性全局审查用于发现 PLAN 范围外的并行旧路径、重复真源和文档—源码偏差，不替代每个版本的定向验收。

## D-023 公开仓库采用固定基线和正常增量发布

- 版本：V1.4.2
- 状态：Accepted
- 背景：V1.4.0 为切断含 PII 的旧 Git 历史，合理地执行了一次单 commit 干净首发；V1.4.1 继续沿用冻结仓库思路后，本地候选、远端 main 和 tag 曾出现不一致。随机 worktree、临时构建目录和验收副本又缺少稳定的版本身份，四方可能读取不同代码。
- 决策：
  - 公开 `main` 是后续开发的唯一长期 Git 基线，后续版本保留正常父子提交关系，不再逐版本重建 orphan/single-commit 仓库；
  - 本机区分 `<canonical-repo>`、`<current-worktree>` 和 `<review-worktree>` 三种固定角色；交接必须提供基线 commit、候选 commit、分支和 clean 状态；
  - 开发 Agent只交候选和 RESULT，不操作公开 main/tag；文档 Agent在用户确认后执行远端 preflight、fast-forward main 和新的 annotated tag；
  - 正常发布禁止 force push；远端非预期变化、非 fast-forward 或 tag 已存在时停止。只有明确事故且用户单独授权时才按精确旧 SHA 保护条件处置，并在 RESULT 留痕；
  - 历史 tag 不因文档补记而移动。发布后才能确认的事实，以后续 main 上的有标记附录追加。
- 依据：固定路径解决“在哪里工作”，commit 身份解决“看到的是哪一版”；正常增量历史同时保留开发经验、缩小 diff 和审查范围，并避免每次发布都依赖覆盖远端。
- 影响：V1.4 的干净首发工具退出常规工具链；全局工作流增加路径角色、commit 交接和最终发布责任。公开仓库 URL 属于用户入口，不按个人隐私删除；本机路径、用户名、凭据和用户数据仍必须脱敏。
